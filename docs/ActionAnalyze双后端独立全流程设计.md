# ActionAnalyze R3／R0 双后端独立全流程

日期 2026-11-24。R3 和普通 R0 是两套正式、独立的调试后端。R3 须在无 KSword 驱动时独立完成受支持的用户态分析全流程。后续实施与验收状态见[工程开工基线](ActionAnalyze工程开工基线.md)。

## 1. 两套正式控制后端

| 后端 | 异常／停止所有者与机制 | 独立性要求 |
| --- | --- | --- |
| R3原生调试 | 本端拥有唯一Windows调试事件循环；受控创建或DebugActiveProcess附加，Wait/Continue、原生上下文／TF／DR／断点、用户态页保护及恢复账 | 完成支持范围内的启动／附加、采集、停止、调试、调查、继续、归档及正常收尾；无须加载或连接KSword驱动，无须目标安装自有VEH |
| 普通R0无附加控制 | 本端用户态编排＋驱动独占会话，驱动持真实异常现场、线程控制、探针和逐项恢复责任；不引入虚拟化 | 独立验证受支持系统中的异常接入、线程门控、权限与恢复；不以原生调试后端代替未实现步骤，也不要求规则／项目／UI运行在内核 |

业务流程、证据语义、项目格式及动作契约保持一致；Qt、Win32、CLI继续各自组织会话与本端后端适配，不新增公共TraceHost、追踪DLL、统一runtime或跨端接管IPC。后端能力可复用现有底层，不要求复制两份规则引擎或归档实现。

R3指不依赖KSword自有驱动，不等于不使用Windows内核，也不等于无须管理员权限。用户进一步明确：**R3不调试驱动**，其完整流程只针对受支持用户态目标。Windows安全边界、用户／会话、目标保护级别和体系结构仍生效。R0选择也不等于任意目标、任意内核线程均可控。

## 2. 全流程的明确含义

支持的用户态目标，在R3模式应能完成：

1. 项目／计划校验，确定目标架构、权限、所需来源、断点与失联策略。
2. 受控启动或附加，绑定真实进程／线程／模块身份，建立采集与恢复资源。
3. 接收原生调试事件及实际可用的API／ETW等来源，记录写入结果、映射／内容版本、覆盖区间和缺口。
4. 在已纳入区域设防，命中后保存现场，建立可靠停止屏障，执行断点／步入／步过／跳出及有限推进。
5. 直接后台获取寄存器、可用栈、内存、模块和dump；结果归本次采样，无页面实例化。
6. 重设防并继续，沿实际来源纳入下一目标；快速下一跳必须验证准入时序，不能只靠收到日志后补attach。
7. 停采、恢复自有权限／断点／TF／挂起及待处理异常、脱离调试、封存项目与证据，保留未决项。

“能独立完成流程”不等于所有路径、字段或目标都可覆盖。未知写入、共享别名、direct syscall和自修改等仍按D/X/P/A四轴报告；缺少必需证据时该规则／自动动作阻塞，不能补造事实。

## 3. 能力边界

| 能力 | R3路径及边界 | 普通R0路径及边界 |
| --- | --- | --- |
| 用户进程启动／附加／暂停／继续 | Windows原生调试＋独立记账的线程操作；已有调试器占用不抢接 | 既有普通后端扩展，精确系统支持与独占资源先验证 |
| 上下文、断点、步入／步过／跳出 | 有成熟系统机制；通用返回边界、异常打断、锁依赖及资源争用仍须产品验收 | 不是原生后端的同一停点；现场、继续令牌及私有ABI分别验证 |
| 已知区域NX观察及内容版本 | VirtualProtectEx及原生异常事件；不要求目标自有VEH，仍有停止／重设防开销 | 原保护事务和异常消费由实际驱动能力承担；未验证不公告Ready |
| 新线程门控 | 真实CREATE_THREAD调试事件提供执行前控制基础；创建竞争、外部远程创建及恢复X时段须独立测试 | 普通notify不能替代门控；当前候选未闭合，不宣称R0自然更完整 |
| API／文件／注册表／网络等行为 | 按目标部署条件使用现有API来源、允许的ETW及系统查询；API Hook可被绕过，ETW有权限／字段／时机限制 | 按实际callback／遥测／受支持入口公告；驱动存在不代表全部store或syscall可见 |
| dump、规则、项目、CLI与GUI | 用户态独立完成，权限不足或缺页逐项报告 | 同样由本端用户态承担，驱动仅提供实际可用底层能力 |
| 内核栈／驱动执行调试／更高保护目标 | 不作为R3完整用户态流程的必需项；纯R3通用用户调试路径不具备，分别unsupported／权限拒绝 | 作为额外能力单列，需实际接口、系统条件和安全性证明，不默认支持 |
| 控制所有者被杀后保留目标正常运行 | 当前NX在途实测失败，不能承诺；正常关闭与任意死亡分开 | file cleanup／owner-death／watchdog仍待实现和实测，不从设计推定安全 |

R3下缺少R0专用字段时，规则准备阶段按字段依赖和缺失策略标blocked／unknown；不以空值代表false或“未发生”。网络断连等还须独立满足权限与协议条件，不因选择R3或R0就保证动作成功。反分析目标可能发现DebugPort／调试对象或改变行为，R3不会提供无附加／隐蔽承诺。

### 3.1 远程注入来源：在哪里观察、在哪里介入

用户追问R3／R0在哪里拦截更好。分别记录观察、同步保留本次操作、执行前停止和拒绝操作，不能把四者写成一个“拦截成功”。行为分析默认保留真实行为；剥夺句柄权限等防护动作须显式策略，不能用阻断注入冒充完整追踪。

| 环节 | R3实际路径与缺口 | 普通R0实际路径与缺口 |
| --- | --- | --- |
| 获取／复制目标句柄 | 已覆盖的OpenProcess／OpenThread／Nt及复制入口可保存请求与结果；遗漏或既存句柄不能补造 | ObRegisterCallbacks可在句柄创建／复制时观察并收紧允许的访问权；不是每次写入回调，不能由此取得写地址、字节和成功长度，既存句柄不被追溯撤销 |
| 写入、分配、保护、映射 | 已部署的Win32／ntdll入口可采参数、实际结果并在受支持同步点准备目标；direct syscall、未覆盖入口、共享视图普通store和驱动代写仍可漏 | Windows没有一个通用公开回调可供普通驱动同步截住全部NtWriteVirtualMemory／NtMapViewOfSection／保护变化或任意内存store。驱动自己调用读写接口不等于观察别人调用 |
| 新线程／APC／上下文改变 | 源侧API路径记录请求及结果；原生debug创建事件提供新线程控制基础；入队／创建不等于执行，既有线程转移另看执行证据 | 线程通知是生命周期来源，不是通用拒绝／挂起闸门，也不覆盖APC和既有线程劫持；当前KnaThreadNotify仅处理退出，不能当注入拦截器 |
| 实际进入已知区域 | 目标外原生debug接NX／TF／断点，已设防区域可观察真实取指；未知新区域仍需来源发现 | 普通无附加后端只在支持内核／私有异常路径处理自有探针；不是跨进程写入的通用钩子，需独立恢复／门控验证 |

内核遥测可补充实际取得的字段，但ETW／TI按权限、provider、版本及阶段验收，不能当任意调用的同步阻止接口。direct syscall仍进入内核并经过适用对象检查，但不等于普通驱动有公开的逐次写入观察入口。SSDT／内核inline等私有修改另列研究候选，受PatchGuard、HVCI、精确版本和生命周期约束，不作为跨版本稳定基线，不为启用它自动改变安全策略。

当前Explorer夹具的写入由R3父进程主动发起并回读，执行由R3原生debug子进程观察；尚未部署截获任意远程注入者的产品来源链。先将R3同步来源、已知区域执行和真实A→B→C独立接通；R0公开来源／控制及经过证明的专用入口逐项扩展，不声称R0天然覆盖更全。

依据：[ObjectPreCallback](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nc-wdm-pob_pre_operation_callback)、[可收紧的句柄权限](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_ob_pre_create_handle_information)、[线程生命周期通知](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/nf-ntddk-pssetcreatethreadnotifyroutine)。

### 3.2 Agent部署与API Hook的实际分工

用户提出R3／R0辅助注入后用inline等Hook作为主线。可行的实施基线是：在获授权的源进程A部署现有采集Agent，在实际选定的Win32／ntdll入口采集强类型参数、调用阶段、结果和覆盖；目标B由所选外部调试后端处理真实执行停点。只向B部署Agent不会自然得到A调用WriteProcessMemory等API时的参数。

部署手段、采集机制和调试控制分别选择：普通R3部署保留无驱动全流程；R0辅助部署是按必要性、权限和系统条件验证的可选能力。通过R0送入目标的用户态DLL及其inline Hook仍运行在R3，不因此变成内核拦截、不可绕过或更稳定。R3模式不能暗中依赖R0部署才能启动。

Hook按入口选择inline／IAT或适用断点等机制，不预设一种方式适合全部入口。复用现有Hook底层，逐项验证ABI、x86/x64、重入、LastError、异常、并发安装／卸载、原字节和生命周期；Win32与Nt层重复命中保留调用关联，不能当成两次独立写入。缺失来源、direct syscall、共享普通store及驱动代写继续显式登记，不用Hook数量证明完整覆盖。

Agent采集、外部控制和可选内核补充各有责任。安装Hook不会解决NX在途owner死亡、停止组依赖或自动发现所有新区域；已确认的Explorer恢复失败仍是独立门槛。

### 3.3 创建期与最早窗口

用户要求验证“刚创建挂起后注入”。[双架构实测](ActionAnalyze启动挂起注入与最早窗口验证-20261124.md)共68项检查通过：现有生产注入器在原始CREATE_SUSPENDED时两架构均返回299；推进到EXE入口暂停后可完成真实Agent安装并捕获构造／main，但TLS已漏过。另一个独立首导入＋小型IAT引导原型在原始挂起内布置、首次恢复后先于EXE TLS安装Hook，捕获TLS／构造／main首调。

因此创建期方案可行，现有Agent不能原样承诺最早覆盖。产品须追加早期安全子集、earlyReady到sourceReady／regionReady的无空窗交接，以及调用者CREATE_SUSPENDED责任保留；不在DllMain等待完整worker。不把测试bootstrap变成新的公共产品DLL，也不把单一IAT成功推为全部inline Hook或依赖DLL TLS已覆盖；R0注入同样需要独立证明时序。

同步下断采用已经确认的直接停点路线。R3 先实现由本端原生 debug owner 接管，明确原生附带的进程级暂停。普通 R0 的实际停驻 route 有独立能力验证，现有 TF／DR 处理不赋予 Agent 软断点接管能力。早期观察与同步停点分别确认就绪。[同步断点专项](ActionAnalyze同步全局断点与性能复查.md)

## 4. 选择、独占与资料身份

开始采样明确选择后端，拟定标识为`r3-native`／`r0-noattach`，正式枚举与schema归A0冻结。相同方法对两个后端报告相同证据意义，保留实际机制与原始错误，不能把日志或历史记录作为实时停止令牌。

计划／capabilities／采样快照至少包含所选后端、实际后端、目标／来源能力、缺失原因、恢复能力、已验证环境及证据版本。R3准备不把驱动在线、私有内核ABI、R0修复或驱动读取能力当作前置。历史阅读与规则重分析不加载任一实时控制后端。

同一目标在一次活控制会话中只由一个后端拥有控制权；R3与R0不同时消费同一异常、修改同一TF／DR或归还对方计数。R3所需临时暂停全部进入R3自己的账本；R0会话不私下补R3操作。两个后端不必同时安装或可用。

R0失败不自动切R3，R3失败也不自动调用驱动。需要更换时，先停止新准入、完成旧后端实际恢复并确认脱离，再新建采样／会话代次、重新绑定定义与验证Ready；旧stopId和恢复账不迁移。旧后端仍有未决责任时，不以切换获得第二个控制所有者。

## 5. 独立恢复门槛

当前[Explorer实测](ActionAnalyzeExplorer复杂环境验证-20261124.md)证明了R3部分机制：五类正常场景79项通过；同时确认“NX事件pending时恢复页权限再杀调试控制器”导致任务栏失效，已按授权重启恢复。该失败继续有效，不能由新的双后端定位关闭。

R3须分别记责原生事件的Wait/Continue、页保护、TF／DR、软件断点字节、每次显式挂起、必要来源和运行句柄。正常close先完成相应保护／现场恢复与正确异常处置，再确认脱离；目标原有异常继续按其原语义分发。kill-on-exit=false、子监护存活、目标进程句柄仍可查询都不足以证明目标可正常继续。

页面／UI或采集线程失效、已登记调用者死亡、CLI EOF与原生调试owner自身死亡分别验收。UI／日志不阻塞活着的原生控制线程是可实现目标；唯一owner进程或其调试线程先死亡后自动接管仍未证明。恢复能力不满足计划要求时，准备阶段拒绝相应无人值守停驻计划；不默认杀目标，也不默认新增共享宿主。
