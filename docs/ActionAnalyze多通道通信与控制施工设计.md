## 2. 关键设计结论

1. **控制权驻留在目标之外。** 每端自己的 EXE 持有原生控制工作线程、会话身份、停止账本和后端句柄。控制线程不属于目标停止组，不依赖目标堆／加载器／业务锁，也不依赖 GUI 消息循环。
2. **通道独立还需执行者独立。** 控制与日志即使各用一条管道，只要目标内控制线程也被暂停，就不能产生配置生效 ACK。外部控制可以回读原生停止状态并恢复自己持有的线程；不能通过一个已停 Agent 命令自己的恢复。
3. **控制事实可回读，通知可补读。** 停止现场、保护状态和恢复责任由真正执行该机制的后端持有。通知只说明需要查询，历史遥测包不能替代当前可消费停点。
4. **数据、控制、大块证据各有预算。** 遥测洪峰、慢盘、符号下载及 UI 筛选不占用控制命令的队列或执行线程。取消和错误也保留容量，控制洪峰仍有拒绝／合并与状态查询路径。
5. **就绪须包含必要能力和代次。** 连通、会话握手、部分 Hook 安装、必需 API 全覆盖、线程配置生效、区域探针武装是不同状态。A 的迁移放行只能依赖本次要求的实际就绪证明。
6. **不声称全局原子停止。** 用户停止组与内部页面停止屏障分开；逐个停止有时间区间。完整屏障须处理新线程和未知执行者，否则只报告部分屏障，不能恢复 X 后称持续完整监控。
7. **R3／普通R0各自形成正式独立后端。** 用户随后明确无R0环境仍须有完整R3流程，调整原R0优先定位，见[双后端设计](ActionAnalyze双后端独立全流程设计.md)。显式选R3时不连接KSword驱动，原生事件与全部临时控制由R3记责；选R0时由实际驱动能力记责。能力／恢复分别验收，不静默切换，不引入虚拟化。

## 3. 参与者、所有权和禁止的依赖

| 参与者 | 所有权／运行位置 | 可等待的对象 | 不可等待的对象 |
| --- | --- | --- | --- |
| 目标内 Hook／异常入口 | 目标进程，可能在业务锁内 | 经过验证的预分配停驻原语及本机制外部释放条件 | 日志排空、磁盘、GUI、符号、规则全扫描、暂停线程持有的锁 |
| Agent 控制线程 | 目标进程，独立于日志发送 | 本端命令、停止事件、有限安装任务 | 被暂停业务线程完成卸载／加载、归档或 UI |
| 每端外部控制工作线程 | 本端EXE，永不进入目标停止集合；向本次显式选择的R3原生或普通R0后端提交 | 所选后端的有界操作／权威状态／取消；R3原生Wait/Continue须由同一真实owner执行 | Agent在全部目标线程冻结时返回applied ACK，或另一后端代答旧stop |
| 每端采集／传输工作线程 | 本端 EXE | 有界 I/O，取消完成，有限工作槽 | 规则、磁盘刷盘、页面创建、GUI 对话框 |
| 每端规则／账本处理 | 本端 EXE 后台 | 不可变批次及预算内分析 | 持状态锁同步调用外部后端／等待用户 |
| 每端归档与调查 | 本端 EXE 后台 | 磁盘、有限并发分析／现有直接调查入口 | 在控制锁下等待 dump／符号 |
| UI | Qt／Win32 本端 | 接收已生成的有限增量 | 同步设备 I/O、整份历史解码、同步等待控制结果 |
| R0 回调／异常入口 | 明确执行环境和已验证后端 | 该上下文允许的非阻塞操作；特定同步停驻须另证 | GUI、用户态管道、分页缓冲、通用可阻塞任务 |

所有执行器均由本端会话拥有，Qt 允许 QtCore 后台对象，自动调查不创建页面／Dock／隐藏控件。现有 `shared/ApiMonitorCapture.*` 等低层函数可复用，不能把本设计实现成新的公共 TraceHost、追踪 DLL、统一 runtime 或跨端 IPC。

Agent 同步命中直接进入已登记的原生停点，由目标外所有者接管。§4 的 Agent 控制通道用于配置、绑定和可异步提交的命令。同步命中不依赖该通道或普通遥测回执。主程序手动暂停使用同一个控制协调者，按后端实际机制获取停止。[同步全局断点与性能复查](ActionAnalyze同步全局断点与性能复查.md)

停止控制的状态变更由本端一个协调者串行提交。适配器执行时不持协调锁；以事务令牌返回结果，再复核代次提交。通知、日志、GUI 回调不得在控制锁内调用。后台任务中心只登记／观察真实会话，不成为控制路径的执行依赖。

## 4. 通道拓扑与第一版传输选择

```text
目标 Hook ── 有界遥测入队 ── Agent 发送线程 ── 遥测管道 ── 本端接收 ── 规范化／归档
目标 Agent 控制线程 ←── 控制管道 ──→ 本端原生控制工作线程 ←── UI 请求／规则请求
目标异常／R0 事实 ── 后端现场与令牌 ── 驱动查询／控制 ──→ 本端停止账本
ETW 独立会话 ── 回调复制 ── 有界接收 ──→ 本端规范化
内存／栈／网络证据 ── 有界任务／分块文件 ──→ 证据索引 ──→ 按需详情
```

| 通道 | 第一版建议 | 原因与边界 |
| --- | --- | --- |
| Agent 遥测 | 沿用现有有界队列与管道，新增字段需显式版本 | 低风险接入既有事件解码；不把遥测 FIFO 提升为同步控制语义 |
| Agent 控制 | 独立本机双向管道、独立读／执行线程、可取消 I/O | 不与遥测批次共用 FIFO／锁／发送阻塞；Agent 停止时仍无执行保证 |
| R3控制 | 独立Windows原生调试事件循环、控制请求／权威状态分离；无KSword驱动依赖 | 唯一Wait/Continue owner，原生异常／显式挂起分别记责；不把日志、UI或Agent响应作为继续执行的必要依赖 |
| R0 控制 | 独立可选；版本化 IOCTL、独占会话设备文件、query／command 分离 | 主程序通过 `ArkDriverClient`，另两端沿各自既有底层访问入口；并发 I/O 按实际实现协商，不能默认已有异步 pending IRP |
| R0 遥测 | 现有预分配 ring／游标模式优先 | 丢失和覆盖可计量；ring 中的旧停止记录不能作为 continue 的授权 |
| ETW | 保留独立真实 ETW 会话及丢失统计 | 异步来源，不能在事件接收后宣称原操作尚未发生 |
| 大块证据 | 文件分块／索引与有界作业；控制只携带引用 | dump 不走停点 ACK 管道，失败／部分结果逐块记录 |
| 共享内存 | 后续测量驱动的优化候选 | 不作为首版必要条件；需要额外验证发布序、读写游标、进程死亡、ACL 和槽位复用 |

第一版不为“多通道”同时引入 RPC、socket、共享内存和新服务。传输实现可替换，但命令结果、停止令牌和覆盖语义不能随通道变化。管道名称存在、WriteFile 成功或对象 signaled 不能单独证明操作生效。

管道使用明确 DACL、拒绝远程客户端并核对对端 PID、创建身份和本次会话挑战。会话 token 用于关联，不将 token 回显视为对已攻陷目标的信任证明。低完整性／不同用户／受保护目标准入逐项记录；不为了连接成功放宽为 Everyone。

现有 Qt 事件连接身份检查主要决定富化资格，不能直接当作新控制通道的拒绝授权门。控制端点身份不符须在副作用前拒绝；同用户 SID、正确 payload PID 或已知 session token 均不足以单独授权高权限变更。复用 broker 已有真实 peer、participant 和创建身份核对，并按实际授权目标分配必要访问权限；Agent 自报 ACK 不提升为独立防篡改执行证据。

## 5. 消息与结果契约

下表是拟定义的逻辑字段，不在本文分配 IOCTL、ABI 数值或直接复用旧结构的保留字段。新增 R0/R3 结构和常量只落 `shared/driver/`，序列化不发送指针、`std::string`、Qt 对象或宿主 `size_t`。

| 字段组 | 必要字段与含义 |
| --- | --- |
| 帧 | magic、协议／头版本、头长／载荷长、消息种类、flags、架构；限制长度后才读载荷，固定宽整数，明确字节序与对齐 |
| 会话 | controllerInstance、sessionId、sessionEpoch、目标 PID＋创建身份、Agent instance／backend instance |
| 命令 | requestId、operation、期望 configRevision／coverageRevision、stopId 或 admissionId、参数摘要及有限 deadline |
| 结果 | resultPhase、原始 Win32／NTSTATUS、错误有效性、实际结果／当前状态 revision、部分失败列表引用 |
| 事件 | sourceId、sourceEpoch、sourceSequence、时钟域／原始时间、事件种类、字段有效性；事件 ID 在规范化后保持稳定 |

对字节流累积完整头与载荷；短读、取消中半包、EOF、超长和版本不符分别报告。断线后不拼接前一连接的残包。x86／x64 固定 ABI 单独 static_assert，源对象身份不能仅凭消息自报 PID。

结果阶段至少区分：

| 阶段 | 可以得出的结论 |
| --- | --- |
| submitted／transported | 本端已提交或传输完成，目标是否读取未知 |
| accepted | 接收端验证并接纳，可能尚未执行 |
| applied | 执行方确认副作用完成，带实际状态和配置代次 |
| observed | 控制端已回读相符状态；需要时用于放行屏障 |
| rejected／cancelled-before-commit | 无副作用执行，保留原因 |
| committed-result-unknown | 操作可能生效但最终回执缺失，不自动用新 ID 重试 |

取消与第一项副作用之间设提交仲裁。提交前取消赢则不执行；提交后取消只能请求后续中止并查询真实状态，不谎报已撤销。`CancelIoEx` 仅请求取消 I/O，必须消费最终完成；不复用仍在内核引用的 OVERLAPPED／缓冲。

重试相同 requestId 必须同时匹配会话、代次、操作和参数，返回原执行状态；相同 ID 不同参数拒绝。去重缓存有界且不能淘汰未决命令；超过历史保留范围的旧命令拒绝并 query，不重新执行。重连先回读 session／stop／config revision，不自动恢复上一条 continue。

### 5.1 R0 通知与权威状态分别持有

首个原型优先建立预分配停止槽、逐项责任和权威 Query。通知只表示状态变化，可以合并为 resync；未释放停止责任不能被 ring 覆盖或通知取消清掉。已有 Callback Monitor 是可丢的数据面，旧 AskUser 虽有真实 pending IOCTL／取消排空，却采用全局等待与裁决语义，不能直接拿来授权新停点。

如增加异步 WAIT，携带 afterStateSequence，在同一个受保护步骤中比较状态与登记等待者；已有更新立即完成，否则等待后续变化。先提交事实，再推进序号及通知，覆盖 Query 后、挂 WAIT 前的命中窗口。WAIT 取消仅结束该次运输，不执行 Continue；queued／driver-owned／已经提交副作用分别仲裁，只有一个完成者。

等待与取消按真实 control file／owner／session 隔离，不 purge 全局队列。异步操作另持自己的 rundown、缓冲和完成责任，不能假定 dispatcher 返回 STATUS_PENDING 后通用 request rundown 仍覆盖全部寿命。FileCleanup 先置 Closing、拒绝新提交并按 file 撤销运输，再排逐项恢复；duplicate handle、owner 死亡与控制租约分别处理。

## 6. 准入状态机与快速多跳

### 6.1 就绪不合并成一个布尔值

```text
Discovered → IdentityBound → ReaderPrepared → Connected → SessionAccepted
           → ConfigApplied → RequiredCoverageVerified → ProbeArmed → Ready
任一步失败／取消 → HeldWithReason 或 RollbackPending → 确认清理／恢复
```

`RequiredCoverageVerified` 必须对应本次必须 API／精确入口和完整覆盖快照，未加载／不支持／部分安装逐项反馈。`ConfigApplied` 必须包含实际线程实例集合、规则快照 hash 和修订；原有 `HooksInstalled` 不自动提供这个契约。

[缺口G10](ActionAnalyze规划缺口复查与补齐任务.md)进一步拆分两条依赖：`sourceReady`说明目标身份／必需来源／实际配置；`regionReady`只说明指定mapping/content/probeEpoch的区域探针。进程来源初始化不等待尚不存在的所有未来区域；具体迁移放行才核对其required closure，必需区域未定／未Ready不授予“执行已受控”。模块卸载、外部保护变更、映射换代或必需来源失效推进coverage代次并撤销相应Ready；旧ACK不能重授放行，无法核实失效时刻则保存unknown interval。

### 6.2 A→B 的建议控制事务

1. 在已验证的同步入口拦住 A 的本次操作，冻结 A、B 实例及本次操作参数，创建 admissionId；其它异步来源只登记已发生的事实。
2. 外部控制器先准备 B 的读端、独占租约和取消资源，再发部署／复用请求。由 broker 先报告目标已创建／端点可用，不等 Hook 就绪才允许控制器建读端。
3. B 完成身份握手、必需 Hook、发现执行者所需探针和初始传播采集配置；控制器复核对应代次实际状态。
4. 提交 Ready 及证据边界，才释放 A 的本次闸门。成功／部分写入后记录真实范围和区域版本；失败操作不创建“已写入”的边。
5. B→C 使用同样事务。下一跳采集路径在允许 B 执行之前准备；尚未得知实际执行 TID 时，发现路径不能受完整 API 的 TID 过滤关闭。

若部署需要目标执行，而目标已处于停止屏障内，必须先判定能否在保持 NX 和其它执行者受控的前提下运行必要控制线程。控制线程也可能进入被监视页或等待暂停线程持锁；无法证明时保持迁移闸门并报告依赖失败，不能只延长超时。

当前子准入还存在 lease 交接顺序：发起端局部 childLease 若仍持有，外部控制器不能一边 acquire 同一租约一边让发起端等待自己。优先由本端既有 broker 流程拥有子配置与租约；如两阶段交接，则在旧句柄仍有效时确认新所有者持有，不关闭后重开。取消后晚到加载仍属于原 request／代次，保留停止墓碑和清理责任。

当前 CreateProcess 包装在原函数返回后才纳入子进程，原本未挂起的新子进程可能已执行下一跳；不能把后置部署说成首条业务执行前准入。调用者原有 CREATE_SUSPENDED 责任也不能擅自解除。目标初始化与 loader 前进条件未证实时，分别报告本路径缺少的前置保证。

自传播／循环 A→B→A 需要实例去重与已有就绪代次复核；不能递归同步持有两端控制锁。并发指向同一 B 的准入合并为一个部署事务，分别保留发起者等待令牌及取消；取消一条边不撤销其它会话仍需要的监控。

### 6.3 配置生效边界与事件跨代

配置发布采用不可变快照，每次调用入口取得其实际 configRevision，返回事件继续引用入口修订。安装中已在途调用、刚进入包装的线程、稍后完成的异步操作不能被新 revision 重新归类。配置 ACK 说明各类路径实际生效条件，不用“当前 revision”给所有历史事件补标。

必需 API 和线程采集配置要报告精确身份、最终覆盖快照 hash／revision、应用结果与失效原因；多个目标／线程逐项生效，不声称同一时刻全组原子切换。若某同步入口必须在本次 A 继续前覆盖，由准入事务建立因果屏障；其它 B 既有活动的覆盖起点分别保存。

来源序号在采集发布契约中定义：尝试分配序号后队列拒收可形成可计数缺口，主动来源过滤另记 suppression，不与传输丢失相混。进程退出前无法送达的尾部丢失可能未知。序号连续也不证明源前置过滤、未安装 API 或其它未采集路径完整。

对每条控制 ACK 保存实际目标状态版本，以及可取得的本来源事件水位。跨源水位没有同步保证时不填统一值；被暂停的来源不会自然推进，规则不能仅因等待超时就确定“没有后续行为”。

## 7. 停止、受控推进与恢复账本

### 7.1 三种状态独立保存

| 对象 | 状态举例 | 不允许的推断 |
| --- | --- | --- |
| 线程 | pause-requested、held-by-session、native-stop、exited、release-pending、unknown | SuspendThread 返回成功不单独证明现场已经可读；有挂起计数不代表本会话拥有全部计数 |
| 页面／区域 | NX-armed、transitioning、X-for-selected-step、rearm-pending、mapping-stale、restore-failed | 本进程 NX 不证明共享别名不可执行；当前相同地址不证明还是同一内容版本 |
| 控制事务 | barrier-building、barrier-complete、stepping、rearming、user-held、recovering、unresolved | 业务暂停回执不能替代页面已经重设 NX；一个线程退出不能代表停止组清理完成 |

账本至少包含：会话／停止／屏障代次、真实线程句柄和创建身份、本会话额外挂起次数、原生事件或异常令牌、原始与当前保护、映射／字节版本、TF／DR 修改责任、并发异常现场、每步原始错误和未决恢复项。

命中时保存的异常／调用现场与稍后读取的停驻等待现场是不同文档。线程已经在 Agent 的等待函数中时，GetThreadContext 可能只反映等待路径，不能拿它替代原始命中 RIP／参数，也不能直接把等待函数现场改成载荷入口来冒充恢复。后端须明确原现场存放、读取权限、提交校验和返回异常／调用路径的责任。

### 7.2 NX 执行进入后的次序

```text
保持 NX → 外部控制保存真实命中 → 建完整必要线程屏障
→ 配置选定线程受控推进 → 确认屏障后恢复 X → 只释放选定线程
→ 到达已验证的安全边界 → 重设 NX 并确认 → 释放其它自有停止责任
```

内部停止集合包括可能进入共页的未关联执行者；临时停止不产生恶意归因。用户的全局断点默认仍只选已关联线程。所有目标用户线程都停时，禁止把“先给 Agent 发恢复命令并等待 ACK”放在外部释放前。

连续枚举两次没有变化不能证明完整新线程屏障；产品需要已验证的新线程准入／创建门控或更强机制。在该机制完成前，夹具只声称固定已知线程集合。长循环、调用进入同页运行库、自修改、并发异常、跨页指令和退出各有有限推进策略；超预算保留当前停点交用户，不自动放开全部线程。

具体候选／否决条件见[缺口G03–G10及页保护源码补核](ActionAnalyze规划缺口复查与补齐任务.md)：传统notify与Ex NonSystem上下文分开，禁止在通知里阻塞等部署；资源预留／可信异常接收／逐段原保护／armed发布必须在可靠门控内完成。原frontend的统一READONLY/READWRITE转换、先改保护再注册、命中即恢复均不能直接提供新事务保证；普通R0负责实际执行／恢复时也须通过同样判据。同线程TF／DR、用户和临时断点由本端唯一资源账仲裁，未知AV／外部#DB继续原异常所有者的真实语义。

恢复按机制逐项处理：继续真实调试事件、归还自有 suspend、清理自有 TF／DR、撤销页保护是不同操作。只执行相应后端接受且令牌匹配的步骤。用户保持停点在自动调查完成后不自动解除；释放失败保留账本和重试入口，不先删除记录。

按最新双后端要求，采样显式选择R3原生或普通R0，所选后端独立执行并持有适用控制责任；上下文、调查和插件适配所需临时挂起也进入同一账本。副作用前预留责任，执行后提交原始结果；丢ACK先按requestId查询，不能再补一次Suspend。页保护／NX重设防、真实异常继续及恢复分别记录，实际接口与系统条件逐项验证。选R3不以R0页保护或恢复接口补足缺失步骤，选R0也不私自增减R3计数。

R3是独立正式后端，在不支持R0的环境中仍可完成受支持用户态流程。后端、来源缺口与恢复能力在capabilities／会话计划中可见，分别通过恢复测试；超时、坏包或资源冲突不触发自动换后端。更换前必须清退旧后端责任并确认脱离，再新建采样／epoch重新绑定。已有独立调试器、历史命令和机制夹具保持各自范围，R3证据不升级为R0产品证据；Explorer已确认的pending异常owner死亡失败仍未解决。

### 7.3 故障与进程死亡

| 情况 | 设计处理 |
| --- | --- |
| 接收／日志线程超时，控制仍存活 | 独立 query 真实状态；保持当前迁移闸门，提示具体阻塞项，不凭心跳续租认定全部 Ready |
| Agent 全停 | 标记控制执行不可用；外部机制回读／释放自有责任，恢复必要执行者后才可能得到 Agent applied ACK |
| UI 关闭或卡住 | 本端会话继续或依既定关闭策略执行，控制所有权不随控件销毁丢失；跨线程收尾不等待 GUI 确认来释放内部锁 |
| 控制 EXE 崩溃 | R3 SuspendThread 没有自动归还保证；同 EXE 的另一线程不能在进程死亡后救援。需按后端能力验证驱动 Cleanup／owner-death 或明确列为未支持故障，不能暗增新守护宿主 |
| 驱动设备文件 cleanup | 仅清理其所有者资源，遵守实际后端恢复顺序；不假定每类旧会话都已经绑定 FILE_OBJECT |
| 目标退出 | 以保留对象的真实退出状态退休；管道断开不单独证明目标退出，PID 后续复用不接管 |
| 页保护／上下文恢复失败 | 保留对象、版本与责任，暂停后续准入；显示 unresolved，不发布“清理成功” |

正常超时默认保持拦截并由用户决定，这与“控制所有者已经死亡”不同。owner-death 的动作必须在启动时按机制声明并验证，不能既承诺永久保留闸门，又承诺无人执行的自动恢复。未经用户明确选择，不把终止任意目标当作通用恢复。

Agent 心跳停滞与租约过期也不能直接解释为会话无人所有：外部协调者可能正有意冻结全部目标线程。暂停前记录执行不可用原因，租约活性由真正运行的外部所有者维持；是否拥有不凭 UI timer 或目标线程心跳判断。异常／TF 仍在途时不得通过超时把停止令牌转交新会话。

当前 Agent 没有向外部可靠公布 worker／sender 角色线程的完整创建身份，新控制握手须绑定角色、TID、线程创建时间和 Agent 代次，外部核对句柄归属后才可选择性放行。只恢复角色线程仍可能被已停业务线程持有的堆／loader／Agent 锁阻塞；全停快路径需预分配状态及无业务锁的安全点，安装／卸载 Hook、读 INI 和大对象构造不进入该路径。

独立审计已完成，父会话读回报告并核对下表关键源码。以下是当前实现差距及后续施工要求，本轮未修复产品或加载驱动。涉及已有虚拟化后端的对照仅用于识别资源预约和消费者差异，不改变本能力的非虚拟化范围。

| 当前实现与定位 | 直接后果 | 后续必须完成的修复／回归 |

命令实际释放本会话责任，不等于线程已经被调度执行；previous count>1 时可能仍有外部挂起，previous=0 表示账本冲突。外部工具若先消费本次计数再增加其它计数，仅凭总数无法恢复归属，不能承诺任意并发工具下的精确自动纠正。

配置过期不得继续授权新 STEP 或扩展放行，但也不能封死精确归还既存责任的入口；恢复保留产生时的 epoch、原身份和责任 token，由相应机制校验。owner 死后残留旧 file 的失败项要可诊断；新 file、同 PID、管理员身份或新 sessionId 不自动取得接管权。本轮不增救援宿主或未经授权的接管协议。

R0 等待必须按真实执行上下文判断：当前 KNA 有特定用户异常、IRQL／所有权条件下的合法停止等待，不能写成异常里一律不能等；IPI、通知回调及其它系统路径不能因此照搬长等待。文件遥测还须区分 requestor PID 与 observedOnThread，缺少真实请求线程身份时不得以当前回调 TID 补授控制资格。

独立报告位于 `.codex-build-logs/behavior-planning/action-analyze-r0-control-audit.md`，其 T01–T29 为 **29 项待执行** 的外部判据测试，覆盖运输取消、恢复失败、租约、并发命中、完整屏障、协议混用与性能；本轮没有这些产品运行结果。现有 Close 外层约三秒循环也不是底层每次恢复调用的硬超时保证。

## 8. 事件、证据与内存生命周期

资料归属更新为“分析项目 → 多次采样 → 本次运行会话／证据”。项目持久保存断点定义及配置修订，采样保存实际快照、运行期变化和结果；运行会话继续持真实停止／恢复责任。归档、事件和 UI 投影保留 projectId／sampleId 归属，历史按采样分页，不把全部采样一次载入内存。见[分析项目设计](ActionAnalyze分析项目与多次采样设计.md)。横向比较暂列待做，不引入比较实现或公共运行宿主。

规范事件使用紧凑有类型头及有限字段／blob 引用，发布后不可变。保存来源、原时间／时钟、进入／返回阶段、字段有效性和丢失账目。迟到符号、模块、签名、内容扫描另建附加记录，注明查询时间及版本，不覆盖事件时事实。

来源序号只保证本来源发布顺序；QPC、CPU 和时间相近不能凭空产生跨源因果。允许有限乱序缓冲及水位，迟到超窗保留证据并标记分析边界。历史回放不能重放原会话的 pause／continue 副作用。

| 存储 | 保留内容 | 释放条件 |
| --- | --- | --- |
| 原始接收块 | 原协议包／解码字段，按块编号 | 归档与分析取得所需引用后释放；慢消费者使用磁盘位置，不能永久 pin 全会话 |
| 对象／字符串索引 | 本会话身份和重复字符串 | 生命周期与引用计数＋预算，地址／句柄复用产生新代次 |
| 规则状态 | 有限窗口、字段摘要、事件 ID | 正常过期／退出／失效；容量淘汰与正常过期分开记账 |
| 停止现场 | 令牌、寄存器、保护与恢复责任 | 原生确认恢复或目标真实退出；未决责任不能因 UI 淘汰而释放 |
| 大证据 | 区域版本、栈／dump／网络分块 | 文件引用计数及会话保留策略；不随表格行删除 |
| UI 投影 | 有界行、密度桶、图节点／边及已展开缓存 | 窗口淘汰／关闭／换代；读取历史走异步分页 |

预算按条数、字节、最旧年龄同时限制，三端分别配置。核算公式为：接收与发送块＋对象索引＋规则状态＋控制责任＋区域／栈缓存＋归档缓冲＋UI 投影＋在途任务；峰值还要计上操作系统管道缓冲及反序列化临时值。

不在内存同时常驻同一事件的二进制原包、Base64、完整 JSON、格式化字符串、详情树及传播边副本。保留旧 JSONL 兼容时在归档线程生成，UI 不解析整文件。事件写入和索引提交分开记录水位，崩溃恢复校验长度／校验码与已提交索引，不将排队数显示为已刷盘数。

容量不足不静默丢弃控制令牌；达到控制责任上限时拒绝新的准入并保留现有责任。遥测丢失需记录层次、来源区间／未知尾部和受影响规则；磁盘满按会话策略停止新采集或显式降级，已有停止组保持可控。

### 8.1 控制资源与历史记录分别限额

探针武装前，为本次可产生的停止责任预留原生状态槽、唤醒原语、继续／重设防命令与结果位置。已经存续的 stopId 的恢复槽不得与可拒绝的新准入命令、历史日志或 UI 消息争用最后容量；恢复完成前不能因年龄／显示淘汰回收。重复请求账本也必须保留未决恢复命令，历史去重范围之外的旧请求明确拒绝。

控制历史归档的有界镜像满时，记录控制历史缺口并停止新增武装；仍保留当前原生状态和恢复责任。这个设计隔离的是资源与执行依赖，不是未经测量的实时延迟保证。离线模型目前只验证控制预留及有限命令缓存，不验证产品每 stopId 恢复槽的实现。

### 8.2 数据路径源码核对与预算计算

当前 API 的 `WinAPIDiskArchive::append` 在读端调用栈内生成 JSON／Base64，达到阈值同步 WriteFile；它有缓冲和 accepted／written 计数，但不是独立归档工作线程。后续提取必须回归旧 JSONL 字段、停止刷盘和读端生命周期，不能在复用时误称已经完成控制／磁盘隔离。

ETW 的 EVENT_RECORD 及载荷只在回调期间借用；异步处理前须深拷贝必要的 header、UserData、extended items 及其长度，不只复制指针。新规范化层保留字段身份和原始证据，不从摘要文本逆向补造未采参数。

预算按 `所需条数≈峰值输入率×可容忍消费停顿` 计算，实际容量取 count／byte／age 最先到限者。举例而非性能承诺：原包 1000B＋假设 256B 规范头，在每秒 10 万条时仅这两项约 119.8MiB/s；32768 条缓存仅覆盖约 328ms，尚未计字段、索引和其它来源。增大队列不能修复消费者长期低于输入速率的问题。

subagent 的可调数值预算候选保存在本地设计审计记录，本文不直接采用 1GiB 或其它未测量值作默认预算。原型须分别量出唯一分配字节、引用归属、分配器余量、目标端 Agent ring／退役代码和本端 RSS；逻辑窗口字节不是进程硬上限。

UI 只处理可重建投影。共享 `AsyncOperation` 已有普通查询和 `submitTransaction` 两种入口，后者可用于 UI 发起的一次已接纳事务；持续原生控制／恢复责任仍由会话所有者持有，不能等已销毁页面的 apply 回调决定是否清理。图、表和详情共享工作台总提交预算，不能各自消耗 4ms 再声称整页只占 4ms。

### 9.1 拆分与适度重构的准入

### 9.2 CLI 结构语言与进程生命周期

CLI 与 Qt／Win32 一样拥有本端会话。一个 CLI 进程退出后，它的线程、管道句柄及停止账本不能继续作为有效控制器；不能设计成第一次 `trace start` 已退出，第二次 `trace continue` 仍天然拥有原会话。后续命令树必须在“有限捕获进程”和“持续存活的交互控制进程”中明确生命周期，不暗增后台 daemon、共享 TraceHost 或跨端 IPC。

2026-11-24 用户再次明确，长程 CLI 不能只靠启动参数。持续存活的控制进程须支持运行期间的双向输入：人工终端命令及 AI 的 stdin／stdout 结构协议，输入、控制、采集、输出各有独立执行责任。有限捕获保留为一次性自动化入口，不替代持续会话。

参数、请求、结果、事件分别有 schemaVersion；数字地址／64 位身份采用无精度损失表示，缺失字段保留 known／null／原因，错误保留原始来源与码。标准输出遵守所选格式，诊断放标准错误，完整 JSON 文档与流式 JSONL 不隐式混用。stdout 阻塞时控制仍须可执行，但不能保证 ACK 已交付；有限帧和优先队列不能抢占已经阻塞的 OS 写操作。

自然语言说明和 JSON 使用相同真实结果：accepted 不能表述为 applied，超时后的未知结果不能提示 AI 自动换 requestId 重试，continue／step 必须绑定当前 sessionEpoch、stopId 与请求身份。结构查询不隐式启动或恢复目标。命令树、消息 schema、收发／关闭生命周期和拆分建议见[长程 CLI 会话与结构协议设计](ActionAnalyze长程CLI会话与结构协议设计.md)；所有新增命令／别名／参数实现同步内置 help 和 CLI 文档。
