# ActionAnalyze 执行覆盖与逐路径验收

日期：2026-11-24。状态：依据用户对脏内存追踪原理的复核补充；没有实现新探针、注入、运行样本或加载驱动。与[主规划](恶意行为单点追踪与调试能力规划.md)、[页面机制验证](非虚拟化页面执行探针验证-20261124.md)及[施工任务](ActionAnalyze施工任务与契约落点.md)共同使用。

## 1. 对“这些是否都能直接监控到”的准确回答

**对已纳入、已设防的实际执行区域，执行入口发现原则上与注入手法无关。** NX探针在实际取指尝试处产生异常，不要求由CreateRemoteThreadEx创建新线程；APC、被改上下文的既有线程、Hollowing后的入口和反射装载代码，只要进入已设防区域，都属于同一执行观察问题。并不需要为每种调度手法单独造一个“执行传感器”。

这个结论的前提不能省去：目标映射／页面可控、设防早于取指、异常进入可信消费路径、当前线程可识别，放行和重设防期间其它可进入者均受可靠门控。当前产品后端尚未满足全部前提；已运行夹具仅支持两个事先已知线程的受控例子。

“发现区域执行”与“自动找到尚未知的新区域”是不同问题。已知脏区复制／解密／重定位到新地址，或经共享别名写到另一个可执行视图时，NX不会把可疑标记自动传播到新地址。连续跟随需要发现相应操作或影响关系、建立新映射／内容版本、完成设防再观察执行。只进入未修改的正常模块、ROP片段或内核路径时，也不能据旧脏页探针宣称全程覆盖。

## 2. 四条独立结果轴

| 轴 | 必需事实 | 不能被什么替代 |
| --- | --- | --- |
| D：区域发现及版本 | 实际目标实例、映射代次、有效范围、写入／映射／内容变化依据 | API名字、请求长度、“私有RX”标签、周期脏位扫描 |
| X：执行进入与确认 | probe版本、实际RIP与线程、取指异常；受控推进后的独立执行结果 | 创建线程、APC入队、SetContext、可执行权限、入口地址参数 |
| P：后续影响及新区域纳入 | 已关联活动影响下一对象／范围的证据、Ready时刻与缺口 | 同进程后来所有动作、hash相等、相邻日志或永久恶意线程标签 |
| A：来源归因 | 原始写入者／输入／传播边、强实例、时间与成功范围的依据 | X命中本身、目标里存在可疑字节、某个API调用者的事后栈 |

每路径分别记录D/X/P/A，不给一个总“支持”勾选。NX异常停在尚未执行的指令前，先记进入尝试；只有可信执行事实才能提升为已执行。页粒度告警不自动证明命中的是页内可疑子区间；真实RIP、内容版本与范围相交关系仍要核验。

## 3. 路径矩阵

本表描述要验证的条件，不是已支持清单。每行从自有无害目标和独立执行计数／已知字节开始；具体系统支持、普通R0和完整线程门控均待实测。D/X/P/A的证据字段按[事件契约](ActionAnalyze事件身份与协议契约.md)统一，不能用路径标签填造字段。

| ID／路径 | 已设防后X是否依赖手法 | D／P／A需要额外补齐 | 必测负控与独立完成判据 |
| --- | --- | --- | --- |
| P01 CreateRemoteThreadEx及Nt创建线程 | 不依赖；任何实际进入受控区域的线程应触发 | 实际创建结果、目标强实例、入口与参数区分；写入成功范围及探针先Ready | 创建失败／入口不在脏区／创建后从未运行；X真实TID和计数对照，不把创建成功叫执行 |
| P02 QueueUserAPC及原生APC变体 | 不依赖；真正投递并进入区域时观察X | APC目标线程身份、入队／投递分开、实际例程；早期投递准入是否受支持 | 入队成功但线程不进入可投递状态、例程正常模块；无X只能报排队或覆盖不足 |
| P03 线程劫持／SetThreadContext | 不依赖；恢复后进入脏区时观察X | context请求／实际写入、寄存器、原挂起责任、恢复结果与真实RIP | 改context失败／恢复未发生／改后又改回；不从RIP请求值推实际跳转 |
| P04 Hollowing／映像替换 | 不依赖；新映像实际执行页已设防即可观察 | 原映射退役、新映射及内容版本、入口／context和初始线程；重定位涉及的内容关系 | unmap／写入／context任一步失败；旧基址重用不得继承旧映射；正常启动／重定位负控 |
| P05 反射DLL／手工映射 | 不依赖系统模块表登记；实际页内X可发现 | 分配／复制／解码／重定位及权限变化；loader与最终模块两段分别纳入 | 只运行loader但最终模块未入监视；合法JIT／运行时载入；候选PE字节不证明DLL已执行 |
| P06 分段注入／多块拼接 | 每一段已设防时均可发现其X | 不连续范围、分块覆盖／顺序、内容版本，跨段跳转和新块Ready | 首段有X、第二段故意不设防应暴露漏跟；片段顺序改变／部分写；不得用首段成功宣布整链完整 |
| P07 复制／解密／解压到新区域 | 新区域设防后可发现；旧区NX不自动涵盖新区域 | 本进程普通store可能无远程API；需要对应写入／转换来源或明确候选关系与新探针 | 同hash无因果、先执行后纳入、解码未完成；有X而A未知允许保留，不反推完整变换 |
| P08 共享section／跨进程视图／别名 | 只对真正设防的执行视图成立 | section／offset／view身份，写视图到执行视图映射；普通store及COW改变共享关系 | A写RW视图、B从不同VA的RX视图进入；B未设防时须报告缺口；同文件不同offset负控 |
| P09 已有映像代码洞／stomping | 已有页也可设防，进入时不要求新分配 | 写入前后内容、原映像身份／COW、页内子范围及正常代码共页 | 正常同页入口只报页观察不判可疑子区执行；写回原字节、晚加载模块和地址重用 |
| P10 线程池／回调／纤程等既有执行者 | 不要求新线程；进入已设防区域应可见 | 完整线程集合／新线程门控；关联活动有效时段，合法切栈 | 正常线程池下一份工作不永久恶意；纤程切换不按TID之外猜新线程；固定已知worker夹具不代替真实集合 |
| P11 direct syscall／无Win32包装路径 | 一旦区域设防，X与调用入口无关 | D/P/A若只靠R3包装会漏；原生内核来源与同步时机须独立证实 | 去掉包装日志仍产生执行；如果没有D导致未设防，必须承认覆盖缺口，不能声称NX会自己找到 |
| P12 内核／第三方组件代写 | 一旦区域设防，目标用户态X仍可观察 | 代写实际范围／请求者及内核执行者分别记；来源权限和接口支持未知 | 仅看最终页不能补最初请求者；不因工具自身R0操作而虚构攻击链；内核代码执行不由用户页探针覆盖 |
| P13 同进程栈控制数据破坏／ROP | 进入已经监视的脏代码页可观察，但复用未修改代码可全程不触发该页 | 异常／GS/CFG/CET、slot生命周期／显式watch、真实转移；见栈专项 | 良性stack exhaustion／fail-fast／尾调用／unwind；API前call字节不匹配只作候选，不能叫完整ROP检测 |
| P14 自修改／再次覆写／RWX并发写执行 | 当前版本设防且覆盖保持时可观察X | 监视有效期间的新写入、版本切分、保护冲突；同页推进期间的写入与取指时序 | 第一次命中后改字节再执行、其它线程同时写；旧hash不当执行时字节；X放开窗口须负控 |
| P15 释放／重映射／地址重用 | 新映射重新设防后可观察；旧probe不能直接沿用 | allocation/mapping代次与退出事件，旧slot／region／binding退休 | 相同VA换成正常新映像、PID/TID复用；旧ACK不得武装新实例，退休后的执行不沿旧归因 |
| P16 未修改正常模块调用与快速下一进程 | 若进入未设防正常模块，不能靠原脏页继续逐指令记录 | 已关联执行活动的后续API／内核事件与候选影响；B→C准入，必要时另研究PT/DBI能力 | 正常宿主调用、瞬时B→C、B先退出；没有调用／转移来源就记录gap，不把“代码跟随”宣传成全指令轨迹 |

## 4. 页面屏障的公共验收条件

1. Arm记录真实mapping/content/protection代次、范围、来源及Ready时刻；后置发现只覆盖从Ready开始，不能补历史执行。
2. 执行异常保存实际线程与RIP、访问类型及probe epoch；读写AV／被消耗Guard不计执行。
3. 恢复X前持有完整相关线程集合并门控新生线程；未知集合、容量满或并发异常无法接纳时不假报屏障完成。
4. 仅选定执行者受控推进，页内长循环、跨页指令、异常、系统调用、TF被改与外部调试器逐项验；推进预算耗尽不无限单步。
5. 先回读重设防完成，再放其它线程；页保护／映射外部变化复核预期值，恢复第N项失败保留原生责任和精确重试。
6. independent witness保存实际执行次数、线程、已知字节或预定位置；产品事件与它对照。不能让探针自己报告的计数同时充当唯一外部判据。

全停方案解决的是恢复X期间其它执行者偷跑的窗口，不能证明所有写入都已被记录，也不保证任意普通程序持锁时都能无扰动推进。停止范围、锁依赖和扰动分别度量，不从两线程夹具推导全进程已验。

机制补齐按[缺口G03–G10](ActionAnalyze规划缺口复查与补齐任务.md)：已有notify不当完整门控；普通store／解码新落点只在有实际来源或已布设限定写观察时推进发现。保护计划逐段保留原权限，不给RX新增W、不为写观察去掉原X；未知保护组合拒绝。NX命中后close／owner死亡、安装半途失败以及外部保护变化均核验恢复顺序；受控单步的#DB、REP部分推进或异常不直接等于完整指令已执行。P01–P16的分类数量不因这些补充而当作新增通过数。

## 5. 记录、归因与用户显示

每路径验收记录固定 `caseId / port / OS及PE-PDB / source版本 / D-X-P-A证据引用 / probeReady / 第一次取指 / 实际执行确认 / nextReady / gaps / 原生恢复 / budgets / result`。字段名为规划约定，正式schema归A0；未采时保存原因，不能填时间零冒充顺序。

图和行为行分别显示“已纳入观察”“发现进入尝试”“确认执行”“直接来源／候选关联／策略纳入”和中断区间。进程持续收集可作为保守超集，但不能让其每个正常线程、后来工作或正常模块永久继承恶意归因。源线程退出不删历史边；重复写、重新纳入及取消订阅使用新有效时段。

公开能力应写成“在指定系统、来源和屏障条件下，已设防区域的执行发现覆盖Pxx”，并分别列自动区域发现和来源归因范围。当前只完成局部机制验证，尚无产品P01–P16通过清单；**“入口发现与注入手法无关”是成立的机制判断，“这些链条已全部自动监控”不是当前实现事实。**
