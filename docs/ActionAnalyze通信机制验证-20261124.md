## 2. 原生 IPC：独立执行者和传输路径

源码：[夹具目录](../tools/action_transport_validation/)，实现为[独立 cpp](../tools/action_transport_validation/ActionTransportValidation.cpp)与[头文件](../tools/action_transport_validation/ActionTransportValidation.h)，均登记在专用工程／filters，没有 `.inc` 实现。运行入口是 [Invoke-Validation.ps1](../tools/action_transport_validation/Invoke-Validation.ps1)。

环境：Windows 10 专业工作站版，`10.0.19045`，x64。编译宿主为 amd64 MSBuild、MSVC `14.44.35207` HostX64，BelowNormal，`/W4 /WX`。中间目录固定为 `tools/action_transport_validation/x64/Release/`，最终输出为 `Ksword5.1/x64/Release/ActionTransportValidation.exe` 及 PDB，没有创建临时运行副本。

### 2.1 同一执行者的负控

子进程先在遥测管道同步写入 1 MiB，再由同一个线程读取控制命令。父进程看到写入尝试事件、管道已有数据、写调用尚未完成，并通过共享内存独立观察实际应用计数。

命令 101 成功进入 OS 管道后，在有限观察窗口没有应用副作用或完整 ACK。父端排空并校验 16,384 个固定遥测帧，随后**同一个命令 101** 才应用并收到匹配 ACK。

这是依赖关系对照，不是仅凭超时断言永久死锁：解除遥测阻塞后，同一操作继续推进。

### 2.2 分通道和分线程的正控

新子进程使用独立遥测写线程、控制读线程及管道。遥测写调用仍未完成时，命令 202 已实际应用，父端收到与会话／命令／线程身份相符的 ACK。

该结果支持控制与数据分执行者、分阻塞路径的设计，不证明任意锁依赖、日志实现或产品 Agent 都已经如此拆分。

### 2.3 全部已声明应用线程停止

第三个自有子进程声明三个应用线程：主业务计数、遥测写入、控制读取。父进程逐个取得真实线程句柄并复核所属子进程，增加一次自有 suspend 后成功读取 `CONTEXT_CONTROL`，才报告本夹具屏障成立。

命令 303 可以进入管道，但在三个声明线程均停止时，没有新应用副作用或 ACK。父端只释放控制线程的自有挂起，随后获得匹配 ACK；主业务线程上下文／计数保持，业务与遥测的挂起责任仍在。

这直接说明：独立管道不能让停止的目标控制线程运行。继续／配置 ACK 的实际执行需要运行中的目标线程或目标外原生控制机制。

冻结范围只包含这三个预先声明线程，不包含运行库额外线程或动态创建线程，不能称任意进程完整停止屏障。此实验没有页面探针、目标锁、Hook 安装或 TF 推进。

### 2.4 管道与清理证据

控制使用固定 64 字节帧，实际按 5 字节写、最多 7 字节读累计，验证分片不能被误当包边界。对端身份由自建进程句柄／创建时间／主映像路径／线程归属核对；句柄继承使用显式白名单。

报告的管道配额为 4 KiB，`PeekNamedPipe` 实测可见完整 1 MiB 待完成写入。**配额不是本次观察到的缓存硬上限**；背压证据是写调用未完成、排空后恢复，不以“最多缓存 4 KiB”表述。

三个子进程均正常退出，退出码 0、无强制终止，全部父端自有挂起责任释放。取消后等待工作线程／子进程结束确认，不把 `CancelSynchronousIo` 返回当作完成；缓冲覆盖写调用全生命周期。本次没有创建测试配置或持久命名 IPC 对象。结束时自有夹具进程检查为 0。

源码审阅发现外层超时结束父进程时，冻结子线程无法执行自查退出。因此补充每个 Session 私有且不继承的 `KILL_ON_JOB_CLOSE` Job：精确自建子进程保持初始挂起，完成分配及成员／限制／非继承属性回读后才首次恢复；分配失败只清理该精确子进程。Job 句柄不进入继承白名单，不修改宿主 Job。最终增量构建和三阶段重跑共 37 项通过，包含新增三个配置回读断言。

关闭 Job 能清理已纳入的自有测试子进程，不要求其线程执行；它不是生产目标恢复方案，也不把终止目标当恢复成功。正常通过仍要求先归还全部自有挂起并观察子进程正常退出。**未执行杀父故障注入**，元数据 `parentKillFaultInjectionTested=false`；异常父退出路径目前只具源码核查及 Windows Job 语义依据，不能写成故障运行验收已通过。

最终各阶段单次总耗时为 735／500／734 ms，其中包含预设观察窗口和协调开销；不是 ACK 延迟分位数、吞吐或性能门槛。原 34 项结果属于加入 Job 前的一轮，本记录以最终 37 项产物为准，不把两轮重复断言累加。

原始证据在 `.codex-build-logs/behavior-planning/`：

- `action-analyze-transport-build.log`：构建路径与退出码。
- `action-analyze-transport-run.log`：逐项断言、实际线程、应用计数和清理。
- `action-analyze-transport-metadata.json`：环境、哈希、运行与清理摘要。

模型区分“目标停止后不能生成新 ACK”与“停止前已生成、之后由外部读到的缓冲 ACK”。外部恢复成功是一个显式输入假设，不是假装模型实现了 Windows 恢复。

模型容量是小型分析域：总队列 8、遥测上限 6、保留控制 2；实体 3、部分匹配 4、证据引用 8。只证明条数和有限身份域，不证明字节数、RSS、操作系统调度、公平性、实际恢复、生产死锁自由或完整状态空间。

## 4. 对施工的约束

1. 控制线程、管道、状态账本和容量分别隔离；只给消息加一个 priority 字段不足以消除同线程／同锁阻塞。
2. 目标外所有者持有原生恢复责任。全部目标线程停止时，不等待目标内控制线程先返回 applied ACK 才允许自己解除其挂起。
3. 准入依据当前代次必要配置与覆盖，取消后旧 ACK 不得放行新事务。
4. 停点／恢复有真实令牌，通知丢失后可以 query；队列预留不能提供无限控制交付保证。
5. 长程 CLI 还需独立验证 stdin／stdout 双向收发、输出背压、EOF 与退出策略，不能把本夹具 64 字节控制管道直接等同于 CLI JSONL 已验收。

仍未完成的关键实验：目标持堆／加载器锁、控制线程进入监视页、动态线程门控、并发异常、实际 Agent 配置／覆盖 ACK、控制 EXE 崩溃后的各机制恢复、驱动版本／部署及真实 A→B→C。已通过夹具不关闭这些待办。
