# Q-01 新增逻辑确实被测试（变异验证）

验收要求："审查链接目标和调用链；**故意改变一条生产分支，确认相应测试失败，再撤回测试变更**。"

## 1. 测试链接的是生产实现，不是测试内副本

`KswordARKLightTests.vcxproj` 直接编译生产源文件，测试只 `#include` 头文件：

```
<ClCompile Include="..\shared\evidence\EvidenceEnvelope.cpp" />
<ClCompile Include="..\shared\evidence\EvidenceJson.cpp" />
<ClCompile Include="..\shared\evidence\LiveNavigation.cpp" />
<ClCompile Include="..\shared\evidence\LosslessValue.cpp" />
<ClCompile Include="..\shared\evidence\ObjectIdentity.cpp" />
<ClCompile Include="..\shared\evidence\ScanBudget.cpp" />
<ClCompile Include="..\shared\evidence\CrossViewDiff.cpp" />
```

F-05 归一层的生产实现在 `Ksword5.1/Ksword5.1/ArkDriverClient/ArkDriverEvidence.h`（inline，与 Qt 主程序 / Light / CLI / 两个 CE 插件共用同一份驱动客户端），测试直接 include 它。

## 2. 变异注入

在生产分支 `shared/evidence/ObjectIdentity.cpp` 的 `MatchProcessInstance` 中，把"创建时间不同即不同实例"改成"确认为同一实例"：

```diff
     switch (Compare(a.createTime100ns, b.createTime100ns)) {
     case FieldCompare::Differ:
-        return MatchResult::NoMatch;  // PID 复用：创建时间不同即不同实例
+        return MatchResult::Confirmed;  // MUTANT-Q01
```

重新构建并运行：

```
  F evidence contract: 88/92 checks passed
MUTANT_EXIT=1

FAIL [F evidence contract] F-03 same PID + different creation time is a different instance
FAIL [F evidence contract] F-03 thread does not attach to a new process on a reused PID
FAIL [F evidence contract] F-03 handle value is scoped to its owning process instance
FAIL [F evidence contract] F-09 a reused PID is refused instead of handing the action to a new process
```

一条生产分支的改动被 **4 条跨 2 个验收编号的断言**捕获，说明这些断言确实击中了 PID 复用判据，而不是只测试了 happy path。

## 3. 撤回

变异已撤回（`grep -c MUTANT shared/evidence/ObjectIdentity.cpp` == 0），撤回后重新构建运行：

```
  F evidence contract: 102/102 checks passed
  X cross-view: 32/32 checks passed
KswordARKLightTests: PASS
RUN_EXIT=0
```

**注意**：撤回的是**生产代码的变异**，测试本身自始至终没有改动 —— 这符合"再撤回测试变更"的意图（不允许为了让变异通过而改测试）。

## 4. 另一条独立证据：测试先于实现发现了真实缺陷

首次运行时 `F-11 the trust statement records same-kernel origin and incomplete coverage` 失败。原因是 `BuildTrustStatement()` 判"覆盖不完整"时只看 `coverage.fullyCovered()` 与 `StatusCarriesObservation()`，而 `CollectionStatus::Partial` 恰好两者都通过 —— 一个 Partial 采集会被当成覆盖完整。已在 `shared/evidence/EvidenceEnvelope.cpp` 修正为把 `Partial` 直接计入覆盖不完整。这条不是构造出来的变异，是测试真实发现的生产缺陷。

## 5. 尚未覆盖

本文件只证明**本轮新增的 F/X 共享逻辑**被测试击中。仓库中既有的 `KernelCleanImageBaseline`、`MemoryDock`、`ProcessDock.CrossView` 等生产路径仍然没有任何测试工程引用（见 `docs/next/实现映射.md` 各行的"现有测试"列，绝大多数是"无"），Q-01 在这些模块上仍未满足。

## 6. 补充：对抗性评审推翻了 I 模块的测试有效性

在 F/X 之后新增的 I 模块（`shared/evidence/PeImageMap.*` + `ImageDiff.*`，155 项断言）经独立对抗性评审发现 **Q-01 违规**：

`KswordARKLightTests/ImageIntegrityTests.cpp:349` 的 `LiveFromMap()` 返回 `LiveImageBytes::fromBytes(0, map.image)` —— 直接把**生产归一化的输出**当成"现场"侧输入。于是文件里 17 处 `CompareImage()` 调用全是"参考对参考"，再 XOR 改几个字节。

评审 agent 按本文件第 2 节同样的配方做了独立变异：把 `PeImageMap.cpp` 复制到隔离目录，注入"在**没有重定位条目**的 RVA（targetRva64 + 0x200）上额外 rebase 8 字节"的静默损坏 —— 即让归一化后的磁盘参考本身出错 —— 重新构建后：

```
155/155 checks still passed, exit 0
```

两条招牌断言因此是同义反复：
- `:667` "a relocation-only base change yields zero unexplained differences"
- `:677` "changing one non-relocated byte produces exactly one difference"

因为 live == reference 是构造出来的。

**结论：I 模块 155/155 的运行结果不构成 I-03 / I-05 的有效证据。** 已派修复：现场侧改为由夹具独立算出"加载器会产出的字节映像"，并要求上述变异重跑后**必须有断言失败**。

这条同时说明：**变异测试必须由不写实现的一方来做**。F 模块的变异是我自己注入的（第 2 节），它证明了 F 的断言有效；但 I 模块的作者自评"做过变异测试"时用的是同一份自我印证的夹具，所以没有暴露问题。

## 7. I 模块的自我印证已修复并重新取证

修复方式：删除 `LiveFromMap()`，改为夹具侧的独立加载器 `IndependentLoadedImage(spec, relocEntries, loadedBase)` —— 它**与 `PeImageMap` 零代码共享**，自己按 `SizeOfHeaders` 拷头、按 `min(SizeOfRawData, VirtualSize)` 逐节拷贝、零填充留 0、只对夹具自己声明的 DIR64/HIGHLOW 点加 delta。所有 `CompareImage` 的现场侧现在都来自 `LiveFromSpec()`。

另加两条直接等值断言：生产的 `map.image` 必须与独立加载的映像**逐字节相同**（两个基址各一条）。

**重跑同一个变异**（在 scratchpad 副本上做，仓库文件未动）：在 DIR64 分支里对 `targetRva64 + 0x200`（该 fixture 下是 RVA 0x1300，**没有任何重定位条目**）静默多 rebase 8 字节。

| | 断言总数 | 结果 |
|---|---|---|
| 修复前 | 155 | **155/155 通过，exit 0** —— 变异存活 |
| 修复后 | 280 | **274/280 通过，exit 1，6 条失败** |

失败的断言包括：
- `I-03 at the other base the normalized image equals the independently loaded image byte for byte`
- `I-03 a relocation-only base change yields zero unexplained differences against an independently loaded image`
- `I-03 a fully covered clean comparison concludes NoDifferenceObserved`
- `I-03 changing one non-relocated byte …`

变异已从 scratchpad 副本丢弃，仓库文件全程未被修改。

两个模块的初版断言面明显不足：**S 有 13/29 条注入损坏存活、G 有 10/12 条存活** —— 和第一轮 X 模块 7/9 存活是同一个病：断言只覆盖 happy path，枚举分支零覆盖。修复后两者的变异全部被捕获。

### T 的两条 partially_fixed 及其去向

1. **`CoverageAccount` 的计数器表达不了"未知"**（T-06）。来源只报总计时（例如 ETW 只给 `EventsLost`），未知项被按 0 汇总进 `failed`/`skipped`，等于把"不知道丢了多少"写成"一条都没丢"。修复 agent 只能改自己那三个文件，而 `CoverageAccount` 在 `shared/evidence/EvidenceEnvelope.h`（禁改）。
   → **集成 owner 已补完**：`CoverageAccount` 新增 `bool countsIncomplete`，`fullyCovered()` 把它当否定项，`describeRemaining()` 返回 `counts-incomplete` 而不是一个看似精确的剩余量；`TimelineCore` 在遇到未知计数来源时置位。新增 3 条断言（F 189 → 192）。

2. **1,000,000 事件时约 1.9 GiB**（T-08）。落盘路径已改成流式（`SerializeSessionTo` 一次一批），存储改成分页 `deque`（消除整窗重分配与 O(n) 淘汰），但**存储本身不可外溢到磁盘**。真正的驱动因素是 `sizeof(TimelineEvent)` = 560 B（含 11 个 `std::string`），要压下去得改公开事件 schema。
   → **如实保留为架构限制**，不是 bug：规范第 7 节 L2 的 ≤1 GiB 目标在当前 schema 下达不到，这一条必须由后续的 schema 精简或外溢存储解决。
