## 1. 这一层是什么

`shared/evidence/` 是一层纯 C++20、**不含 Qt、不含 Win32 头**的分析代码。它不采集数据，只负责描述"这次采集是怎么回事"和"从采集结果能推出什么"。Qt 主程序、KswordARKLight 和 KswordCLI 都能直接编译它，Light 的"不链接 Qt"边界不受影响。

它解决的是规范第 4 节点名的一件事：**把"采集失败"、"分析无法判断"和"正确的空集合"变成三个不同的值**，而不是三张一样的空表格。

## 3. 怎么用

### 3.1 记录一次采集

```cpp
using namespace Ksword::Evidence;

EvidenceEnvelope envelope;
envelope.source = ksword::ark::makeDriverSource(
    "ui.driverTable",              // 这一层包装的 id
    1U,                            // 解析版本
    "r0.module.enum",              // 底层证据来源 —— 同一 collector 的多层包装必须共用
    "IOCTL_KSWORD_ARK_QUERY_MODULES");
envelope.window.bootId    = currentBootId;   // 跨启动周期禁止拿单调时钟相减
envelope.window.machineId = currentMachineId;
envelope.window.mode      = CaptureMode::Snapshot;

const auto result = client.queryModules(...);
envelope.outcome = ksword::ark::toCollectionOutcome(result.io, {result.unsupported, result.partial});
envelope.coverage.succeeded = rows.size();
envelope.coverage.totalKnown = OptionalU64::unset();   // 不知道总数就写未知
```

### 3.2 得出结论（而不是自己判"正常"）

```cpp
const AnalysisConclusion conclusion = envelope.deriveConclusion(foundDifference);
```

`deriveConclusion` 的硬规则：采集状态不是 `Success`/`Partial` 时**一律返回 `NoEvidence`**；覆盖不完整时最多到 `Indeterminate`。**没有任何路径能从"没采到"推出"正常"。**

### 3.3 对象身份

```cpp
ProcessInstanceId id;
id.bootId = bootId;
id.pid = OptionalU64::of(pid);
id.createTime100ns = OptionalU64::of(createTime);   // 缺这个就只是 Weak

if (id.crossSessionKey().empty()) {
    // 身份不足：可以显示，但不能当跨会话主键，也不能自动跳转
}
switch (MatchProcessInstance(saved, live)) {
case MatchResult::Confirmed: /* 同一实例 */ break;
case MatchResult::NoMatch:   /* PID 被复用或跨启动 —— 拒绝把操作交给它 */ break;
case MatchResult::Candidate: /* 证据不足，保留候选，不要升级成确定关系 */ break;
}
```

### 3.4 Cross-view 差异

```cpp
std::vector<SampleRound> rounds = /* 每轮包含各视图的 ViewSnapshot */;
const CrossViewReport report = AnalyzeCrossView(rounds);
// report.trust.viewCount 与 report.trust.independentSourceGroupCount 必须一起显示
for (const CrossViewFinding& f : report.findings) {
    // f.state: NoDiscrepancy / PendingRecheck / Transient / Persistent / ObjectEnded / Unverifiable
    // f.latestHits 可展开到每个视图的命中情况和源记录 id
    // f.recheckHistory 是复核历史（含间隔）
}
```

`ViewSnapshot::coversTargetScope` 必须由采集方如实填写。它为假、或视图状态不是 `Success`、或覆盖账目不完整时，该视图**没有资格**参与"缺项"推断，结果显示 Unknown 而不是"确认不存在"。

## 4. 这一层证明不了什么

- **多个视图一致 ≠ 系统没被入侵。** `BuildTrustStatement` 只产出 `limitationKeys`，结构上无法生成正向安全断言。同一个 collector 的两层包装被折叠成一个来源组，不会虚增可信度。
- **`Persistent` ≠ 恶意。** 它只表示"在满足条件的多轮复查中，成功且覆盖完整的视图始终没有列出这个对象"。判据里没有恶意分类，API 里也没有 malicious/threat 字段。
- **`NoDifferenceObserved` ≠ 正常。** 它只表示这些视图之间未发现矛盾，且覆盖足够。
- **读取本身有副作用。** 通过 `MmCopyMemory` 读目标内存会影响驻留状态和时序。任何"完全无观测副作用"的说法都是错的。
- **身份不足就是不足。** `Candidate` 不会因为再多几个弱证据就自动升级成 `Confirmed`。

## 6. 为什么没有把旧 PE 映射直接换掉

`KernelCleanImageBaseline`（2182 行、192 处 Qt 调用、含 WinTrust/签名校验）是内核代码完整性扫描的现役实现，仓库里没有任何测试工程引用它。新核在畸形节上的行为**故意不同**（按节降级为不可比较，而不是整映像 return false），换过去会改变现役安全功能的判定结果。本机没有可用的 R0 验证环境，无法证明替换后的现场行为不退化。

在不能端到端验证的前提下改写一条安全关键路径，属于规范禁止的"猜测通过"。因此本轮把新核和它的 155 项离线断言交付出来，把合并列为**下一步的明确动作**：

1. 先让 `kernelHookReadPeBytesAtRva`（inline hook 的磁盘基线，目前完全不做重定位，其自身 tooltip 已承认这点）改调 `PeImageMap` —— 这条本来就是坏的，换过去只会变好；
2. 再在有 R0 的授权测试机上，用同一批模块对比新旧 `mapPeImage` 的逐字节输出，确认一致后才替换 `KernelCleanImageBaseline`。

逐条状态以 `KSword_Acceptance_Results_Template.json` 为准；那里每条 `PASS` 都有对应的 `executions` 与 `evidence_paths`。
