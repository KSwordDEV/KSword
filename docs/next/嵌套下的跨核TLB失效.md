# 嵌套下的跨核 TLB 失效

**状态：已定案并已修复。** 2026-09-07 在 2 vCPU 嵌套 Hyper-V 靶机上量到、修好、复验。

这份文档记的是一个曾经写在代码注释里、标着 `unmeasured` 的隐患。它不是低概率事件——
量出来是 **97%**，而且它解释了此前三种没有归因的崩溃。

---

## 1. 问题

常驻起来之后，我们把 guest 的 `HvCallFlushVirtualAddressSpace` /
`HvCallFlushVirtualAddressList`（及其 `Ex` 变体，call code `0x0002`/`0x0003`/
`0x0013`/`0x0014`）原样转发给 L0。

L0 失效的是**它认为的 L1 VP**。但那个 VP 此刻正在跑我们的 L2——也就是被我们降级的
Windows 自己。兄弟核只要不发生 VM exit，就一直留着旧翻译。

**x86 的 TLB 失效本来就是每核本地的，跨核只能靠中断**，而这一步我们没有做。

### 为什么这是嵌套特有、且是我们引入的

裸机上 Windows 自己发 IPI 做 shootdown，目标核在中断处理里**自己执行**失效指令，
所以是对的。Hyper-V 来宾里 Windows 把这件事外包给 hypercall——那条链被我们截断了。

换句话说：**这个缺陷只在"我们插在 Windows 和 Hyper-V 中间"时存在。**

---

## 2. 判据：不要用"跑很久没崩"

代码注释里原本建议的测法是"单处理器对多处理器的长时间对照"。那是统计实验：
靠撞低概率崩溃取证，**跑完没崩什么也证明不了**。

换成确定性判据：

> `VirtualProtect` 返回的语义就是"所有处理器都已看到新保护"，而它内部正是靠跨核
> TLB shootdown 兑现这个语义，那条 shootdown 在 Hyper-V 来宾里走的就是被我们转发
> 的那个 hypercall。

于是：

1. 主线程把一页改成 `PAGE_NOACCESS`，**等 `VirtualProtect` 返回**
2. 返回**之后**才把 epoch 推成奇数，宣告"从现在起谁读到内容都是违规"
3. 绑在别的处理器上的工作线程在奇数 epoch 里读这一页
4. 读**成功**就是陈旧翻译——它用的是一条本该已被失效的映射

epoch 在读之前和之后各取一次、要求两次相同，用来排掉"读之前窗口就已经关了"的情况：
窗口一变就不计入，**宁可漏计也不误判**。

实现是 `hvm_ctl tlb-probe`，纯用户态，不碰 IOCTL（只在开头查一次常驻状态用于报告），
不改页表，不动驱动，跑崩不了机器。

**一次读成功就是一条证据，不用等它撞坏别人的内存。**

## 3. 读数

交替对照，2 vCPU：

| 轮次 | 常驻核数 | 窗口内取样 | 拿到 AV | **违规** | 判定 |
|---|---|---|---|---|---|
| 基线 | 0 | 10,429,398 | 10,429,398 | **0** | coherent |
| 常驻 | **2** | 180,208,570 | 5,419,741 | **174,787,358（97%）** | stale |
| 基线 | 0 | 10,644,062 | 10,644,062 | **0** | coherent |

**开关一次，现象跟着开关一次。** 这是因果，不是相关。

### 修复后

| 轮次 | 窗口内取样 | 违规 |
|---|---|---|
| 常驻中 ×3 | 6,434,264 / 6,952,434 / 6,782,150 | **0 / 0 / 0** |
| 基线 | 10,112,305 | 0 |

**除了计数归零，还有一个独立的正确性特征**：常驻中的取样量级从 1.8 亿掉回
600–700 万，与基线同量级——读会正常 AV 才会这么慢。只看"违规 = 0"可能是探针失灵，
**量级一起对上**才说明真的在走页表。

## 4. 它解释了哪些崩溃

同一条件下此前收集到三种没有归因的崩溃，现在都收敛到这一个原因：

| Bugcheck | 现场 |
|---|---|
| `0x139` (`0x1D`) | 内核分页池段堆的 RB 树节点被踩，崩在 `nt!MiRelocateImage → MiCompressRelocations`——**正是密集改页表映射的路径** |
| `0x0A` | IRQL_NOT_LESS_OR_EQUAL |
| `0x50` | PAGE_FAULT_IN_NONPAGED_AREA，**写**无效内核页 |

都是陈旧翻译的典型后果：内核用一条已被失效的映射去读写，目标已经不在那儿了。

池损坏是异步的，**栈上永远是受害者不是凶手**——`0x139` 的栈全在 `nt` 里（预读线程
给一个无关进程建 image section），七个维度并行审计驱动侧所有可能非法写内核池的
路径，全部返回空。真凶不在那些路径上。

---

## 5. 修法

### 5.1 前提先被验证，才动手

"让兄弟核退出一次就够"依赖一条属性：**未启用 VPID 时 VM entry 会失效与 VPID 0000H
关联的线性映射**。

这个前提用 `hvm_ctl tlb-probe-exit` 直接量——工作线程每次读之前先执行一条 `CPUID`
（无条件 VM exit）。常驻起着，取样 1,929,924 次，**违规 0**。

前提成立，才值得去实现 NMI 那一套。

### 5.2 第一次尝试失败，失败本身定下了设计

先只加了 NMI exiting 和广播，**第一次上机就是 `0x80 NMI_HARDWARE_FAILURE`**。

真因：**NMI exiting 只在 guest 运行时把 NMI 变成 VM exit。** 目标核若此刻正在 VMX
root 里处理另一次退出，NMI 走的是 `HOST_IDTR_BASE` 指的那张表——一直是 guest 自己
的表，其 vector 2 属于 Windows，而 Windows 对归因不了的 NMI 判硬件故障。我们每秒
上万次退出，撞上几乎必然。

**所以私有 host IDT 不是优化，是发 NMI 的前提。**

### 5.3 最终形态

1. **私有 VMX-root IDT**：从运行中的表**整份拷贝**，只改 vector 2 的 64 位偏移，
   选择子 / IST 索引 / type-DPL-P 全部保留。
   - 整份拷贝而非只填一个门：VMX root 本不该有异常，但"不该"不是保证，只有 vector 2
     的表会把退出路径里的任何差错变成**三键故障**——重置、无蓝屏、无转储，本驱动能
     产生的最难查的失败。
   - IST 索引尤其要保留：Windows 的 NMI 处理程序跑在专用栈上，stub 要转发过去。
   - 构建在 prepare（PASSIVE_LEVEL，要分配内存）。失败则不安装，VMX root 沿用
     guest 的表，行为与之前逐字相同，只是不再发 NMI。

2. **vector 2 的 stub**：用 `CPUID.1:EBX[31:24]` 认出自己是哪个处理器——这里没有
   per-CPU 指针可用，GS 是 host base。台账里**先减后补**地认领（先测后减会让两次
   投递认领同一份额度）。是自己的就 `iretq`（返回本身就是目的：这个核已经离开非根
   模式，陈旧映射死在下一次 VM entry）；不是就寄存器原样恢复后 `jmp` 到 guest 原来
   的 vector 2，中断帧逐字节不动。

3. **台账按初始 APIC id 索引**，不挂在 VCPU 上：两个消费者必须共用一份，而汇编 stub
   够不到 VCPU 结构。**两半都要**，因为 NMI 不能被要求等待——落在非根模式的变成
   VM exit 由 C 认领，落在根模式的走私有 IDT 由 stub 认领。

4. **发送端**：转发完那四个 flush call code **之后**（不是代替），给其余每个仍
   `Active` 的处理器的槽位加一，再用 x2APIC ICR 的 **all-excluding-self 短写法**
   广播**一个** NMI（省掉逐个记录目标 APIC id）。
   - **不等待**：等待就是看门狗死锁——一个需要本处理器服务的远端永远不会应答。
     不等待留下的窗口只有 NMI 投递的宽度。
   - 没有私有 IDT、或本地 APIC 不在 x2APIC 模式，就不发。是否有影响由探针的违规数
     说话。

5. **还给 guest 的 NMI 不能硬注**：VM-entry 事件注入是**无条件**的，处理器不看 guest
   的可中断性状态。所以 guest 正待在自己的 NMI 处理程序里（`blocking-by-NMI` 置位、
   还没 `IRET`）时直接注入，等于嵌套投递一个 NMI。改成先读可中断性 bit 3，阻塞就
   **扣住**并请求 NMI-window exiting，窗口开了再投递，然后**无条件**清掉那个控制位
   ——留着会持续退出，因为"能收 NMI"是常态不是事件。扣住的不会丢也不用排队超过一个：
   架构本来就把多个待处理 NMI 合并成一个。

---

## 6. ⚠️ 与 VPID 的耦合

**这条修法依赖"我们没有启用 VPID"。**

广播 NMI 之所以能治好跨核失效，是因为未启用 VPID 时 VM entry 会刷掉 VPID 0000H 的
线性映射。**一旦为了性能启用 VPID，那次 entry 什么都不刷，修法会静默失效**——而且
失效的形态就是本文开头那个 97%，不会有任何报错。

所以这两件事必须一起改：启用 VPID 的同时，把"把它打出去一次"换成"发信号 + 对方
自己 `INVVPID`"。

代价的另一面也要记住：不启用 VPID 意味着**每次 VM exit/entry 都在刷 TLB**，这是我们
现在一直在付的性能代价。

---

## 7. 对既有读数的影响

修好之前，多核 + 常驻在嵌套下是不安全的——那不是某个功能的门，是**常驻本身**的门。

**2026-09-07 之前所有的多核"全绿"读数都要打折看**：它们只说明那一轮没撞上，不说明
一致性成立。之后的不用打折。

---

## 8. 方法论

留下三条：

1. **"跑了很久没崩"对静默损坏没有信息量。** 这个缺陷在 soak 30 秒全绿的同时，
   每秒都在发生几万次。遇到"偶发、随机符号、多核才有"的崩溃，先去找确定性判据，
   别去堆运行时长。
2. **最好的线索可能已经在自己的注释里。** 这个隐患连同实验方法早就写在
   `hvm_exit.c` 转发段的注释里，标着 `unmeasured`。搜索前先问：这个仓库里有没有人
   已经把它写下来过。
3. **一次只动一个变量。** NMI 这条线分了三步落地（开控制位并接住 → 私有 IDT 纯转发
   → 加判断和发送端），每步单独验收。第二次尝试炸掉时，回退的只是最后一步，前两步
   的读数还站得住。
