# 嵌套虚拟化实现设计（L2 完整支持）

**状态**：设计稿，未开工。这一份只定方向与判据，不描述已实现的东西。
既有实现的落点见文末"现状"一节。

## 目标

让 KSword 的 thin VMM 能在自己底下跑一个**自带 VMX 的客户机**，并且：

1. **L0 与 L1 两种模式都要成立。** 裸机上我们拿到真 VMX / EPT / MTF；跑在 Hyper-V
   底下时只有 L0 愿意给的那一套 —— **实测这台靶机就没有 MTF**。设计不能依赖
   任何"裸机上才有"的能力，否则一半的场景直接落空。
2. **套内的 L2 要拿到和直控客户机差不多的能力，EPT 是其中最关键的一项。**
   这条直接决定了必须做**影子 EPT**：L1 会给它的 L2 装一套 EPT，而那套 EPT 里的
   "物理地址"是**客户物理**，不是真的物理。不合成就只能不给 L1 EPT 能力，
   等于 L2 比直控客户机少一大块。

## 阶梯与现状

协议里把嵌套成熟度定义成六级（`KSWORD_ARK_HVM_NESTED_STATE_*`）：

```
0 DISABLED → 1 CAPABILITY_ONLY → 2 DISPATCH_READY → 3 L1_VMXON
  → 4 VMCS12_CURRENT → 5 L2_PARTIAL → （目标）L2 真正运行
```

当前到 **4 VMCS12_CURRENT**：操作数解码、VMXON/VMXOFF、VMCLEAR/VMPTRLD/VMPTRST、
VMREAD/VMWRITE 都按架构语义工作，错误号逐条对 SDM。VMLAUNCH/VMRESUME 仍然按架构
拒绝，INVEPT/INVVPID 也拒绝。

整条通路由常驻启动时的 `ENABLE_NESTED_VMX` 标志控制，**默认关闭**；关闭时对
VMX 指令注 `#UD`，而在 CPUID 不报 VMX 的前提下这也是架构正确的行为。

## D0：退出安全的物理内存窗口 —— 所有后续步骤的前提

### 为什么是第一步

D 阶段每一步都要读**客户物理**地址上的内容：

| 步骤 | 要读什么 | 地址类型 |
|---|---|---|
| VMXON / VMPTRLD 的 revision id 校验 | 区域头四字节 | 客户物理 |
| vmcs02 合并 | vmcs12 的内容 | 客户物理 |
| **影子 EPT 合成** | **L1 的 EPT 各级页表** | **客户物理** |
| I/O 位图 / MSR 位图路由 | L1 提供的位图页 | 客户物理 |

而我们现在**一个退出安全的物理访问器都没有**。

### 现有的那个不能用

`KswordARKHvmMemoryTranslate` 底下的 `KswordARKHvmMemoryReadEntry` 走
`KeAcquireSpinLock` 保护的共享窗口。在 VMX root 里拿自旋锁有两个问题，任一都足够
否决它：IRQL 提升在 root 模式下是一个我们兑现不了的声明；而如果持锁的是另一个
同样处在 root 模式的核，两边互等。**那套是 IOCTL 通路的基础设施，不是退出通路的。**

### 两份参考在这里分道扬镳，结论明确

**kHypervisor 在退出处理里直接调 `MmGetVirtualForPhysical`**
（`vmx.cpp` 里 `UtilVaFromPa` 的调用点：825 / 882 / 981 / 1238 / 1239 / 1798 /
1917 / 2137，全部在 VMX 指令仿真路径上）。

另一份成熟实现在注释里把这条路**明确否掉**：它说 `MmGetVirtualForPhysical`
（作为备选方案）在 DIRQL 下不安全，因此它只在**初始化期**用它走一遍宿主页表，
运行期一次都不调。

**我们跟后者。** 理由不是"它更新"，而是这条判据本身站得住：`MmGetVirtualForPhysical`
要查 PFN 数据库并可能取锁，不是一个能在 root 模式调的函数。kHypervisor 能跑，
是因为它的测试面窄（README 自己写明"只支持受限客户机（protected-paging 模式）"、
嵌套 EPT "还没在 Windows 10 上测过"），不是因为这样做是对的。

### 设计

**初始化期（PASSIVE_LEVEL，每 vCPU 一份）**

1. 分配一页连续内存作为**窗口背板**，记住它的 VA 与 PA。
2. **手工走一遍宿主页表**求出这个 VA 的叶 PTE 的虚拟地址：从 `CR3` 起，
   每一级用 `MmGetVirtualForPhysical` 取页表页的内核别名，逐级下行。
   兼容四级与五级分页；遇到大页叶子直接失败 —— 窗口必须独占一个 4 KiB PTE。
   *这样就完全绕开了"PTE 基址随机化"，不需要去搜自映射索引。*
3. 保存叶 PTE 指针与它的原值，并**回读校验**：叶 PTE 的 PFN 必须等于背板页的 PFN。
   对不上说明我们解错了地址 —— 那时宁可不准备窗口，也不能上线一个会改错别人 PTE
   的东西。

**运行期（退出处理内）**

```
map(pa, bytes):
    拒绝跨页（offset + bytes > PAGE_SIZE）
    拒绝超出物理地址位宽的 pa
    Interlocked 抢占忙标志 —— 抢不到就返回 Busy，不自旋
    回读叶 PTE：不存在、或 PFN 已不是背板页 ⇒ 放弃并报出来
    写入新 PTE（指向 pa，保留原属性位）
    __invlpg(窗口 VA)
    返回 窗口VA + offset
unmap():
    恢复原 PTE
    __invlpg(窗口 VA)
    释放忙标志
```

三条设计要点，每一条都对应一种具体的坏结果：

* **忙标志用 Interlocked 且抢不到就返回失败，不自旋。** 自旋就把上面否掉
  `KeAcquireSpinLock` 的理由又请回来了。窗口是每 vCPU 独占的，真正的竞争只来自
  同一个退出里的嵌套调用 —— 那是设计错误，应该当场暴露而不是等。
* **每次 map 都回读叶 PTE 并比对背板 PFN。** Windows 有可能在我们背后改过它。
  不比对的后果是我们把一个**不属于我们的** PTE 改指向别处，破坏面无法预测且
  不会立刻显形。
* **跨页一律拒绝，不做自动分段。** 一次映射只覆盖一页是这个原语的契约；
  要读跨页结构由调用方分两次，因为只有调用方知道两次之间能不能被打断。

### D0 判据

* 窗口准备失败时**不得上线**：`Prepared` 为假则所有 map 返回 NotPrepared。
* 读一个**已知内容**的客户物理页（例如我们自己分配、写入特征值的页），
  经窗口读回必须逐字节相同。
* 窗口 unmap 之后，背板 VA 读到的必须是背板页原本的内容 —— 证明 PTE 真的复原了。
* **多核并发**：两个核同时经各自窗口读不同物理页，互不串扰。

## D1：vmcs12 存储扩容

现在 `KSW_HVM_VMCS12_FIELD_CAPACITY` 是 **64**，而真实 vmcs12 有一百多个字段。
64 槽在 D2 之前必须提上去，否则 L1 写到一半就开始收到
"unsupported component"，而它多半不会把这当成致命错误 —— 它会带着一份**残缺的
控制状态**继续走到 VMLAUNCH。

扩容本身不难，要定的是**存储形态**：继续用线性扫描的稀疏缓存，还是改成按字段
编码索引的固定布局。倾向后者：编码的 index 段（bits 9:1）本来就是稠密的，
固定布局让 VMREAD/VMWRITE 变成 O(1)，也省掉"缓存满"这个纯属我们自己的失败模式。

## D2：vmcs02 合并

把 L1 可见的 vmcs12 与我们自己的宿主状态合成一份**真实硬件 VMCS**。

三类字段三种规则：

* **宿主状态字段**：永远是**我们的**。L2 退出必须回到我们手上，不能回到 L1。
* **客户状态字段**：基本照抄 vmcs12 —— 那是 L1 想让 L2 看到的状态。
* **控制字段**：`我们必须有的` ∪ `L1 要求的`，再按**我们自己的能力 MSR** 夹一遍。

第三条是整件事的关键，也是**满足"L1 模式下也要支持"的那条路**：

> MTF 对 L1 可见与否，是 L0 的策略选择，不是硬件属性。

kHypervisor 就是靠"把 vmcs12 的控制位 OR 进 vmcs02"实现的这一点
（`vmcs.cpp:1172-1173`、`vmm.cpp:729/1031/1056`）。顺带一条**不要拿来当证据**的
东西：它的 `InitVmxExtensionMask`（`vmx_common.cpp:346`）故意漏掉 MTF，看起来像是
"用能力位图控制"，但那段是**死代码** —— `g_vmx_extensions_bitmask` 全仓只在
`IsEptptrValid` 里被查，而那个函数从未被调用，位图恒为 0。结论成立，但支撑它的是
控制位 OR 那条路。

所以：**即使我们自己跑在没有 MTF 的 L0 底下，也仍然可以选择不给 L2 提供 MTF，
而不是整个嵌套功能塌掉。** 能力要按"我们实际拿到的"如实上报给 L1，不能照抄硬件。

### D2 判据

* 合并后的每一个控制字段都必须落在我们能力 MSR 的 allowed-0 / allowed-1 区间内 ——
  **在 VMLAUNCH 之前自检**，而不是等硬件报 VM-entry 失败。
* 宿主状态字段逐条回读，确认没有一项来自 vmcs12。
* L1 请求了我们没有的能力时，必须是**明确拒绝**（VMfailValid + 正确错误号），
  不能静默降级。

## D3：影子 EPT（EPT01 ∘ EPT12）

L1 给 L2 装的 EPT（EPT12）把 **L2 物理**映射到 **L1 物理**；我们的 EPT（EPT01）
把 **L1 物理**映射到**真实物理**。硬件只认一层，所以要合成一张
**L2 物理 → 真实物理** 的表。

### 按需填充，不预先全建

在 EPT violation 上**逐页合成**：走一遍 EPT12 得到 L1 物理，再走 EPT01 得到真实
物理，把结果写进影子表那一项，然后 resume。

选它而不是"进入 L2 前整张建好"，有三个理由：

1. **不需要 MTF。** 填充完直接 resume 重执行那条指令，不需要单步。这是
   "L1 模式也要支持"的硬要求。
2. L2 的地址空间可以很大而实际用到的很少，全建是纯浪费。
3. kHypervisor 走的是在 VM entry 仿真时构建（`vmx.cpp:1276-1285`
   `EptpBuildNestedEpt`），而它的嵌套 EPT 按 README 自陈只在 Windows 7 上验过。

### 失效

L1 发 INVEPT 时必须真的丢弃对应的影子映射。**这里有一条自己踩过的教训**：

> 叶子写对了却完全不生效、自检还全绿 —— 因为失效发的是"当前装载的那个 EPTP"，
> 而不是"真正要装载的那个"。

影子 EPT 的失效必须指名**影子那套层次**，并且要覆盖所有 vCPU 上的对应缓存。
现阶段宁可粗暴（整套丢弃重建）也不要精细但不确定 —— 精细化要等有判据能证明它。

### 现在就要说清楚的两条

* **A/D 位**：EPT12 里的 accessed/dirty 位是 L1 的观测面。合成时硬件只会更新影子表
  的 A/D，L1 看不见。要么把 A/D 传播回 EPT12，要么**如实告诉 L1 我们不支持
  EPT A/D**。后者简单且诚实，先走后者。
* **本版本拒绝什么**：EPT 违规的 qualification 里有三组位我们至今没读
  （bit 8 caused-by-translation、bits 3/4/5 表项当时的 R/W/X、bit 12 NMI unblocking）。
  影子 EPT 的违规处理**必须**读 bit 8：它区分"取指/取数碰到这一页"与
  "客户页表遍历本身碰到这一页"，两者的正确响应不同。

### D3 判据

* L2 里写一个已知特征值，从 L1 侧按 L1 物理地址读回来必须一致 ——
  证明两层翻译真的串起来了。
* L1 改 EPT12 某一项并 INVEPT 之后，L2 对那一页的访问必须走到新映射，
  **不能还看到旧的**。
* **对照**：另一个不相干的进程/地址空间不受影响。影子 EPT 装在客户物理页上，
  作用域错了不会让任何测试变红 —— 这条判据必须常备。

## D4：退出反射

L2 退出时先落到**我们**手上。要决定：这次退出归我们处理，还是交给 L1。

判据是**所有权**：这一项退出是因为**我们**装的控制位才发生的，还是因为
**L1** 装的控制位才发生的。

* 只有我们要求的（比如我们自己的 EPT 违规、我们的 MSR 位图命中）→ 我们处理，
  L1 完全看不见。
* 只有 L1 要求的 → 把退出信息写回 vmcs12，切回 L1 的状态，让 L1 以为是它自己
  收到的退出。
* **两边都要的** → 我们先处理，再决定要不要转交。这一类最容易出错，
  必须逐项列出来而不是写一条通则。

I/O 位图、MSR 位图、异常位图这三类都要按 L1 的位图查，而位图页在客户物理上 ——
又回到 D0。

### D4 判据

* L1 装一个只有它关心的退出（例如某条 CPUID 叶），L2 触发后 L1 必须收到，
  且 vmcs12 里的退出原因/qualification 与硬件语义一致。
* 只有我们关心的退出，L1 的退出计数**必须一个不涨**。
* L2 连续跑一段时间不掉出去（soak），且期间宿主自身的常驻不受影响。

## 明确不做的（本版本）

* **虚拟 APIC / posted interrupt 的嵌套**。这是独立的一大块，不在这一轮。
* **eVMCS 的嵌套透传**。我们自己在 Hyper-V 底下用的是部分 eVMCS，
  再往下透传一层不在这一轮。
* **EPT A/D 位传播给 L1**（见 D3，先如实报不支持）。
* **五级分页下的 L2**。窗口的页表遍历会兼容五级，但 L2 本身只按四级验收。

这些都属于"本版本拒绝 + 出路已知"，不是"架构上不可能"。

---

## 风险与需要知情的一处

D0 的窗口意味着**驱动会改写内核页表项** —— 只改我们自己分配的那一页的 PTE，
但性质上比之前任何一步都重。三条护栏在上面已经写明（初始化回读校验、每次 map
比对背板 PFN、准备失败就不上线），此外：

* 窗口的背板页用 `MmAllocateContiguousMemory` 分配并**长期持有**，
  不在退出路径上做任何分配。
* 卸载路径必须先复原叶 PTE 再释放背板页，顺序反了会留下一个指向已释放物理页的
  内核映射。
