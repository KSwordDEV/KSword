# KSword 测试机操作手册

一份合并的操作顺序。前面的排查里步骤散在几十条消息里，这里按**场景**收拢，
每个场景从头到尾自足，不需要往回翻。

所有命令都在**管理员 PowerShell**、仓库根目录下执行。

---

## 场景 A · 日常验收（不进 VMX，最安全）

```powershell
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -OfflineOnly
```

只跑离线断言套件 + 编译 guest 工具。不碰虚拟机。判定 `PARTIAL` 是正常的
（在机段记 `NOT_RUN`，既不算通过也不算失败）。

---

## 场景 B · 在机验证（标准循环）

### B1. 确认虚拟机可用

```powershell
.\scripts\Get-KswordVmTriage.ps1
```

它会区分三种"看起来一样"的状态：`Paused-Critical`（宿主磁盘满，**不是崩溃**）、
真挂死、被调试器冻住。

### B2. 磁盘不够就先清检查点

每个检查点约 8 GiB，几轮就把系统盘吃光，表现是
`Checkpoint operation failed ... 磁盘空间不足 (0x80070070)`。

```powershell
.\scripts\Clear-KswordVmCheckpoints.ps1
```

看清单无误后加 `-Confirm` 真删。`clean-install` 永不删除。

### B3. 部署驱动

```powershell
.\scripts\Deploy-KswordDriverToVm.ps1
```

**每次重启 guest 之后都要重跑** —— 驱动服务是 `start= demand`，不会自动加载。

脚本会先在宿主验签名（未签名直接中止），再**先卸载旧服务再拷贝**
（已加载的映像被内核持有，顺序反了会撞文件占用）。

### B4. 分级推进

```powershell
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -Stage safe
```

`-Stage` 取值与含义：

| 值 | 做什么 | 风险 |
|---|---|---|
| `status` | 只读查询 | 无 |
| `safe`（默认） | 必要的 reset-fault/prepare + `self-test` | 低，VMXON/VMXOFF 即退 |
| `launch-guest` | 再加一次性 VMLAUNCH 受控 guest | 低，单处理器、`__try` 内、4 KiB guest 栈 |
| `resident` | 全处理器常驻 | **高，当前会挂死 guest** |
| `soak` / `full` | 常驻 + 浸泡 / 再加清理 | 同上 |

脚本自己看状态决定动作：带 `FAULTED` 先 `reset-fault`；`RESOURCES_READY` 已置位
就跳过 `prepare`（重复 prepare 会再把状态打成 `FAULTED`）。

## 场景 C · 改了驱动之后

```powershell
& "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\MSBuild\Current\Bin\MSBuild.exe" `
    KswordARKDriver\KswordARKDriver.vcxproj /t:Build /p:Configuration=Release /p:Platform=x64 `
    /p:KswordArkSkipAutoVariantSign=true /v:minimal /nologo
```

```powershell
.\scripts\Sign-KswordArkDriverTest.ps1 -DriverPath 'Ksword5.1\x64\Release\KswordARK.sys' -SkipMachineTrust
```

**签名这一步不能省。** `KswordArkSkipAutoVariantSign=true` 会把测试签名一起关掉，
而 testsigning on **不放行未签名驱动** —— 缺签名就是 `sc start` 577。
脚本末尾 `signtool verify /pa` 退出码 1 是**预期的**（宿主不信任自签根），
只要看到 `Successfully signed` 即可；`Get-AuthenticodeSignature` 报 `UnknownError`
表示"签了但本机不信任链"，与 `NotSigned` 是两回事。

然后回到 B3。

## 场景 D · 带内核调试器跑（要看代码走到哪一步）

**顺序不能变。** 挂死之后 NMI 与 Ctrl+C 都打不进去，断点必须提前下好。

### D1. 一次性启用（会重启 guest）

```powershell
.\scripts\Enable-KswordVmKernelDebug.ps1
```

撤回用 `-Disable`。

### D2. 先开 kd（专用窗口，会接管控制台）

```powershell
.\scripts\Start-KswordVmDebugger.ps1
```

它会自动加载符号、下 7 个延迟断点、`g` 放行。
`bl` 显示 `u`（未解析）在驱动加载前是**正常的**。

### D3. guest 已经在跑就重启它（另一个窗口）

```powershell
Restart-VM -Name 'KSword-HVM-Target' -Force
```

**命名管道只在虚拟机初始化 COM 口那一刻握手** —— guest 跑起来之后接不进去，
kd 会一直停在 `no_debuggee`。

### D4. 部署驱动，kd 会断一次

```powershell
.\scripts\Deploy-KswordDriverToVm.ps1
```

在 kd 里：

```
.reload /f KswordARK.sys
bl
g
```

`bl` 这时**不该再有 `u`**。还有就是符号没对上，停下来别往下跑。

### D5. 跑常驻

```powershell
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -Stage resident
```

kd 会依次打印 `[1] ResidentStart` → `[2] StartCurrent` →
`[4] AsmLaunchResident` → `[3] ConfigureVmcs`（在这里**停住**）。然后：

```
gu          ← 回来 = ConfigureVmcs 没死在里面；卡住 = 死在里面
r eax       ← 0 = 配置成功
u . L18     ← 找到 vmlaunch
```

**到了 `vmlaunch` 用 `g` 不要用 `p`。** `p` 会先摘掉所有软件断点，
VM entry 成功时 guest 侧断点不会命中，读数就废了。

## 场景 E · 挂死取证（宿主飞行记录仪）

挂死之后 guest 里读不到任何东西（驱动无日志、无注册表写，每处理器行在非分页池）。
证据只能在挂死**同时**送到宿主。

```powershell
.\scripts\Invoke-KswordHostFlightRecorder.ps1
```

它自己会：前置自愈 → 基线 20 秒 → **标定**（发一次 `launch-test-guest`，
确认计数器真的会动）→ 观测 90 秒 → 打印涨幅排名。

**标定不过时它会明说"读数只能当参考"** —— 那时候不要下结论。

判读：

| 读数 | 含义 |
|---|---|
| `Nested VM Entries/sec` 持续非零 | VM entry 一直成功，guest 零前进 |
| 恒为 0 + 拦截≈0 + guest%≈100 | CPU 在 L1 的 VMX root 里静默自旋 |
| 恒为 0 + hypervisor% 高 | 卡在 L0 那一侧 |

涨幅排名里领跑的那个计数器就是循环体在干的事。

## 场景 F · 恢复挂死的虚拟机

```powershell
Checkpoint-VM -Name 'KSword-HVM-Target' -SnapshotName 'hung-0000'   # 可选，留现场
```

```powershell
Stop-VM -Name 'KSword-HVM-Target' -TurnOff -Force
```

```powershell
Start-VM -Name 'KSword-HVM-Target'
```

`-TurnOff` 是拔电源，不需要 guest 配合。**"关机"走集成服务，挂死时必然失败**
（`0x800710DF` 设备未就绪），那不是虚拟机坏了，是关机方式选错了。

起来之后回 B3 重新部署驱动。

改 vCPU 数做二分用：

```powershell
.\scripts\Invoke-KswordVmCpuBisect.ps1 -Count 1     # 恢复用 -Count 4
```

## 场景 G · 验证 hypercall 透传（当前这一轮）

### 背景：为什么之前一直挂

常驻模式对**任何不带私有签名的 VMCALL 注 #UD**，而
**Windows-on-Hyper-V 的 hypercall 就是 vmcall**。转储实证：

```
bugcheck 0x1E  P1=0xC000001D (STATUS_ILLEGAL_INSTRUCTION)
FAILURE_BUCKET_ID: 0x1E_C000001D_BAD_IP_winhv!WinHvpFastHypercall
storvsc -> vmbus!BusChSendInterrupt -> winhv!WinHvSignalEvent
       -> winhv!WinHvpFastHypercall -> hypercall page -> KiInvalidOpcodeFault
```

也就是说 **VM entry 一直是成功的、退出派发器一直在跑** ——
"嵌套不支持 VMLAUNCH"那个框架是错的。同理，位图外的合成 MSR
（`0x40000000-0x400000FF`，每次中断结束都要写 `HV_X64_MSR_EOI`）被注 #GP。

之前**没有转储**也是同一个原因：写转储要走
`storvsc -> vmbus -> hypercall`，又被自己的 #UD 打断，bugcheck 永远完不成。

### 已改的两处

* VMCALL：L0 存在时转发给 L0（`KswordARKHvmAsmForwardHypercall`），否则维持 #UD
* 位图外 MSR：落在保留区 `0x40000000-0x4FFFFFFF` 且 L0 存在时直接透传

bit24 无条件 I/O 退出的诊断**已关掉** —— 真因已知，留着它只会让第一条端口
I/O 就退虚拟化。

### 第一次在机结果（2026-09-05 23:24）

透传**成立了**：`RESIDENT_ACTIVE | RESIDENT_NESTED`、
`residentProcessorCount=1`、`residentImplementation=ACTIVE`、guest 全程存活、
没有蓝屏。多轮排查的那个 #UD 自杀路径被堵住了。

**但只活了 3 次退出。** `stop` 的响应给出 `vmExitCount=3`、
`lastExitReason=12`（**HLT**）。原因是 L0 把 HLT-exiting 报成 must-be-one
（`AdjustControls = (Desired | mustBeOne) & mayBeOne`，驱动清不掉），
而 HLT 当时在 fail-closed 列表里 → 空闲循环第一次 HLT 就退虚拟化了。

已修：`KswordARKHvmExitHandleHlt` 推进 RIP 后写 `GUEST_ACTIVITY_STATE=1`
（架构 halt 态），guest 正常空闲、下一个中断唤醒。

### 结果（2026-09-05 23:35，`-Stage soak`）

```
soakElapsedMilliseconds          2000
soakUnexpectedDevirtualizations  0        ← 判据
vmExitCount                      14079    ≈ 7000 次/秒
lastExitReason                   18 (VMCALL)   instrLen=3
判定 OK   总判定 PASS   guest 全程存活
```

**常驻在嵌套虚拟化下持续驻留成功。** `reason=18 / instrLen=3` 就是被转发的
Hyper-V hypercall，它成了主要退出来源。

`lastVmInstructionError=12` 是**预期残留不是故障**：`VM_INSTRUCTION_ERROR`
(0x4400) 是只读粘滞字段，只记该 VMCS 上最后一次失败的 VMX 指令，而遥测每次
退出都无条件 publish 一遍。12 = "VMWRITE 到只读/不支持的组件"，来源是故意
改成尽力而为的 `__vmx_vmwrite(KSW_VMCS_GUEST_SMBASE, 0U)`（L0 不实现 0x4828）。

### 跑法

不要开内核调试器（`Enable-KswordVmKernelDebug.ps1 -Disable`），然后:

```powershell
.\scripts\Deploy-KswordDriverToVm.ps1
```

```powershell
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -Stage soak
```

**用 `soak` 不用 `resident`。** `resident` 的响应是 `KeIpiGenericCall` 刚返回
那一瞬间的快照 —— 它已经骗过我们一次了（全绿，而常驻毫秒级就没了）。

### 判读

| 读数 | 结论 |
|---|---|
| soak 跑完、`soakUnexpectedDevirtualizations=0`、guest 还活着 | **成功**，常驻在嵌套下持续驻留 |
| `vmExitCount` 持续增长、`lastExitReason` 多为 18(VMCALL)/12(HLT) | 正常 —— hypercall 与空闲是主要退出来源 |
| `soakUnexpectedDevirtualizations` 非零 | 又有退出原因掉进 fail-closed。**看 `lastExitReason`，它会直接点名** |
| 又蓝屏 | **一定有转储**（hypercall 通了，storvsc 就能写盘）。跑场景 H |

判成功**只看 `soakUnexpectedDevirtualizations` 与 guest 存活**。
`GUEST_LAUNCHED`(0x40) 被 `LAUNCH_TEST_GUEST` 污染；
`RESIDENT_ACTIVE`(0x100) 只证明"那一瞬间起来了"，两个都不够。

## 场景 H · 蓝屏取证

```powershell
.\scripts\Get-KswordVmBugcheck.ps1
```

一次走完：没在跑就开机 → 等 PS Direct → 读崩溃转储配置 → 读事件日志
（WER 1001 与 Kernel-Power 41，后者 XML 里直接带 `BugcheckCode` 和四个参数）
→ 把最新 minidump 拷回 `docs/next/logs/` → 直接跑 `!analyze -v` 并落盘。

PS Direct 起不来 = guest 还停在蓝屏画面上（`AutoReboot` 关着），
脚本会明说并让你去 vmconnect 看屏幕。
转储写不出来也会**明确报告是哪一种**（`CrashDumpEnabled=0` 还是页面文件太小），
不会含糊成"没找到转储"。

**蓝屏比挂死好。** 挂死什么都不留，蓝屏留下 bugcheck 码 + 参数 + 转储，
而且这条通道**不经过串口**。

## 常见现象对照表

| 现象 | 成因 | 处置 |
|---|---|---|
| `sc start` 577 | .sys 未签名 | 场景 C 补签 |
| `CONFIRMATION_REQUIRED` | 缺 `FLAG_FORCE` 位，**与安全策略无关** | 用 `hvm_ctl` 而不是手搓 IOCTL |
| `ALREADY_PREPARED` 后状态变 `FAULTED` | 重复 prepare 返回 NT_ERROR | 先 `status` 再决定；脚本已自动处理 |
| `LIFECYCLE_GUARD_FAILED` | unload 守卫捕获值过期 | 已修（延迟到武装时刻捕获） |
| `0x80070070` 检查点失败 | 宿主磁盘满 | 场景 B2 |
| `0x800710DF` 关机失败 | guest 挂死，集成服务不响应 | 场景 F 的 `-TurnOff` |
| kd `no_debuggee` | guest 已在跑，握手窗口过了 | 场景 D3 重启虚拟机 |
| kd 连上但无 `kd>` | 缺 `-b`，没断入 | 脚本已加；手动可按 Ctrl+C |
| 实验"跑完了"但什么都没测到 | 前置条件没满足，命令在门口就被拒 | 看响应里 `preparedProcessorCount` / `eptPointer` 是不是 0 |

## 别用的判据

这几个都实测给出过假阳性，详见 `docs/next/自动化测试.md`：

* `GUEST_LAUNCHED` (0x40) —— 被 `LAUNCH_TEST_GUEST` 置上且不被清，改用 `RESIDENT_ACTIVE` (0x100)
* `lastVmInstructionError == 0` —— 有三个来源
* 没有 `RESIDENT_STARTING` —— 它在三条出口全被清
* `failedProcessorCount` —— 是 `总数 − 通过数`，不是失败计数
* `SELF_TEST` 通过 —— 只证明能 VMXON/VMXOFF，对 VMCS/EPTP/VMLAUNCH 零证据
