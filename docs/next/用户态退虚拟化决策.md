# 用户态触发的退虚拟化：为什么不修

**日期**：2026-09-06　**状态**：已决定不做，本文记录理由与复议条件。

---

## 一句话

严格 EPT 规则命中时，退虚拟化路径**假定 guest 在内核态**，用户态触发会
double fault。修它需要构造跨特权级返回帧（`iretq`）—— **但不修反而更好**，
因为那条路径本身就是 fail-open 的，修好只会把一次响亮的蓝屏换成一次
静默放行。

---

## 一、现象与实证

`hvm_ctl probe-xonly` 早期版本从**用户态**读一页被 deny-READ 的内存：

* guest bugcheck **0x7F (0x8)** = `UNEXPECTED_KERNEL_MODE_TRAP` / double fault
  （靶机事件日志 Kernel-Power 41 实证，2026-09-06 04:47 UTC）

原因（代码事实）：`hvm_entry.asm` 的 `KswordARKHvmResidentDevirtualize`
是**同特权级返回** ——

```
mov rsp, <DevirtualizeRsp>   ; 切到 guest 栈
push RIP / RFLAGS / GPRs
... 弹回去
```

已验证过的两个用例都是 ring 0（STOP 私有 hypercall 从 IPI worker 发出、
一次性受控 guest）。用户态退出时 `DevirtualizeRsp`/`Rip` 是 ring-3 的值，
带着它们在 ring 0 上返回必然出事。

---

## 二、为什么决定不修

### 2.1 承重理由：这条路径本身是 fail-**open**

所有 fail-closed 站点传的 `InstructionLength` 都是 `0UL`
（`hvm_exit.c` 的四个 `DeactivateCurrent(Context, 0UL, TRUE)`）
⇒ RIP 不推进 ⇒ VMXOFF ⇒ **那条违规指令原地重执行，而本核已经没有 EPT**
⇒ **必然成功**。

协议注释原话（`shared/driver/KswordArkHvmIoctl.h` 的 `deniedAccess`）：

> This is a tripwire mask, not a durable access-control guarantee: a strict
> hit records and **devirtualizes** without injecting an exception, so the
> same native access **may retry and succeed after VMXOFF**.

实测印证：`probe-xonly` 的读数是 `residentAfterRead=0` **且**
`observedByte=0xA5` —— 常驻掉了，**而那次读成功了**。

所以严格规则的真实语义是：**绊线 → 拆掉自己的保护 → 放行**，
用户态触发时再顺带打死机器。

`iretq` 只修最后半句。剩下的半句原样保留，而且会把一个**响亮的失败**
换成一个**静默 fail-open 且看起来全绿**的机制。对一个反 rootkit 产品，
后者更坏。

### 2.2 覆盖面很小

五个 `DeactivateCurrent` 调用点里，只有两个既可能在 CPL3、又确实必须离开
VMX（VMRESUME 失败、未知退出原因）。而遥测读失败那条 `iretq` **根本救不了**
—— 它正是因为 VMREAD 失败才进来的，而构造 `iretq` 帧需要**更多** VMREAD。

### 2.3 两个未标定的前提能直接否决方案

* **CR4.CET**：若为 1，ring-3 的 `IRET` 有自己的影子栈协议
  （`IA32_U_CET` / `IA32_PL3_SSP` 都不是 VMCS 字段，整条路径从没保存过）
  ⇒ ring-3 返回不成立。
* **KVA shadow**（`nt!KiKvaShadow`）：若非零，用户态退出时 GUEST_CR3 是
  **用户影子 PML4**，而 `hvm_resident.c` 的 `__writecr3(GuestCr3)`
  在 VMXOFF 之后立刻执行 —— 那会把内核从地址空间里抹掉 ⇒ 三重故障，
  且症状与 §1 的 0x7F 极像，**会被误判成同一个 bug**。

第二条是**本轮新增的 `__writecr3` 带来的**，今晚没暴露只因为两次退虚拟化
都发生在内核态。见 §4。

---

## 三、对 CLOAK/HOOK 的影响：**没有**

规则与视图是两套机制：

| | 规则（tripwire） | 视图（CLOAK/HOOK） |
|---|---|---|
| 命中做什么 | 记录 → 退虚拟化 → 放行 | 翻叶重定向到影子页 |
| 走不走退虚拟化 | 走 | **不走**（它不"拒绝"） |
| 受本文影响 | 是 | **否** |

⇒ 分离视图的接线**不被本决定阻塞**。

---

## 四、由此产生的一条待办（未修）

`hvm_resident.c` 的 `__writecr3(Context->GuestCr3)` 在用户态退出 + KVA shadow
同时成立时会三重故障。今天不可达（用户态退出在到这一步之前就 double fault
了），但一旦 §2 的决定被复议、或退虚拟化路径以别的方式支持了用户态，
**这条会立刻变成活雷**。

最小防御：在写 CR3 之前检查 CPL，非 0 就不写（保持 HOST_CR3 直到能安全切换）。
**但那本身需要先确认 KVA shadow 的状态** —— 见探针。

---

## 五、复议条件

出现下列任一情况时重开此议题：

1. 探针确认 **CR4.CET = 0 且 KVA shadow = 0** —— 两个否决理由都消失；
2. 严格规则的处置从"退虚拟化放行"改成真正的拒绝（例如骑到视图上，
   读到全零影子页而不是读到真值）—— §2.1 的承重理由随之失效；
3. 实测发现用户态触发的退虚拟化在真实负载里**频繁发生**
   （需要 §六 的遥测先落地）。

---

## 六、先决条件：把判据补齐

在复议之前，下面两件事必须先做，否则任何结论都没有事实基础：

1. **只读平台探针**（零 VMX）：标定 `CR4.CET` / `IA32_S_CET` / `IA32_U_CET` /
   KVA shadow / `IA32_KERNEL_GS_BASE`。这三个量各自能独立否决方案，
   而仓库里从没记录过实测值。
2. **退出遥测补 CPL 与选择子**：整条退虚拟化路径今天只读四个 VMCS 字段
   （RSP/RIP/RFLAGS/CR3），选择子和 FS/GS base 一个都没读。
   没有它就答不出"用户态触发的退虚拟化到底发生几次"。
