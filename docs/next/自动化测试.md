# KSword 自动化测试

一条命令跑完：离线断言套件 → guest 工具编译 → 嵌套虚拟机里的真实驱动验证，
产出机器可读 JSON 与可直接贴进验收记录的 Markdown。

```powershell
.\scripts\Invoke-KswordAutomatedAcceptance.ps1              # 全套（到 self-test 为止）
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -OfflineOnly # 没有虚拟机时
.\scripts\Invoke-KswordAutomatedAcceptance.ps1 -Stage soak -SoakMs 5000
```

产物落在 `docs/next/logs/`：

| 文件 | 内容 |
|---|---|
| `acceptance-autotest-<时间戳>.json` | 全量结构化记录 |
| `acceptance-autotest-<时间戳>.md` | 汇总表 |
| `hvm-autotest-<时间戳>.json` | 在机段逐步骤记录（含每步的状态位展开） |
| `autotest-build-<时间戳>.txt` / `autotest-run-<时间戳>.txt` | 原始构建与运行输出 |

## 判定语义

四个值刻意分开，**不要合并**：

| 值 | 含义 |
|---|---|
| `PASS` | 实跑通过，有执行证据 |
| `FAIL` | 代码/逻辑失败 |
| `BLOCKED` | 缺硬件能力、权限、签名环境或真实样本 —— 不是代码的问题，但**也不是通过** |
| `NOT_RUN` | 这一段本次没跑 |

总判定取最坏：任一段 FAIL 则 FAIL；否则有 BLOCKED 则 BLOCKED；否则有 NOT_RUN 则
PARTIAL；全 PASS 才是 PASS。退出码只在 FAIL 时为 1 —— BLOCKED 不该让 CI 变红，
但它同样不能被读成通过。

在机段的状态码分流写在 `Invoke-KswordHvmControl.ps1` 里：
`UNSUPPORTED_CPU` / `FIRMWARE_DISABLED` / `HYPERVISOR_CONFLICT` /
`NESTED_UNSUPPORTED` / `EVMCS_UNSUPPORTED` / `PARTIAL_IMPLEMENTATION` 记 BLOCKED，
其余非零状态记 FAIL。

### 为什么还要一张清单

只看退出码抓不到**整个套件没被链接进来**。`HvmEptSwitchTests.cpp` 就发生过：
467 条断言写完了，工程文件里却没有这个 `ClCompile`，测试进程照样退出 0、照样
打印「全部通过」，那 467 条一次都没跑过。日志上完全看不出区别。

所以 `scripts/ksword-expected-suites.json` 登记了应当出现的套件与各自的断言条数
下限，脚本逐条核验：

* 清单里的套件没出现 → **FAIL**（不是「少了一行日志」）
* 出现了但断言数低于下限 → **FAIL**（有人把断言删了）
* 出现了清单外的新套件 → 只提醒，因为新增是好事，但要有人更新清单

这条判据本身做过负向测试：往清单里加一个不存在的套件，脚本判 FAIL、退出码 1。

### 新增一个套件要改的地方

1. `KswordARKLightTests.vcxproj` 与 `.filters` 加 `ClCompile`
2. `TestSupport.h` 末尾加 `int RunXxxTests();`
3. `KswordARKLightTests.cpp` 的 `Run*` 链加 `failures += RunXxxTests();`
4. `scripts/ksword-expected-suites.json` 加一行

套件名**必须是纯 ASCII**。非 ASCII 的套件名会在默认 locale 下让 MSVC 给
`wcout`/`wcerr` 置 badbit，并吞掉此后**所有**输出 —— 包括后面套件的失败标签和
最终汇总。主入口已经切到 `.UTF-8` locale 兜底，但别去试它的极限。

## 第 2 段：guest 工具

`scripts/Build-KswordHvmTools.ps1` 编译 `hvm_probe.exe` 与 `hvm_ctl.exe`。

两个都用 **`/MT` 静态链接 CRT**。这不是风格问题：全新安装的 Windows 没有 VC++
可再发行组件，动态链接的 exe 在 guest 里根本起不来 —— 退出码 `0xC0000135`
(`STATUS_DLL_NOT_FOUND`)、stdout/stderr 全空，看上去像「命令没有输出」，其实是
进程没跑起来。静态链接省掉整套 DLL 投送。

### hvm_ctl

```
hvm_ctl.exe [--json] <命令> [参数]

  status           只读查询，不改状态
  prepare          分配每处理器资源，不进 VMX
  self-test        逐处理器 VMXON/VMXOFF
  resident         全处理器常驻 VMM + EPT
  soak <ms>        有界常驻
  stop             停止常驻
  teardown         释放全部可逆资源
  reset-fault      清 FAULTED / ROLLBACK_REQUIRED
  validate-nested  嵌套 VMX 与 eVMCS 的部分能力校验
```

退出码：`0` = 协议 status OK，`2` = 协议 status 非 OK，`1` = 传输层失败。

它**直接 include** `shared/driver/KswordArkHvmIoctl.h`，不再手抄协议结构。上一版
手抄的代价见下一节。

## 第 3 段：在机验证

`scripts/Invoke-KswordHvmControl.ps1` 推进生命周期。与「按顺序发一串命令」不同，
它**先读状态再决定动作**：

```
status
  ├─ 带 FAULTED / ROLLBACK_REQUIRED ─→ reset-fault
  ├─ 没有 RESOURCES_READY          ─→ prepare
  └─ 已有 RESOURCES_READY          ─→ 跳过 prepare
checkpoint ─→ self-test ─→ 存活确认
（resident / soak / stop / teardown 按 -Stage 追加，每个风险级别各打一次检查点）
```

`-Stage` 取值：`safe`（默认，到 self-test 为止）、`prepare`、`self-test`、
`resident`、`soak`、`full`、以及 `status` / `stop` / `teardown` / `reset-fault`
四个单命令模式。

### 三个踩过的坑

**1. `CONFIRMATION_REQUIRED` 与安全策略无关。**

`hvm_runtime.c` 对 `SELF_TEST` / `LAUNCH_TEST_GUEST` / `START_RESIDENT` /
`VALIDATE_NESTED` / `SOAK` / `RESET_FAULT` 要求 `KSWORD_ARK_HVM_CONTROL_FLAG_FORCE`，
缺了就返回 `CONFIRMATION_REQUIRED`。这个状态码**看上去**像「安全策略没放行」，
把排查引向了完全无关的方向；实测安全策略这一侧默认就是 `0x3fbff`
（`ACTIVE | ADVANCED_MODE | ALLOW_KERNEL_PATCH` 全在内），`query-policy` 里
`lastDecision=1 allowed=1 denied=0` 明确写着它放行了。

每条命令接受的标志集合必须与 `hvm_runtime.c` 的 `allowedFlags` switch **逐位一致**：
多一位是 `INVALID_REQUEST`（`flags & ~allowedFlags`），少 `FORCE` 是
`CONFIRMATION_REQUIRED`。两种拒绝都发生在真正做事之前，从外面看不出区别。
`TEARDOWN` 与 `STOP_RESIDENT` 尤其要注意：它们**不接受** `ALLOW_NESTED`，
顺手带上就被判 `INVALID_REQUEST`。这张表现在钉死在 `hvm_ctl.c` 的 `g_Verbs` 里。

**2. 重复 `prepare` 会把状态打成 `FAULTED`。**

已就绪时 `KswordARKHvmPrepareLocked` 返回 `STATUS_ALREADY_REGISTERED`，那是
`NT_ERROR`，会落进 `hvm_runtime.c` 的 `StateFlags |= FAULTED` 分支。而 `FAULTED`
会让后面的 `START_RESIDENT` 被 `hvm_resident.c` 判 `STATUS_INVALID_DEVICE_STATE`
直接拒掉。也就是说「多跑一次 prepare」这种看上去幂等的操作会把后续流程堵死，
必须 `reset-fault` 才能走出来。脚本因此先 `status` 再决定要不要 prepare。

**3. `failedProcessorCount` 不是失败计数。**

`hvm_runtime.c` 现算的是 `ProcessorCount - SelfTestPassedProcessorCount`。
PREPARE 之后 `selfTestPassed` 必然是 0，于是这个字段必然等于处理器总数 —— 4 核机
上看到 `prepared=4 failed=4` 会以为四个核都挂了，实际只是「还没有处理器通过自检」。
`hvm_ctl` 现在把它印成「未通过自检 = N，注意这不是失败计数」。

### 安全边界

脚本**不会**改宿主机的安全配置、不重启、不启用 Verifier、不往宿主装驱动、
不上传任何数据、不发布远程版本。它唯一有副作用的动作是给虚拟机打检查点和在
guest 内发 IOCTL，两者都在那台一次性隔离测试机内部。

失去响应时脚本会把回滚命令与转储位置写进记录：

```powershell
Restore-VMCheckpoint -VMName 'KSword-HVM-Target' -Name '<检查点名>' -Confirm:$false
# 转储在 guest 的 C:\Windows\MEMORY.DMP（部署脚本已提前开启内核转储）
```

## 在机实测结论（2026-09-05，嵌套 Hyper-V L1）

### VMXON 在嵌套 L1 里可行

`SELF_TEST` 实跑通过：

```
status=0 (OK)   状态位 0x00080007 -> 0x0008011F   代次 4 -> 5
prepared=4  selfTestPassed=4  failed=0
新状态位: INITIALIZED RESOURCES_READY EPT_READY SELF_TESTED SELF_TEST_PASSED
          GUEST_READY EVMCS_PARTIAL
```

**4 个 vCPU 全部完成 VMXON → VMXOFF，虚拟机存活。** 这是整条路线的前提条件，
现在有实测证据了。记录在 `docs/next/logs/hvm-autotest-20260905-154612.json`。

### 能力面：缺的不只是 MTF

`featureFlags = 0x0009803F30FFFFFF` 逐位解码，**缺失**的关键位是：

| 位 | 名字 | 影响 |
|---:|---|---|
| 24 | `MONITOR_TRAP_FLAG` | 现有「写叶 + monitor-trap」后端起不来 |
| 49 | `VM_FUNCTIONS` | guest 侧 VMFUNC 不可用 |
| 50 | `EPTP_SWITCHING` | VMFUNC(0) 切 EPTP 不可用 |
| 46 | `EPT_VIOLATION_VE` | #VE 转换不可用 |

**存在**的关键位：`EPT` / `EPT_WB` / `EPT_4_LEVEL` / `EPT_2MB` / `EPT_AD` /
`INVEPT` / `INVEPT_SINGLE` / `INVEPT_ALL` / `VPID` / `MSR_BITMAP` /
`EXIT_EMULATION` / `VE_INFO_READY` / `EPTP_LIST_READY`。

> `EPTP_LIST_READY` 置位**不等于**可以用 VMFUNC 切 EPTP。它只说明驱动分配了
> EPTP 列表页；真正的门是 `VM_FUNCTIONS` + `EPTP_SWITCHING`，两个都不在。

现有 EPT 后端硬性要求 `INVEPT_SINGLE | MONITOR_TRAP_FLAG`，门在：

* `hvm_ept_view.c:626` → `VIEW_STATUS_MULTIPROCESSOR_UNSAFE`
* `hvm_ept.c:1024` → `return FALSE`
* `hvm_resident.c:1382` → `LocalEptArmed` 保持 false

所以**基于 MTF 的分离视图在嵌套 Hyper-V 下根本起不来**。这不是代码缺陷，是宿主
暴露的能力面缺一位，按判据记 `BLOCKED` 而不是 `FAIL`。

### VMLAUNCH 与退出派发在嵌套下成立

`LAUNCH_TEST_GUEST` 实跑通过（`docs/next/logs/hvm-autotest-20260905-184534.json`）：

```
status=0 (OK)  lastStatus=0x00000000
状态位 0x0008011F -> 0x0008151F   新增 GUEST_EXITED | NESTED_VALIDATED
vmExitCount=1   lastExitReason=18 (VMCALL)
CPU 0 state=0x000000E7
      RESOURCE_READY SELF_TESTED VMXON_SUCCEEDED VMCS_LOADED
      GUEST_LAUNCHED VMEXIT_HANDLED
```

`GUEST_LAUNCHED` 与 `VMEXIT_HANDLED` 两位同时置起、退出原因恰好是 18(VMCALL)，
说明整条链在嵌套 Hyper-V 下**全部成立**：

```
VMCS 构造 → EPTP 装载(L0 为它建影子 EPT) → VMLAUNCH →
guest 执行 VMCALL → VM exit → 派发 → 处理 → 干净退出
```

这一条此前完全没有证据 —— `SELF_TEST` 只做 VMXON/VMXOFF，不写 VMCS、不装 EPTP、
不 VMLAUNCH。**"self-test 4/4 通过"对这一整块是零证据**，两者相隔很远。

> 附带一条：响应里 `vmInstrError = 12`（VMWRITE to read-only/unsupported component）
> 是 `GUEST_SMBASE` 那次尽力而为的写留在 VMCS 0x4400 里的残值 —— 退出路径把它当
> 兜底值读了出来。它**独立印证**了 SMBASE 的诊断（L0 把 0x4828 当作不支持的字段），
> 但作为报告值是误导性的：一次无害的失败会让一次成功的操作看起来带着错误码。

### 全处理器常驻仍然挂死

`START_RESIDENT` 在同一台机器上把 guest 硬挂死：心跳通信中断、PowerShell Direct
无响应、CPU 稳定在宿主的 13%（24 个逻辑处理器 ≈ 3 个核满负荷）、`Uptime` 不归零。

四条合起来指向**多个核在高 IRQL 自旋**：所有核都关着中断转，连时钟看门狗
（`CLOCK_WATCHDOG_TIMEOUT` 0x101）自己都跑不起来，所以**不会有蓝屏、不会有转储**。
典型成因是全处理器 rendezvous 在 IPI_LEVEL 上等一个永远不会到达的同伴。

由此得到的搜索范围：VMCS 构造、VMLAUNCH、退出派发这三块已由 `launch-test-guest`
证明可用，所以问题在 **resident 特有的那部分** —— 全处理器 rendezvous、
"当前执行上下文变成 guest" 的构造、或常驻的 VMRESUME 退出循环。

这类失败**事后读状态是查不出来的**（现场在挂死那一刻就没有出口），需要内核调试器。

### 候选出路：VMM 侧 VMWRITE 切 EPTP

`shared/driver/KswordArkHvmEptSwitch.h` 走的是**第三条路** —— 既不用 MTF、
也不用 VMFUNC：把主值与次值放进 `1 + L` 套内容不同的完整层次，在 EPT violation
的 VM-exit 里由 VMM 对自己 VMCS 的 `EPT_POINTER`（`0x201A`）做一次 VMWRITE
换掉当前处理器走的树，然后 resume。VMWRITE 是任何 VMX 实现都有的，不需要任何
可选能力位。这正是它在这台机器上可能可行的原因。

该后端目前**只有离线算术与状态机验证（467 条断言），尚未接进任何生产 `.c`**，
接线方案正在评审中（换 EPTP 后 INVEPT 的必要性、L1 里的 TLB 失效语义、
SMP 竞态与 fail-closed 汇流都还没有定论）。在拿到结论之前，**不要把
「self-test 通过」读成「HOOK 在嵌套下可用」** —— 那是两件相隔很远的事。
