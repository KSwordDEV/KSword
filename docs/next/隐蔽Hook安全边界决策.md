# 隐蔽 Hook（CLOAK / HOOK 分离视图）算不算安全边界

**日期**：2026-09-06　**决定人**：项目负责人
**结论**：**不算**（选项 A）。按"仅对非对抗性读者有效"实现与宣传。
选项 B（做成真安全边界）写入开发规划，见 §5，**不得在 B 落地前按 B 宣传**。

---

## 一句话

分离视图今天的**每一条**失败路径，结局都不是"拒绝访问"，而是
**hypervisor 自己退场、然后那条访问原样读到真页**。而失败路径可以被
知道页地址的人**用一条指令主动构造**。所以它是隐蔽性特性，不是访问控制。

---

## 一、这个问题在问什么

不是技术选型，是**威胁模型**。CLOAK 要挡住的"读者"是谁：

| | 判成功的标准 |
|---|---|
| **A：不是安全边界** | 常规完整性扫描器、崩溃转储、其他 AV、好奇的软件读到影子页。偶尔失效是功能降级。 |
| **B：是安全边界** | **不存在**一条对手能主动构造的路径让它失效。一次可被主动触发的失效 = 这个边界不存在。 |

安全边界的标准是**存在性**的，不是概率性的。这是两者的根本差别，
也是本文只能二选一、不能"大体上算"的原因。

---

## 二、承重理由：失败路径是 fail-**open**，而且可被主动触发

### 2.1 失败即放行（代码事实）

`hvm_exit.c:860`，视图命中后无法完成时：

```c
handled = KswordARKHvmResidentDeactivateCurrent(Context, 0UL, TRUE);
return handled ? KSW_HVM_EXIT_ACTION_DEVIRTUALIZE : KSW_HVM_EXIT_ACTION_FATAL;
```

`InstructionLength` 传 `0UL` ⇒ RIP 不推进 ⇒ VMXOFF ⇒
**那条访问原地重执行，而本核已经没有 EPT** ⇒ **必然成功，读到真页**。

这与严格 EPT 规则是同一个语义，已在 `用户态退虚拟化决策.md` §2.1 记录并实测
（`probe-xonly`：`residentAfterRead=0` 且 `observedByte=0xA5` —— 常驻掉了，
而那次读**成功了**）。

`EPT切换后端设计.md` §5「层级二」把这条写成了设计的一部分：
*单次违规不可表示 → publish telemetry → `DeactivateCurrent(Faulted=TRUE)` → DEVIRTUALIZE*。
本文补上那份文档没说的那半句：**对安全边界而言，这条降级路径就是拆除路径。**

### 2.2 三条可主动构造的拆除配方

| # | 触发条件 | 代码位置 | 构造方法 |
|---|---|---|---|
| 1 | 重叠翻转（`Transient->Armed` 未还原） | `hvm_ept_view.c:735` | 制造两次交错的违规 |
| 2 | 访问方向与视图不符 | `hvm_ept_view.c:746` | 对 CLOAK 页取指；对 HOOK 页读 |
| 3 | 一条指令同时要求两个叶的次值 | `KswordArkHvmEptSwitch.h:1709`（`REASON_UNREPRESENTABLE`） | 取指落 HOOK 页、读操作数落 CLOAK 页 |

第 3 条最致命：`KswordArkHvmEptSwitch.h:60-63` 自己就写明这种组合
"在任何单套层次里都不成立"。**知道两个页地址的人，一条指令就能让 hypervisor 退场。**

**这三条在两种后端下都成立。**「写叶 + MTF」与「切 EPTP」在这一点上没有差别，
所以**换后端救不了它**——这是本决定与后端选型正交的原因。

### 2.3 顺带澄清一个说小了的说法

内部讨论里一度把代价说成"针对性工具可能**发现**隐藏的 hook"。
发现是轻的那一半。实际是**可被主动拆除**，且拆除之后连隐蔽性一起失去。
按"可能被发现"去权衡会得出错误的结论。

## 三、选 A 意味着什么

### 3.1 代码

**基本不用改**——今天的行为就是 A 的语义。本决定**不阻塞** EPTP 切换后端接线。

### 3.2 但必须改说法（这是 A 的义务，不是可选项）

1. **文档**：凡描述 CLOAK/HOOK 之处，写"对非对抗性读者呈现影子页"，
   **不得**写"防止读取""保护内存""对抗 rootkit 读取"。
2. **UI**：不得给用户"这块内存受保护了"的印象。装上视图的提示语要说明
   它是隐蔽性措施。
3. **验收台账**：相关条目的 `requirement` / `expected` 按 A 的语义写；
   实测"读到影子页"只能记成"隐蔽生效"，**不能**记成"访问被拒绝"。
4. **限制必须与能力同处**：§2.2 那三条配方要出现在面向使用者的限制说明里，
   不能只躺在本文件。

### 3.3 为什么 A 不是降低标准

含糊地当边界用、又不修 fail-open，得到的是最坏结果：
**一个被拆穿了还报绿的保护**。明确记 A 是把真实能力说准。

项目已有先例：EPT **规则**子系统的协议注释原话是
*"a strict hit records and devirtualizes without injecting an exception,
so the same native access may retry and succeed after VMXOFF"* ——
规则早已自我声明是**绊线不是访问控制**。视图继承同一立场。

## 四、按视图种类的细化

A 对两者都适用，但复议优先级不同：

| | 用途 | 对手模型 | 复议优先级 |
|---|---|---|---|
| **HOOK** | 让我们的钩子代码被执行到 | 天然非对抗——真要绕过钩子有一百种别的办法，EPT 不是那道防线 | **低**。建议长期保持 A |
| **CLOAK** | 别让人看见我们改了什么 | 更接近对抗场景 | **高**。B 落地后优先复议这一个 |

## 五、开发规划：选项 B（做成真安全边界）

**状态：未开工。以下是前置链，不是任务清单——上一环不通，下一环无意义。**

### B-1 先决条件：解决 ENFORCE 的 #PF 活锁（**卡点**）

要成为边界，fail-closed 的语义必须从"退虚拟化"改成"**持久拒绝**"——
注异常且常驻继续。规则子系统里对应 `KSW_HVM_EPT_DISPOSITION_INJECT_FAULT`。

**这条今天是堵死的。** `hvm_runtime.c:3124` 明写着拒绝 ENFORCE、
返回 `KSWORD_ARK_HVM_EPT_RULE_STATUS_UNIMPLEMENTED` / `STATUS_NOT_IMPLEMENTED`，
理由是注进去的 #PF 会**活锁**：guest 的缺页处理器看不见 EPT，
它修不了任何东西，返回后重试再缺页，无限循环。

可能的出路（都未验证，**不要当成已有方案**）：

* 注一个 guest 会当成**错误**处理的异常（#GP / #UD），而不是它会尝试修复的 #PF。
  代价：触发方拿到一个用户可见的异常，产品行为改变。
* 给 guest 一个它能理解的失败语义（例如让访问读到确定的零页而不是报错）。
  代价：这不再是"拒绝"，是另一种欺骗，可能又回到 A。
* 只对**已知安全的触发上下文**注 #PF，其余仍退虚拟化。
  代价：白名单本身成为攻击面，且"其余"仍是 fail-open。

**B-1 不通，B 的其余部分全部无意义。**

### B-2 消除三条拆除配方

§2.2 三条要逐条给出**持久拒绝**的处置，而不是退虚拟化：

* 配方 1、2 是状态机问题，`HandleViolation` 返回 FALSE 的分支要有非退虚拟化的出口。
* **配方 3 是结构问题**：单套层次表达不了那个组合。要么承认它并持久拒绝，
  要么改设计（例如指令模拟），后者是数量级更大的工作。

### B-3 重新标定并加负向验收

每条配方一条**负向用例**：构造该访问，断言 `residentProcessorCount` **仍非零**
且访问**被拒绝**。按 `ksword-hvm-false-criteria` 的纪律：
断言写期望的**确切状态码**，不写 `!=`；并检查有没有更早的门会让它空过。

### B-4 复议条件

出现下列任一情况时重开：

1. **B-1 有了经实测验证的解**（持久拒绝真的能在 guest 里稳定工作，不活锁）；
2. 产品侧出现**明确要求边界语义**的需求（例如对抗已知会主动探测 EPT 的样本），
   且愿意承担 B-2 的工作量与 B-1 的产品行为改变；
3. 发现 §2.2 之外的**第四条**拆除配方——说明当前的枚举不完整，
   A 的限制说明需要同步更新（**这一条不需要等 B，发现即更新**）。

## 六、本决定不改变什么

* **不阻塞** EPTP 切换后端接进生产。后端选型与本决定正交（§2.2）。
* **不改变** `用户态退虚拟化决策.md` 的结论。那条的承重理由同样是 fail-open，
  两份文档指向同一个根因。
* **不覆盖**原虚拟化 roadmap 的任何真机验收要求。本文只记录一个语义定性，
  不放宽任何既有标准。
