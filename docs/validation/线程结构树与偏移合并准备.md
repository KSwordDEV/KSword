# 线程结构树与偏移合并准备

## 窗口与读值口径

- 入口：进程详情的线程行双击、进程列表线程区域右键「线程详细信息」。页面属于对象详情和专业字段树，外层复用详情窗样式、对象摘要、搜索、工具带和表格呈现；专业树固定为相对偏移、地址、字段、类型、实际值／解释值五列。正文统一四边 8 px 留白，横向滚动只发生在字段树内。
- `ETHREAD → Tcb (_KTHREAD)` 展示内嵌结构，`Cid` 展开成两个 ID，`ThreadListEntry` 展开成前后链接。偏移相对于包含它的结构，地址是成员存储位置；指针内容只在最后一列显示，不自动读取指向对象。`0`、不可用和布局位置未知是不同状态；旧协议无法辨别某个栈指针为真实零值与未读取，继续显示不可用，而不猜测。
- `ETHREAD` 子树只消费已有固定只读回执，不读取整个结构，不声称已呈现所有成员。R0 刷新调用栈的功能没有因此改变：字段值不是帧，ETW 也不是对象瞬时栈。
- 五列树单独实现在 `ProcessDock/ThreadDetailTreeWindow.cpp`，原 `ThreadDetailWindow.cpp` 保留共用身份核验和只读查询。HostX64 增量构建中两份源码均编译通过，双语和主题门禁通过；最终链接因正式 Release EXE 正在使用而报 `LNK1104`，未更新正式产物，也未做真实 GUI 验收。

## 公开线程设置的行内编辑

- 两条入口仍打开同一个线程详情。顶部搜索按五列文本筛选，保留命中项的父层并展开；清除搜索不重新查询。`R3 线程设置` 和 `ETHREAD` 是同一五列表中的独立根项。公开设置不声称对应某个私有字段，偏移和地址列不填数值。R3 设置和 R0 数据分开刷新，不因 R0 不可用而禁用 R3。
- `ThreadSettingsInline.cpp` 复用树模型、共享工具栏、紧凑 SVG 按钮及标准下拉主题。仅两个公开设置在已取得读取值和普通写权限时出现铅笔。编辑进入受限下拉，右侧 ✓ 提交当前项、× 只丢弃草稿；搜索和复制仍使用已读取值，不把草稿当成已应用。R0 刷新不销毁草稿；R3 刷新在编辑中禁用。五列按用户指定顺序固定，窄窗使用树自己的横向滚动，无额外操作条。
- `ThreadSettingsR3.cpp` 用公开 Win32 API 操作原线程。提交重新复核身份和基线并回读；写前比较和设置不是原子操作。不同结果分别反馈；不设置「时间关键」，不新增驱动通信接口，也不修改任何私有指针或调度字段。
- Windows 自有线程夹具 `tools/tests/thread_settings_r3_tests.cpp`：HostX64 `/W4 /WX`，36 项通过，包括档位、提升布尔方向、写前冲突、身份失配、线程退出和只读权限；固定输出目录内的夹具产物已清理。主程序三个相关翻译单元编译、双语和主题检查通过；正式链接仍因运行中的 `Ksword5.1.exe` 报 `LNK1104`（`.codex-build-logs/ksword-build-check-20261121-121358.raw.log`）。未更新 EXE；真实 GUI 的两入口、搜索清除、行内提交/取消、窄窗、DPI、深浅主题和首帧仍待验收。

- 用 `Machine / PE TimeDateStamp / SizeOfImage / RSDS GUID+Age` 精确对照当前发布包。`InitialStack`、`StackLimit`、`StackBase`、`KernelStack`、`Process` 五个已有项目各有 1,946 个 PE 文件的有类型值可比较，全部已经在发布包且偏移一致（一个键有多个 PE 文件），没有发现这五项需要重复写入。该检查没有修改发布包。
- 宿主磁盘内核 `10.0.19041.7844`（`E2672D6A-6393-04EC-AF7D-417B71DC4D0B/Age 1`）既不在这批 F 盘 PE 里，也不在当前发布包里；邻近构建的偏移不能用来填它。下一步须单独按该 PE 和精确 PDB 的 DBI Age 做发布条目，运行现有发布和解析校验。截图的 `0x20` 是「线程栈字段」能力缺项；组状态确实允许已有三个边界而无 `KernelStack`。即使补齐偏移，也不会自动得到调用帧。

## 如何限制布局矩阵成本

两份精确 PDB 的直接成员实测：Win10 PE `19041.631` 的 `_KTHREAD` 为 204 个字段、`_ETHREAD` 为 120 个；Win11 PE `26100.9711` 分别为 237 与 149 个。两份的位域和重叠偏移数量不同，例如两者的 `ExitTime` 与 `KeyedWaitChain` 都共享偏移，但成员偏移在两版本不同。不能按截图或系统版本号代替精确布局，也不能把 union 的各个别名同时解释成当前有效值。

- 宿主 `19041.7844` 另用微软匹配 PDB 复核：`_KTHREAD` 大小 `0x430`，204 个直接成员（其中 59 个位域）；`_ETHREAD` 大小 `0x898`，120 个直接成员（其中 46 个位域，包含 `Tcb`）。其 `CreateTime@0x430`、`Cid@0x478`，与用户所引文章的 `CreateTime@0x5e0`、`Cid@0x630` 不同。该计数包含符号记录中的重叠项，不是独立存储块数，也不是已读取值的数量。
- 用户最新截图的 `1 / 0x00000000`、缺失能力 `0x0` 表明当次固定请求的项目已返回；截图中 `KernelStack`、`ThreadListEntry` 和两个入口字段的偏移也与上述宿主布局一致。截图未提供偏移来源，不能据此认定发布包新增了条目。当前产品代码仍只投影五个 KTHREAD 和四个 ETHREAD 成员，非完整 `dt`；本次复核未更新发布包或界面。

- 驱动发布包只包含已支持、已校验的运行时字段 ID；给界面用的完整类型布局应独立于驱动启动包。计划以精确内核身份映射到去重的布局记录，按需加载当前身份，而不是主程序启动时读完所有版本。
- `_ETHREAD.Tcb` 只引用 `_KTHREAD` 类型；同一布局里的结构成员只存相对偏移、类型引用与位域描述。字段中文解释单独按限定名维护一次，不随每个内核版本复制。两个相同的偏移只有在完整布局一致时才可以复用，不按单个字段凑配。
- 布局和现场读值分开：类型目录可列出已知字段；实际值仅来自通过身份、范围和读取校验的字段。未读到的值、union 未知分支、符号未公开的成员分别标明。
- 体积试算只在内存中进行：两个精确 PDB 样本，将两种根类型的大小、324／386 个直接成员的名称、相对偏移、显示类型及位域位置／宽度编码为紧凑 UTF-8 JSON，分别是 18,262／21,799 字节，`zlib` 压缩后是 4,298／5,059 字节。不含嵌套类型目录、来源索引、中文释义或实时值，不是正式布局格式或全版本包大小。没有生成任何布局文件，也未测量界面加载和展开耗时。
- 第一期不生成全版本布局矩阵。UI 只按当前精确 PE/PDB 身份加载，复用紧凑布局缓存；没有精确布局时保留原来的有限结果。若以后确需离线分发，先按完整类型布局去重，再按需分片，避免大单体与全量启动加载。代码按符号提取、缓存读取和树表投影分模块，不把生成的数据写进源码。
- 运行时定位只兜底已验证的字段。两台来宾的 `Process`、`InitialStack`、`StackBase`、`StackLimit` 已有访问器路径，离线交叉检查 8/8 与精确 PDB 一致。该结果不证明能推算 `KernelStack`，也不证明可从指令恢复未被访问的成员、类型、位域或重叠布局；没有可靠来源就不猜值或偏移。

## 当前发布包命中率与同分支复用

- 将当前 Release `.json.qz` 按 `Machine / PE TimeDateStamp / SizeOfImage / RSDS GUID+Age` 与 F 盘去重后的 1,954 个内核身份连接。线程详情当前九个直接成员的偏移条目：1,945 个身份齐全；4 个有精确发布条目但缺这九项；5 个没有精确发布条目。九项静态配置不全的占比为 `9 / 1954 ≈ 0.46%`，不代表用户机器分布、实时读取故障率或完整布局可用率。
- 按同架构、同主版本／次版本／build 分组，仅比较语料中相邻且两端身份和九项条目均明确的修订。1,730 对的九项发布偏移均未变，但附带符号的结构大小在 8 对中有变化。例如 `22621.2486 → 22621.2506` 的 `_ETHREAD` 大小为 `0x900 → 0x910`，九项偏移仍相同。相邻样本不是每一次实际发布更新；比较的是静态条目，不是现场读值。
- 上一修订可提供字段名称、类型说明和待核对的偏移候选。只在当前精确符号或当前内核的独立定位结果证实后才允许按偏移读值；没有证据时不得用旧偏移计算地址或把旧布局标为当前布局。两份精确布局一致时可复用同一缓存记录。此次仅做离线核对，未更改加载规则或偏移包。

## 以完整直接成员数为分母

- 口径：`_ETHREAD` 与 `_KTHREAD` 的直接符号成员，计入 `Tcb` 和位域／重叠字段，不再把展开后的子字段重复累加。现有线程详情的运行时偏移解析，源码有 8 个对应成员的定位路径：`_KTHREAD.Process / InitialStack / StackLimit / StackBase`，以及 `_ETHREAD.Cid / ThreadListEntry / StartAddress / Win32StartAddress`。对于 324／386 个直接成员的两份样本，这一已接入路径覆盖 `8/324`（2.47%）／`8/386`（2.07%）；不是逐字段实机读取成功率。R3 公开查询值不计为私有字段原始读值；依赖精确 PDB 或另一套静态偏移来源的路径不计为动态定位。
- 离线对照 F 盘四对精确 PDB，按结构名、字段名、偏移、位域位置和位宽匹配；不验证嵌套类型或语义，不下发任何偏移。`19041.630 → 19041.631` 与 `19041.7802 → 19041.7811` 均为 `324/324`，`26100.9616 → 26100.9711` 为 `385/386`（一项名称不再匹配），`22621.2486 → 22621.2506` 为 `356/357`（新增一项）。这只衡量上一修订作为参考时能匹配多少位置，不能折算为无表读值率。
- 要测无表现场读值率，需用受控目标与已知快照分别记下偏移来源、可定位、读值成功和可核对结果，并排除精确发布档案、内置静态档案及其他已缓存的偏移。现有 deep 采样依赖精确布局且不等于完整树读取，不能拿它的读值数量充作动态定位结果。

## 双邻居推断的留中盲测

- 按同架构、同内核 build 将语料按版本修订号分组，不跨分支。每组三个相邻样本用最前和最后的符号作预测，用中间版本的精确 PDB 作裁判；有缺 PDB／线程类型的窗口跳过。选定的 24 项成员在 1,704 个可比较窗口里有 40,896 个「两侧元数据一致」的预测，均与中间样本一致。样本集中在常用字段，窗口相互重叠，不能据此给出全部字段的错误率。
- 对异常结构大小的窗口重提取两种根类型全部直接成员，用结构名、成员名、相对偏移、位位置和位宽对照。`14393.1737 → 14393.1770 → 14393.1794` 的两个邻居对 280 项均一致，但中间版本 `ETHREAD.ReadyTime` 为 `0x7D0` 而两端都是 `0x7D8`，且中间没有两端共有的 `SetContextState`；两端 `_ETHREAD` 大小均为 `0x7E0`，中间为 `0x7D8`。
- `26100.4484 → 26100.4520 → 26100.4648` 的 384 个两侧一致项均匹配，但中间另有两边都没有的 2 项；`22621.2483 → 22621.2486 → 22621.2506` 有 356 个一致项，另有 1 项只在后一版本出现。比较不证明递归类型相同或现场可读。
- 因此两侧一致适合作为优先核对的参考候选，不是当前版本的证明。两侧不同可保留两个版本及候选，缺字段也是一种候选状态；只有单侧时明确标记。实际读值仍要求当前版本独立定位或精确布局。不因读出的字节看似合理就选择候选，不将推断写入驱动启动包。本轮只做诊断文档和离线核对，未启用运行时回退。
