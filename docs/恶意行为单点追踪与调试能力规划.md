## 1. 产品目标与要解决的问题

KSword 正在准备把系统监控能力发展为产品重点。本能力依托现有全面系统监控、内核访问、调试及取证基础，提供可编辑的全自动或半自动恶意行为监控与调试工作流。

用户希望解决的主要问题：

- 传统行为监控对不断转移执行位置的新型病毒跟踪不足。
- 样本通过进程注入、线程间执行转移或驱动干扰，脱离原进程及普通 R3 监控范围。
- 日志输出分散、不直观，难以理解样本如何传播、哪些线程实际执行了载荷。
- 发现异常后，暂停相关对象、保留载荷和归档通信需要大量人工操作。

产品竞争目标是显著超过 Action Scope 等同类行为分析工具。该目标需要通过同场景的覆盖、时延、归因、取证和交互比较验证，不作为现有能力声明。

核心体验：从一个指定调查起点出发，持续跟随其跨进程影响和实际执行传播，用树状行为视图展示，在规则指定的节点暂停、调试并取证。

### 2.1 进程粒度作为第一阶段交付目标

2026-11-23 补充：先以进程实例为追踪颗粒度，在已验证操作路径内尽早纳入受到影响的进程；线程与区域执行追踪用于继续提高归因精度，不作为进程级纳入的必需前置条件。

```text
种子 A 对 B 发生符合策略的跨进程影响
  → 将 B 纳入关联监控，保留 A → B 的直接证据
  → 继续接收 B 的相关跨进程行为
  → 按策略纳入 C，保留 B → C 的事实或候选关系
```

这样可以避免依赖新线程通知，也不因 B 使用既有线程、线程池或 A 已退出而天然断链。进程内执行者切换不改变 B 的实例身份。相比任意区域的持续全线程执行监视，该目标更容易形成可验证的闭环。

但降低颗粒度只降低目标管理与关联难度，不能补齐传感器缺口，不能据此承诺“一个不漏、一个不多”。至少分别维护：

| 维度 | 状态及依据 |
| --- | --- |
| 监控范围 | 未纳入、准备中、已纳入、覆盖降级、已退出；保留生效时间与准入来源 |
| 载荷执行 | 未观察、进入尝试、已确认；没有证据时不因已纳入便认定执行 |
| 下一跳 | 观察到直接跨进程操作、样本来源传播已确认、策略候选；操作发生事实与恶意来源归因分开 |

B 可能是大型正常宿主；将其整体纳入可以提高调查召回，但 B → C 的实际写入本身并不证明由 A 的载荷发起。进程级策略可以保守扩大监控，必须显示扩大依据及策略版本，不能将所有宿主活动涂成已确认病毒传播。

**快速连续传播仍需独立解决订阅竞态。** 如果 B 被纳入前已经操作 C，R3 收到 A → B 后才添加 B 的源过滤条件会断链。候选方案是在受支持的同步入口内先扩展受控集合，或由已启动的来源保留足够的最小事件并按身份、时间补关联；后者只能在保留窗口与无丢失条件内成立，也不具备追溯的同步阻止能力。精确执行前控制仍需另行验证。

目标数量、事件吞吐或深度达到上限时，记录未纳入对象和覆盖缺口，不能静默截断后仍报告完整。共享映射、驱动代写、监控启动前传播及丢包继续保留原有边界。

第一阶段建议的产品表述：

> 在已验证的跨进程操作路径和监视窗口内，从指定种子出发，及时纳入受影响进程，持续保留关联与取证，并明确显示候选归因和覆盖缺口。

分别验收“相关进程纳入覆盖”“已观察操作的关联正确性”“样本来源归因”和“线程执行证据”，不以其中一项通过代替其余项目。

### 2.3 分析项目、多次采样与运行会话

2026-11-24 用户明确把断点、采集结果等统一组织在“分析项目”里，一个分析项目包含多次采样。项目是跨程序启动保存的工作单位，采样是一次独立配置、环境、事件与结果记录；运行会话持有本次真实控制权。详细层级、配置快照与断点复用见[分析项目与多次采样设计](ActionAnalyze分析项目与多次采样设计.md)。

项目断点定义可跨会话复用，每次采样重新绑定实际目标并记录生效状态；旧 PID／TID／VA、stopId、挂起责任与句柄不直接迁移。采样保留实际规则／断点版本、运行期配置变化及证据，后续项目编辑不覆盖历史。多次采样横向比较明确列为待做，目前只保留未来比较需要的来源、环境、版本与完整性依据。

## 3. 能力模型：来源、内存、线程、下一跳

### 3.1 主链路

```text
指定种子进程 / 线程
  → 可观察的跨进程写入或映射行为
  → 目标进程中的区域及内容版本
  → 目标线程到达 / 执行该内容
  → 该执行活动产生的下一次跨进程影响
  → 下一目标区域及实际执行线程
```

用户目标是跟住载荷与执行者的转移，不因原进程退出、目标是正常程序、没有新线程或没有私有 RX 区域便中断关联。

树是展示形式，底层建议采用有类型、有方向、有证据引用的关系图。一块区域可有多个写入来源，一个线程可执行多个载荷；进程父子树与载荷传播关系必须分开。

### 3.2 术语与证据强度

| 术语 | 含义 | 不可混用的结论 |
| --- | --- | --- |
| 污染 / 脏内存 | 本会话记录了需要跟踪的来源影响，是来源标签 | 不自动等于内容恶意，也不等于 CPU 页表 Dirty 位 |
| 写入请求 | 捕获准备操作的目标、范围和参数 | 不等于成功写入 |
| 写入结果 | 捕获成功、部分成功、失败及有效字节数 | 不能把请求长度直接当作实际成功长度 |
| 执行进入尝试 | 断点或执行异常证明线程到达受监视位置 | 不保证原指令已经完成或已产生副作用 |
| 已确认执行 | 后端根据明确证据确认其支持范围内的实际执行 | 不能只用“已发送继续”代替 |
| 历史执行关联 | 某线程曾经到达 / 执行特定版本内容 | 不代表它此后每项正常工作都来自该载荷 |
| 活动执行关联 | 当前执行活动仍有依据与污染来源关联 | 不能用任意固定时间窗口冒充精确控制流归属 |
| 下一跳传播 | 有明确操作把来源影响连接到另一目标 | 同时发生、持有写权限或线程有历史标签均不足以单独证明 |

事实记录、规则判断和操作权限建议分别维护。用户可以选择较宽的追踪策略，但界面与证据必须保留该策略属于直接关联还是保守扩展。

### 3.3 身份及版本建议

建议的最小身份：

- 进程：启动标识、PID、创建身份。
- 线程：所属进程实例、TID、线程创建身份。
- 内存：目标进程实例、映射代次、字节区间、内容版本、来源事件。
- 事件：会话与传感器代次、源内序号、时间及其时钟定义、调用关联标识、来源与结果。
- 停点：会话所有者、目标实例、stopId、现场代次和实际状态。

释放后重新分配的相同 VA 不继承旧标签；同一地址被覆盖后的内容不能继续使用旧版本证据。实现可用页面承担监听，但来源记录应保留实际字节区间。并发修改导致内容版本无法确定时，明确记录不确定。

## 4. R0 跨进程追踪的研究边界

### 4.1 操作覆盖清单

优先建立以下语义清单，逐项登记 API / syscall、真实经过的内核路径、可观察字段、同步性、系统条件及验证结果：

1. 跨进程内存写入、部分写入及失败。
2. 分配、释放和保护变化，包含先 RW 写入、后转为可执行。
3. 节对象及共享映射承载代码、解除映射和别名关系。
4. 新线程执行、既有线程上下文变化及恢复。
5. APC、线程池、回调等执行转移入口，不按某一种手法替代全部覆盖。
6. 原有映像可执行代码被修改后沿原路径执行。
7. 驱动代写及内核发起的相关路径，按实际能力单独登记。

共享映射中的代码传播仍在研究范围内，不能因为本期排除了仅数据攻击就顺带排除。普通 CPU 存储、共享别名和内核直接修改不一定经过用户态远程写入 syscall；未覆盖的路径应保留缺口。

“穷举 syscall”用于避免遗漏操作入口，不构成“已经观测到全部内存写入”的证明。R0 正在执行的线程、附加的地址空间、请求发起者与最终代码来源也不是天然同一身份，需按具体路径分别记录。

### 4.2 三个必须分开的能力等级

| 等级 | 能力 | 对同步追踪的意义 |
| --- | --- | --- |
| 操作遥测 | 收到某操作发生的事件 | 支持及时关联，不能保证已经来得及阻止执行 |
| 操作边界介入 | 在操作前或返回前执行追踪逻辑 | 有机会布设监视，但仍须验证目标并发执行 |
| 执行前停点 | 在受监视指令产生预期副作用前停止 | 支持载荷执行前调试；不能将前两级默认升级到本级 |

普通对象回调主要观察句柄操作；线程通知主要观察生命周期；现有普通 syscall ETW 不提供完整跨进程写入参数。拥有一个能读写目标内存的驱动，也不等于拥有观察其他程序全部写入的入口。

候选来源包括符合部署条件的专用内核遥测、公开回调和受限同步插桩。Threat Intelligence 的消费权限、事件字段、开关及系统差异需实际核对，不能假定普通管理员或普通驱动自然具备全部条件。

自行修改内核代码或服务路径存在 PatchGuard、HVCI、版本和生命周期约束。精确 PDB 定位不能替代长期稳定性证明；本规划没有确定通过关闭安全能力或绕过保护获得覆盖。

### 4.3 写入与执行的关键竞态

```text
A 开始修改 B 的已有可执行区域
  → B 的既有线程并发进入这块区域
  → A 的写入操作返回
  → 监控端收到事件并开始设防
```

如果只在写入返回后布设监听，可能已经错过执行；写入进行期间还可能出现部分更新的内容。原型必须证明支持范围内何时完成设防、何时确认内容版本，以及是否存在其他线程可以进入的窗口。

## 5. 指定可执行内存的执行线程监视

### 5.1 已明确的研究问题

对于某个具体可执行区间，从监视开始后识别哪些线程到达 / 执行过它，并评估能否完整覆盖全部相关线程。这是本能力的技术重点，不以周期采样 RIP、线程起点或事后扫描代替。

如果此前没有执行记录，不能仅凭当前内存、页表和线程状态可靠恢复过去所有执行线程。本规划关注开始追踪之后的在线行为；归档用于证据和规则验证，不把历史复原变成主任务。

### 5.2 已定原型路线与其它机制用途

对已纳入区域，首个原型采用NX取指发现、目标外停止账、选定线程受控推进和重设防；不是“所有机制尚未选型”。下表保留各机制的适用职责，完整线程／新线程门控、写入发现、异常继续和Ready失效仍按[缺口复查G03–G10](ActionAnalyze规划缺口复查与补齐任务.md)验证；未通过不得开放全覆盖声明。

| 候选 | 可以研究的能力 | 主要验证边界 |
| --- | --- | --- |
| 硬件执行断点 | 精确地址的同步进入事件 | 通常四个地址槽、逐线程配置、任意区间及中部进入不能由少量入口自动覆盖 |
| 软件断点 | 已知地址的同步进入事件 | 修改目标代码、并发恢复、自修改和代码版本 |
| NX / 页面执行异常 | 捕获页面上的执行进入尝试 | 页粒度、权限更改、并发放行窗口、目标原有异常语义 |
| PAGE_GUARD | 页面访问告警 | 非执行专用且一次触发后清除，不能直接当成持久执行监听 |
| 动态二进制插桩 DBI | 受控执行路径内逐线程记录 | 覆盖完整性、目标兼容性、动态生成代码、自修改及性能 |
| Intel PT | 硬件控制流记录与线程执行归属 | 平台及 OS 接入、上下文关联、代码版本、解码和溢出；不天然提供同步停点 |

Intel PT 本身不是自建 Hypervisor 方案，可作为不引入虚拟化的候选研究，但尚未确认当前部署条件与工程选择。任何候选都不能仅凭一次命中实验宣称覆盖全部线程。

### 5.3 页面监视的并发窗口

```text
页面不可执行
  → T1 触发执行异常
  → 页面临时恢复执行，允许 T1 前进
  → T2 在另一 CPU 进入同页
  → 页面重新设防
```

简单的放行再设防可能漏掉 T2。页面执行权限不能直接表达“仅允许 T1 执行”。是否通过线程调度约束、插桩或其他办法消除窗口，必须由原型证明，不能把缩短回调耗时当作窗口已经消失。

2026-11-24 用户明确允许命中后统一停止。由此不再要求页面权限本身提供逐线程执行资格：保持 NX，完成必要线程的停止屏障，只放行选定线程受控前进，重设 NX 后才恢复其它线程。第 5.6 节已用固定两个自有线程验证这一顺序；“其它线程一直运行”的限制不再作为本路线的前提。

### 5.4 完整性与时延的判定

分别报告精确命中、完整线程集合、同步暂停三项结果。理论上的完整性只在明确假设下成立：提前设防、相关线程和映射均受控、内容版本有效、没有放行盲区、记录无丢失且监视链可信。

明确标注每段覆盖的起止、未武装区间、重装窗口、丢失记录和失效原因。“未记录到其他线程”不能自动改写为“没有其他线程执行”。

### 5.5 线程池工作项篡改与原有代码洞场景

2026-11-24 用户指定验收场景：样本篡改目标进程线程池工作项，将 shellcode 写进目标程序原有代码洞，再由原有工作线程执行。该场景属于代码执行传播；不能因为其中包含工作项数据修改，就按 R-12 的“仅数据攻击”排除。

此场景尚未实现或通过运行验证。需求模型可容纳，不等于现有 API Monitor、ETW 或普通回调已经覆盖。分别验证以下证据：

| 环节 | 需要的证据与边界 |
| --- | --- |
| 来源影响 | 写入或映射的真实来源、目标实例、区间、实际结果及版本；未捕获来源时不能从模块差异反推注入者 |
| 原有映像代码修改 | 纳入现有可执行映像与代码洞，不只观察新分配、MEM_PRIVATE、RWX 或保护变化；模块身份正常不代表其中字节未被改动 |
| 工作项关系 | 篡改对象与回调目标可取得时保留其依据；不能将“线程执行该代码”直接命名为“已确认线程池工作项篡改” |
| 原有线程进入 | 通过已验证执行来源取得 TID、线程身份、实际进入地址与匹配的内容版本；不以新线程通知、线程起点或回调 API 日志替代 |
| 后续传播 | 对已关联线程继续收集适用 API 和下一跳影响，明确直接证据与持续跟随策略的区别 |

用户已明确两个默认值：

- 尚未确定执行 TID 时，“默认等待”仅指等待开启该线程的完整 API 记录；发现执行者所必需的探针仍须工作。不能先按相关 TID 过滤掉发现证据，再等待该证据自动确定 TID。
- 线程池线程关联后，默认持续追踪，结束条件可配置。后续正常任务不自动成为“已确认来自载荷”的行为；实际载荷执行与保守延续跟随分别呈现。

受支持的迁移入口默认采用内部准入：拦截本次发起操作、布设目标监控与所需探针、核对真实就绪后自动继续；没有用户断点时不触发可见全局暂停。用户选择只拦迁移发起者，B 原有业务可以继续，因此“目标 Agent 已安装”不能单独证明 B 的既有线程执行已经受控。已纳入区域采用前述NX原型路线，具体来源的sourceReady与指定区域的regionReady分别核对；完整门控仍待验证。若仅具备异步执行证据，还须报告启用 TID 完整 API 记录前的覆盖窗口。

仅捕获写入时，结果为“已观察修改，执行者未确认”。仅发现执行而没有来源证据时，结果为“已观察执行，原始来源未确认”。若写入途径未覆盖、执行设防太晚或存在并发放行盲区，须按对应层报告缺口，不能把此场景列为完整支持。

官方语义核对：[Thread Pools](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-pools) 说明同一工作线程可以先后执行多个回调；[VirtualQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualqueryex) 说明发生写时复制后的映像页仍可能报告为 MEM_IMAGE。这些资料支持场景与判据边界，不证明本项目已有执行监听实现。

### 5.6 页面执行探针实测与统一停止路线

2026-11-24 已完成自有原生夹具 HostX64 Release 构建与 Windows 10 19045 运行，21 项断言通过。详细源码、产物、日志、官方资料与验证范围见[页面执行探针验证记录](非虚拟化页面执行探针验证-20261124.md)。

| 测试 | 取得的证据 | 不能扩大的结论 |
| --- | --- | --- |
| PAGE_GUARD + 预先存在的线程池 worker | 首次进入自有 MEM_IMAGE 页取得真实 TID；重复进入及读取先消耗 Guard 的漏报均复现 | 不能据首次命中宣称持续监听；没有修改代码或篡改工作项 |
| NX 后直接恢复 RX，其它线程继续 | 首线程仍保持在异常处理器时，另一个线程可以执行同页而不产生新异常 | 只否定这个放行次序，不否定先统一停止的方案 |
| NX + 两个自有线程停止屏障 + 选定线程 TF 推进 | 恢复 RX 前逐个持有挂起并读取现场；T1 前进到页外并重设 NX 后，T2 仍产生独立执行异常；各有副作用，正常退出 | 固定两个自有原生线程，控制器继续运行；不是任意目标完整线程冻结、新线程准入或生产调试后端验收 |

当前判断：采用命中后停止必要执行者、按需放行的调试式方案，页面首次发现与受控重设防已有机制证据，值得进入产品原型；持续零漏报、任意代码洞、来源写入完整性与性能仍分别验收。

至少停止目标进程中可能进入同一页的执行者，不能只停已经关联的 TID，否则未关联的工作线程仍可能漏过。内部页面停止组与用户选择的“全局暂停默认只含已关联线程”分开：临时冻结宿主线程不将其纳入病毒来源归因，处理完成后只释放本会话增加的控制责任。

迁移前只拦发起者与命中后停止目标并不冲突。没有用户断点时，内部停止、执行者登记与重设防可自动完成；用户断点命中则按其动作保持停点。实际控制器应避免被自身停止集合冻结，且不能等待暂停线程持有的目标堆、加载器或业务锁。

实现前还须解决完整线程集合与新生线程门控、并发异常独立现场、同页正常代码、内容版本、恢复失败及长时间不离开被测页。单步一条后 RIP 可能仍在页内，不能立即恢复所有线程；推进范围与时间必须有预算及明确退出策略。

### 5.7 栈破坏、返回地址与代码复用

用户复核指出原规划未展开“堆栈溢出攻击发现”，本轮补充[栈破坏与控制流劫持发现设计](ActionAnalyze栈破坏与控制流劫持发现设计.md)。栈空间耗尽、栈缓冲区越界、可信GS／CFG／影子栈保护失败、返回地址／异常处理目标破坏、pivot及ROP分开处理；不能根据一个异常码、栈界限或一次展开失败确定攻击。

这条分支允许同进程普通CPU写入，不以远程写API或新可执行页作为前提；ROP复用原有代码，NX区域路线不构成完整覆盖。返回地址等控制数据破坏在本范围内，不因“仅数据攻击延期”被排除。计划接异常／保护来源、有限现场、frame/slot生命周期、显式选择的精确watch和可验证控制转移证据；先保存事实再作归因，不宣称普通R0能观察全部store或在所有越界写之前阻断。现有Minidump异常释义不是持续检测器。

## 6. 线程传播、调试及取证工作流

### 6.1 线程粒度的传播

建议同时保留线程历史关联与本次活动关联。线程池工作线程可能在执行载荷后继续处理正常任务，不能默认将其所有未来行为永久归因给样本。

2026-11-24 用户明确：线程一旦关联，默认持续追踪，结束条件可配置；这是采集与跟随策略，不是持续来源归因。活动关联如何开始、结束和跨调用保留仍待验证，必须在关系和视图中标注策略推断，不能把它写成精确数据来源。

### 6.2 可编辑处置流程

用户希望支持全自动和半自动；具体规则语言与编辑器尚未确定。建议先支持有限、可解释的条件和动作：

- 在写入请求、写入完成、执行进入或下一跳传播节点触发。
- 按条件暂停线程、相关进程或用户明确选择的集合。
- 保存寄存器、线程现场、相关区域、进程 dump 及对应网络证据。
- 半自动提出动作并展示目标；全自动执行预先配置的策略。
- 每次操作记录触发依据、真实对象、请求和实际结果，提供继续、取消及失败恢复。

原生调试事件、普通挂起、页面异常停点和历史日志是不同语义。某线程进入内核不代表可在任意回调中等待 R3；同步等待必须限定执行环境、锁与恢复责任。

暂停只持有和归还本会话的责任，不释放外部调试器的停点或其他工具的挂起。全进程及单线程暂停均可能影响锁持有者，需实测 dump、控制端退出及恢复流程。

2026-11-24 用户先要求挂起等控制尽量提升到R0，随后明确建立**R3和普通R0两套独立调试机制**。以最新要求为准：R3是可独立完成受支持用户态分析流程的正式后端，不以驱动在线或R0源码修复作为前置；R0后端在验证通过的系统中承担自己的控制与恢复。每次采样显式选择，挂起／恢复、停止组、上下文、TF／DR、页保护及异常继续由所选后端唯一记责，不在调查内部绕账本。两后端能力不足均明确报告，不因故障或超时静默切换，也不将用户态控制扩大为任意内核线程安全挂起。

具体流程、能力差异、owner死亡失败和DB01–DB06施工增量见[双后端独立全流程设计](ActionAnalyze双后端独立全流程设计.md)。R3控制采用目标外Windows原生调试事件，无须目标自有VEH；API／ETW来源按实际权限与覆盖接入。流程完整不等于全部写入／共享别名／下一跳均可观察，也不代表调试控制器任意死亡后仍能保留目标正常运行。当前Explorer负控已经发现后者失败，不能靠改选R0关闭该门槛。

### 6.3 驱动线程目标

“病毒驱动线程智能暂停”保留为用户的能力目标，单独研究，不冒充已经可行。驱动可能通过专属系统线程、公共工作线程、DPC、定时器或回调执行；不一定有一个可代表驱动全部行为的线程。

归属到驱动、捕获执行与安全暂停分别验收。挂起持有内核锁的线程可能阻塞系统与恢复通道，不能直接套用用户态线程策略。同内核信任域受干扰时，也不能保证所有来源持续可信。

### 6.4 取证及行为视图建议

以一个会话关联树、时间轴、事件详情、停止现场和证据文件。显示来源线程、目标区域版本、命中线程、传播证据、监视缺口和处置状态。多来源及循环传播用交叉引用呈现，不伪装成单父节点关系。

dump 与区域保存说明采集范围、时间、完整或部分结果和内容一致性；先取证还是先暂停由流程明确。网络存档若需要覆盖触发前通信，必须提前采集并说明实际保留窗口，不能事后补造流量。

已明确的布局与规则语义见第 6.6、6.7 节，调查动作与导航语义见下节。后续页面须按根目录 AGENTS.md 分类、检查相似页面并复用共享组件；本说明书不构成已实现 UI 或视觉验收。

### 6.5 行为树上的全局下断与一键调查

2026-11-23 用户补充：行为树应成为 KSword 全方位检索与调试的操作入口。在全局下断后，用户能一键组织线程堆栈解析、进程/区域内存保存、shellcode dump 等，不必手动逐个打开工具、重新输入 PID/TID/地址和整理输出。

本设计中“全局”指当前追踪会话纳入的对象集合或明确选择的全部分支。采用请求时冻结的进程/线程实例集合，分别记录每个对象的停止机制、停点及成功/失败；不能将逐个暂停报告为同一 CPU 时刻的全系统原子停止。驱动线程等对象按已验证能力单独处置，不将用户态批量挂起扩充成安全冻结整个 Windows 的承诺。

用户已确定 Agent 同步下断采用命中线程直接进入已登记停点、由目标外所有者接管。UI 和 CLI 手动暂停进入同一协调者。原线程停止、组内逐项停止和附带原生暂停各自有明确回执。R3 首个切片覆盖实际调用前与调用返回边界。[同步接口与性能](ActionAnalyze同步全局断点与性能复查.md) · [工程开工基线](ActionAnalyze工程开工基线.md)

建议工作流：

```text
规则触发 / 用户对当前追踪会话下断
  → 回读各对象真实停止状态，形成本次停止组
  → 用户点击“一键调查”，选择已有调查预设或沿用默认预设
  → 冻结对象、停点、线程上下文与关键内存
  → 解析调用栈、注释模块/符号、保存载荷候选并开展关联检索
  → 结果及证据挂回树节点，可继续打开既有 KSword 专业工具
  → 用户明确继续时，由原控制所有者恢复
```

调查范围支持会话、子树、所选进程、线程及区域，分支间共享的对象按实例去重。预设说明将采集哪些内容和预计范围，执行后逐项反馈；“一键”表示一次发起一组明确任务，不把全部全盘检索和所有大内存导出默认启动。

| 调查能力 | 一键流程的目标 |
| --- | --- |
| 线程上下文与堆栈 | 批量保存适用的真实上下文、用户栈和内核栈，解析模块/符号，定位落在关联载荷区域的帧；各来源分别呈现 |
| 内存 dump | 按预设采集进程转储、模块或字节区间，保留格式、范围、架构、缺页与部分结果；原始区域文件和标准进程转储明确区分 |
| shellcode dump | 从关联写入范围、执行进入地址或用户所选区域提取候选原始字节，保存 VA、边界依据、版本、入口及 hash；不能假定整块 RX 页都是 shellcode |
| 内存与模块分析 | 对已保存字节复用 HEX、反汇编、RAW 反编译、字符串及内容比较；后续实时扩读属于新的采集批次 |
| 全方位关联检索 | 在所选范围和预算内联动现有线程、模块、句柄、内存、文件及网络记录，区分停止组现场、历史事件与稍后查询 |
| 专业工具直达 | 从线程、帧、区域、模块、文件与证据节点直达对应主程序工具，保留会话/对象/地址身份，不重复附加或抢占原停点 |

先捕获容易随继续执行而变化的原始现场，再进行耗时符号下载、解析及界面生成。目标被暂停也不代表共享映射或内核代写已冻结，跨进程采集保留各自时段，不冒充全组一致的原子快照。捕获原始证据完成后，解析可独立继续；调查完成不自动放行原本由用户保持的停止组。

Qt 依赖允许存在于可独立调用的分析执行模块，主程序保留完整调查能力。自动调查不得为了复用功能而创建页面、Dock、隐藏窗口或控件；只依赖 QtCore 的后台对象与 UI 控件分别核对。CLI 在自身能力范围内执行，不依赖启动主程序或连接本轮未实现的 Qt 执行端；尚未脱离页面的流程须先抽取本端直接入口，不能按“窗口隐藏”计作完成。

停止组、先采集后解析、对象身份与结果挂树的语义继续保留；三端分别落地，不据此要求统一执行宿主或跨端会话。历史执行器讨论见 [原架构设计第 6.4 节](单点追踪共享采集架构与CLI设计.md#64-停点调查工作台与-qt-能力执行器)，不得将其中部署形式直接当作当前决定。

### 6.7 行为语义规则、条件表达式与模板来源

用户所说“行为规则”是把原始事件解释成行为语义，例如注册表访问解释为虚拟机线索探测；不能仅设计成自动暂停／dump 的处置配置。

已确认默认聚合成语义行，可展开原始事件与时序；默认同一线程关联，规则可声明同进程、传播分支等更宽范围。上游明确要求跨线程／同进程时须保留该作用域，不能无提示改成同线程后仍宣称等价。字段缺失、截断、读取失败与真实空值分开，缺字段处理由每条规则配置。

规则模板范围包括本地 `KswordSandbox` 与公开上游的全部可收集类别。详细来源清单、逐项授权状态、事件字段缺口、适配顺序和验收工作包见[行为语义规则模板收集与并入规划](行为语义规则模板收集与并入规划.md)。收集目录可以先完整登记，运行时仅装载本会话启用且依赖满足的规则子集；没有字段和关联能力的模板不得按已支持计数。

用户提出 C# 风格表达式，并要求字符串、缓冲区、多参数、计数与序列等能力。保留有界表达式外观，调用前单事件谓词在受支持同步入口内执行，跨事件状态由本端控制器处理。具体类型、函数、转义、三值与预算已有[筛选器与规则语言设计](ActionAnalyze筛选器与规则语言设计.md)建议；尚待A0机器契约及A2执行器实现，不再整体留作“待设计”。不开任意C#／Python执行，不把异步语义匹配伪装成操作前判定。

### 7.1 结构、内存和 UI 性能约束

2026-11-24 用户强调谨慎设计代码结构，关注程序内存与 UI 性能。下面是产品原型的设计及验收要求；不是已经测出的性能结论，也不要求先重构全项目。

| 职责 | 结构与资源约束 |
| --- | --- |
| 命中／同步控制路径 | 保存必要固定现场、对象身份与控制代次，使用预分配的有界记录；控制回执与普通日志分离并预留容量，日志拥塞不能吞掉停点／恢复。不解析脚本、不展开堆栈符号、不写大 dump、不调用 UI，不持有日志／Hook／队列锁等待用户 |
| 停止协调 | 各端由明确所有者持有停止组与恢复责任；控制通道不依赖被停目标的业务线程。先确认屏障，再恢复 X；重设防成功后才解除其它线程，失败保留真实状态 |
| 事件规范化 | 用紧凑、不可变事件与稳定 ID 保留来源、时间域、字段有效性；路径／模块等高重复数据按会话索引。禁止 UI 行、语义命中、传播边各复制整份原始事件 |
| 区域及线程账本 | 按进程实例、映射代次和区间索引查询，不为每条 API 扫描全部进程／线程／区域。内容版本按实际变化创建，不因显示刷新重新读内存；缓存与历史均有上限 |
| 规则与关联 | 按已启用规则、事件类型与字段建立候选索引，预编译适用谓词；窗口、对象状态、证据引用与依赖闭包有预算。超限、丢包、超时分别记覆盖降级，不静默生成确定结论 |
| 归档与调查 | 原始归档、内存检索窗口、语义状态、调查文件与显示缓存分别计量；批量后台写入，原始证据保存后按需解析。慢磁盘不能使命中路径无限积压 |
| UI 投影 | 复用项目模型与结果容器，后台产生增量批次，GUI 在时间预算内提交；列表采用模型及按需行，不为每条事件创建控件，不逐事件 reset／重排／重绘全表。状态以真实回执为准，内部逐指令停顿不触发逐次动画或全图重建 |
| 图、瀑布流与详情 | 有界时间密度、稳定对象节点和局部边更新；缩放不重建采集记录，原始依据与堆栈按需展开。隐藏页可延后投影，不停止业务采集／归档，也不无限累积待绘队列 |

内存核算至少分为：原始包窗口、字符串／对象索引、规则状态、停止现场与栈、区域字节版本、UI 投影缓存。兼容现有归档字段时，不在内存中同时常驻同一事件的 Base64、完整 JSON、表格文本和详情副本；格式化与反序列化按需进行。区域 dump 和完整调用栈可能比规则正文占用更多，必须分别计量，不能只限制表格行数。完整历史通过带索引的归档异步读取，展开一条证据不能让 GUI 线程载入整份会话 JSON。

首轮基线分别测无监控、仅记录、记录加规则、再加可见 UI、命中冻结与单步重设防。记录事件速率、各队列高水位和丢失、归档吞吐、工作集／私有提交峰值、各缓存及关联状态占用；控制阶段测冻结、停止回执、单步重设防的 P50/P95/P99 与最大值。

UI 验收包含持续追加时滚动／选择、筛选、拖选瀑布流、图多选、展开依据和后台归档并行；测输入响应与提交耗时，不以定时器间隔宣称流畅。数值预算随原型基线确定，超预算时的降采集／停止／保留证据策略必须可见；未测量前不承诺帧率、内存固定值或暂停上限。

## 8. 建议验证顺序与验收依据

本节是产品能力的后续建议。第 5.6 节只完成局部机制夹具，其余工作不能按表中阶段已经通过计数。

| 阶段 | 验证目标 | 必须得到的证据 |
| --- | --- | --- |
| P0：入口与部署核对 | 选出可用跨进程事件来源和同步入口 | API / syscall 到内核路径的覆盖矩阵、权限和配置条件、捕获字段及时间语义 |
| P0a：进程级连续传播 | 无需等待线程命中也能跟住 A → B → C | 纳入真实生效时刻、极短间隔下一跳、源过滤与补关联边界、容量上限及正常宿主扩展的候选标记 |
| P1：单区域执行实验 | 指定区域与既有线程的可靠命中 | 独立真实执行计数与记录对照、并发盲区、进入尝试与实际执行区别 |
| P2：完整第一跳 | A 写入 B，B 的线程被精确跟踪 | 写入前设防时序、成功范围、版本、停点及恢复结果 |
| P3：多跳传播 | B 的关联执行活动影响 C | 传播边证据、活动与历史状态区分、正常线程池工作不被无依据扩散 |
| P4：规则及取证 | 各端的半自动及预设全自动流程、停止组一键调查 | 动作真实回执、失败恢复、栈与 dump 证据对应同一批次、不创建对应页面的直接调用、结果挂回树及保持停止；分别记录三端覆盖 |
| P5：对抗与产品验收 | 支持矩阵内的稳定性、性能及交互 | 长期压力、多版本、传感器失效及竞争产品同场景对照 |

最小原型用自有 A / B / C 程序建立独立的执行事实源，不依赖真实病毒是否恰好触发行为。

重点用例：

- 标准 API、直接 syscall、失败与部分写入。
- 先 RW 写入后转 RX、修改已有可执行映像、写入进行中目标即尝试执行。
- 既有线程、多个并发线程、新线程、CPU 迁移、从区间中部进入。
- 内容覆盖、自修改、跨页指令、共享映射别名、释放与地址复用。
- 线程与进程退出、PID/TID 复用、监控启动前已有执行。
- 外部调试器占用、停止中取消、控制端死亡、记录队列满及磁盘写入失败。

报告事件层、执行层和控制层各自的覆盖与丢失，测量行为到停点 / 通知的 P50、P95、P99，以及 CPU、内存和归档成本。具体阈值待原型基线确定；不能拿刷新周期或平均值代替最坏窗口与漏跟证据。

普通构建和离线模型通过不代表驱动可加载、执行追踪完整、GUI 已验收或长期稳定。完整端到端原型验证前，不采用此前粗略工作台估算承诺本执行引擎工期。

| 迁移同步准入 | 各端 A→B 准入状态机、目标身份与必要 Hook／探针就绪回执 | 快速 A→B→C；B 读端提前建立，不能出现 broker 等 Hook、控制端等 broker 的互等 |
| 页面执行与停止协调 | 以第 5.6 节为机制起点，加入完整线程集合、并发异常和保护恢复账本 | 未知既有 TID、多个合法入口、新线程竞态、退出与恢复失败分别有真实回执 |
| 逐线程 API 与调用前条件 | TID 配置及 ACK、有限参数快照、独立可靠控制通道、有界表达式编辑与示例 | 真实前置匹配、无日志丢包依赖、停线程／停止组／继续、目标持锁场景与失联恢复 |
| ETW 并采 | 明确 payload 身份、订阅条件、事件与接收时间、异步暂停入口 | 时序不伪造，无法取得前置控制的来源明示异步；不同丢失层分别统计 |
| 行为模板及语义处理 | 全来源目录、适配器、字段依赖、规则版本、证据聚合；详见模板专题 | 单事件／共现／有序／计数分开测试，反例与缺字段通过；不执行上游脚本 |
| PowerShell 与脚本 | 启动命令、明确脚本事件来源、ScriptBlockId／分片重组、正文证据及条件 | 区分命令行线索与实际脚本块；没有正文时内容规则不可用，不以启用 Provider 算已捕获 |
| 网络关联与归档 | 连接／请求对象生命周期、DNS／HTTP 适用字段、可选流量存档与保留窗口 | 同对象关联、真实完成／字节数；没有正文／TLS 元数据时不得伪造，触发前通信只能来自预先保留 |
| 一键调查 | 本端直接调用用户栈／内核栈、区域／模块 dump、候选载荷保存和补充检索 | 不创建页面／Dock／隐藏控件，现场与批次身份完整；标准进程 dump 另证，不冒充区域 raw dump |
| 工作台与分端交付 | 第 6.6 节布局、图与调试条、聚合及可展开依据、各端导出 | 真实导航与对象选择、取消语义、三端覆盖、深浅／窄窗及输入性能分别报告 |

线程级污染、联合暂停、栈溢出发现、反反虚拟机等不能以宣传项代替实现证据。用户现已明确要求反反虚拟机深入行动方案，已单列[16探测面／15项任务／7组实验](ActionAnalyze反反虚拟机与环境实验行动方案.md)：从观察字段、一致profile、类型正确的有限替代到目标所见、计时／内联指令旁路及失败恢复，逐项有产物和退出条件；仍未实现或运行，默认不干预。代码传播与暂停能力也不能由规则数量或局部夹具代替。90天的第一阶段目标需随关键探针门槛复核，不将研究难点直接写成已排定工期的完整承诺。

## 9. 竞争比较及尚未确定的决策

Action Scope 的公开介绍以动态行为揭示与人工交互为主；本次资料不足以确定其具体线程传播覆盖，不能据此断言它只支持新线程。Defender、Joe Sandbox、ANY.RUN 等已有注入分析及自动化能力，CAPE 已有规则化调试和自动 dump；“识别 APC / 线程劫持”或“自动 dump”本身不足以证明领先。

用户进一步授权对Action Scope官方历史分发包作全面静态核实，见[功能与实现核查](ActionAnalyze对ActionScope功能与实现核查.md)。该研究固定输入hash和version=20191230，区分演示宣称、配置绑定、代码通路与未收集范围；已补API入口调用现场候选、WMI／环境干预、网络字节／日志运输、配置SDK与子进程发送侧的实现证据。ROP现用路径未形成多帧跟踪、堆喷告警门控未闭合、Get前后文本缺发送、Loaded不等于Hook就绪均保留边界；不能以此包代表当前新版，也不将字符串或局部算法等同运行可用。产品比较仍需同版本／场景实测，不自动复制其插件runtime或改变首版范围。

本能力拟争取的差异是：单点在线、多跳来源链、区域内容版本、实际执行线程，以及可编辑同步调试与取证流程。产品比较应使用相同样本 / 夹具、版本、系统及配置，保留事实与限制，不把供应商宣称当作实测。

原轮尚待确定的问题如下；本轮[完整开工审查与实施总表](ActionAnalyze完整开工审查与实施总表.md)原28项补入用户指出的栈／控制流分支后为29项总账，并给出工作包。筛选器、文件存储、事件／身份／CLI字段不再只留“实现时再定”。专项契约为具体实施建议，真实机制与性能仍须实测，尚非既有能力：

1. 支持的 Windows 版本、位数、系统保护配置及部署条件。
2. 跨进程语义的完整入口清单和同步插桩方式。
3. 任意区间与所有相关线程的执行观测机制；首命中与持续监听分别如何实现。
4. 允许的性能和目标扰动、完整性降级规则。
5. 活动执行关联的边界，保守传播策略的标记方式。
6. 私有 ABI 依赖的范围、版本准入及长期维护成本。
7. Intel PT / DBI 是否进入原型，以及各自与同步停点的分工。
8. 驱动执行归属与可安全停止的具体对象范围。
9. 规则表达式的具体类型／函数／预算、尚未明确的动作细节、证据保留上限、工作台真实导航入口与分阶段排期；不重置第 6 节已确认的布局和默认值。
