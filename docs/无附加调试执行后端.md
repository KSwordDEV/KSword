# 无附加、无目标注入执行后端

## 范围与当前状态

“无附加”指后端不建立或借用 Windows 用户态调试关系；“无目标注入”指不向目标安装 DLL、VEH 或执行控制组件。两种后端分别报告实际机制，不能把普通 Titan/CE 的 Windows 调试循环当成独立停止通道。

当前 HVM v2 只控制一个强身份绑定的 native AMD64 用户线程：EPT 执行断点、MTF 优先或明确报告的 VMX TF/#DB 边界单步、继续、一次性运行到地址，以及 GPR/RIP/RSP 编辑。其它线程和内核保持可运行。完整 XSTATE、数据观察点、WoW64、AMD 以及完整前端 F7/F9 调试循环尚未由此通道提供。

普通驱动异常后端已实现独立的 TF/DR 异常消费者，并在指定 VM 的 26300.9974 内核通过 CE/Titan 两条实际 API 通道。它不依赖 VMX，不创建 Windows Debug Object，不向目标注入组件。当前是精确映像绑定的实验后端，不代表所有 Windows 内核或 PatchGuard 环境均已兼容。

## HVM v2 结构

- 唯一协议：`shared/driver/KswordArkHvmNoAttachIoctl.h`。请求 232 字节，响应 480 字节，版本 2；旧版必须成套升级。
- 会话由确切设备文件、所有者对象、PID/TID 和各自创建时间绑定。执行与修改必须消费匹配的 `sessionId/stopId`。
- 最多八个执行地址。两个预分配 EPT bank 在普通控制面重建；每次发布配置后经全核屏障，逐核在使用新代次之前 INVEPT，旧 bank 才可重用。
- 同页其它指令及其它线程通过当前 CPU 的普通 EPTP 临时放行，下一次退出恢复受限视图。不会临时放宽共享叶子而让其它核一起通过。
- 安装时锁定 backing，查询重新探测 VA/PFN。映射变化明确标为失效，要求删除后重装；不静默迁移至新代码。会话累计锁页容量为 64，成功全核退出后统一归还。
- MTF/VMX TF 恢复和用户单步分别记账。中断、异常或不匹配线程不报告单步完成；`STOP_STEP` 表示已核对的 MTF 或 VMX TF/#DB 边界，REP 等特殊边界不保证 RIP 一定改变。
- GPR 修改在下一次匹配取指处提交，并生成新的 `STOP_CONTEXT`。不编辑 RFLAGS、DR、SIMD/XSTATE。
- 关闭失败保留恢复身份。所有者/目标退出及文件 Cleanup 撤销当前执行权，不以历史 ring 冒充当前停止。

## GUI 与操作身份

入口为 **内存 → 内存调试 → HVM 无附加调试（实验）/普通驱动无附加调试（实验）**。

原页面属于专业内存/反汇编工作台，外围复用 PrimaryPageStyle、NormalizeToolbarRow，内部控件身份和滚动不由通用框架重排。新增“无附加调试 · 断点与寄存器”工具窗属于参数/执行页，使用 ParameterWorkspace，并以 SecondaryPageLayout 管理独立工具窗主题。断点表显式选择 Compact 操作条，使用 TablePresentation/ResultTableHost。寄存器查看沿用同一 StructuredFieldView 文档与详情投影。

流程为：选定进程和线程 → 只读查询能力 → 显式确认开启 → 请求暂停 → 等待真实停点 → 编辑断点或寄存器草稿 → 明确提交/运行 → 根据新停点确认结果。工具窗关闭不自动继续目标；显式关闭运行控制保留独立内存会话。旧会话的工具草稿不能操作另一个会话。

源码对照了 SystemTimePage、VirtualLocationPage、ParameterWorkspace 及既有 MemoryDebugPage/ExecutionPanel。构建与 GUI 结构验证不能替代深浅主题、窄窗、DPI、背景模式和实际执行的完整验收。

## x64dbg / CE 接口

`KSwordDebuggerCall` 命令 **33 / KSWORD_DEBUGGER_NOATTACH**（HVM v2）和 **34 / KSWORD_DEBUGGER_KERNEL_NOATTACH**（普通驱动 v1）使用独立的持续控制句柄。命令 3 可在离线状态查询此命令的大小与版本；调用新通道不会初始化 Titan 的 Windows 调试事件适配。当前不允许与该适配器已有原生会话、EPT/Shadow 绑定混用。

CE 先以 `KSword.noAttach.useBackend("hvm"|"kernel")` 选择通道，再使用 `KSword.noAttach.query/open/pause/step/continue/close/addBreakpoint/removeBreakpoint/runTo/setRegister`。`open` 必须显式传入确认。请求接受和完成由 `state/stopId` 区分，非停止响应不暴露历史寄存器为当前现场。

独立 x64dbg 插件为 `KSwordNoAttach.dp64`，先用 `ksna_backend hvm|kernel` 选择通道；普通驱动 OPEN 使用 `confirm_boot` 明确确认内核补丁与启动期留驻。提供 `ksna_open PID, TID, confirm [, nested]`、`ksna_query/pause/step/run/close`、`ksna_bp`、`ksna_bc`、`ksna_runto`、`ksna_set`。PID/TID/ID 使用十进制，地址/值使用十六进制。其控制结果在日志显示，原生 x64dbg F7/F9 和 CPU 窗口仍使用原生引擎语义；此插件不把自有停止伪装成原生调试事件。完整 CPU/寄存器前端投影仍需后续适配。

## 普通驱动后端与实机证据

协议为 `shared/driver/KswordArkKernelNoAttachIoctl.h`（IOCTL 0x938、版本 1、232/480 字节）。会话与 HVM 共用排他预约，设备文件、所有者、进程/线程创建时间及 stopId 均核对；原生 Titan/Windows 附加会话不得混入。

当前核对的 OS build 为 26300，精确 ntoskrnl 为 26100.9711 与 26100.9974。9974 的五个目标函数及被调函数逐指令差分、恢复包装器唯一被调关系、两个上下文内部入口均已独立核对，未沿用旧 RVA。9974 文件 SHA256 为 `F6F275F67C7EF44FC2DF2D828658FB31EAFFD41018AC5A0FD9440E08D9912C30`；9711 的最终修复尚未再做硬件复验。

OPEN 使用已验证入口前的填充区和一个完整两字节原子指令建立异常转接，调用当前内核的帧转换及上下文 API。内核缓冲区模式与用户现场模式分开传递；纯 TF 下 Windows 未投影的 DR6 取自同一目标线程分发入口的真实硬件状态。无关异常、混合外部调试原因及高 IRQL 不会冒充用户停点。

普通后端最多 4 个 DR 执行地址，TF/DR 可观察，不修改目标执行字节。关闭确认实际状态恢复和处理者排空；入口原指令恢复后，转接器与模块仍留驻到重启，避免晚到调用进入已释放内存。该后端不实现 PatchGuard 绕过；测试签名、HVCI 关闭及精确映像检查不是长期 PatchGuard 稳定性的证明。

## VMX TF 备用边界与最终双后端验收

MTF 硬件能力仍优先，原路径保留。没有 MTF 时，只有实际支持 MBEC、INVEPT、完整常驻生命周期、NMI/外部中断退出及关闭 ACK-on-exit 的 VMX 平台才报告 `CAP_VMX_TF`（0x20）。选择模式和 QUERY 不开启 VMX；OPEN 仍须显式确认。此位明确表示 TF 可观察，不应把它显示成 MTF。

- 在普通控制面通过 MDL 保持 backing、创建只读/NX 系统映射。TF 路径只接受当前为只读可执行且无 guard 的页；不在 VMX root 查询、分配或读取用户 VA。代码映射和内容并发改变不属于支持范围。
- root 仅对白名单指令类放行；MOV/POP SS、远控制流、INT、SYSCALL、POPF、IRET、LOCK 等特殊边界不进行推测性 TF 放行。拒绝 STEP 保持目标未执行；运行中的无法放行路径撤销执行拦截并保留恢复身份。
- 临时 TF、全部同步异常拦截及外部中断退出只属于当前 CPU，下一次退出先恢复。真实其它异常按硬件描述符重新投递，页故障保留 CR2/错误码；不伪造目标调试事件。原 IF 和目标代码/DR 不修改。
- 实测外部 IRQ 会先于目标指令退出。仅当 RIP/RSP、全部 GPR、CR3 和普通 flags 仍匹配时，对同一个已消费 STEP 有界重试（最多 64 次）；中断处理者不带本方 TF。RF 是 CPU 在 fault/retry 中管理的标志，不因 RF 变化覆盖已完成 STEP；其它标志变化仍使旧停止失效。
- 首轮实机转储 `hvm-vmx-tf-first.dmp` 暴露旧 native-return 在 CPL0 换到用户 RSP 后 push 的双重故障。独立后端恢复改为归还拦截、保留资源，由控制面在内核屏障 Close；不直接从用户停止点执行该 native-return。后续停点中关闭与连续切换均已通过。匹配驱动 PDB 的具体现场保存在 `hvm-vmx-tf-first-context.log`，没有将 CDB 的缺失 ntoskrnl 符号提示当作根因。
