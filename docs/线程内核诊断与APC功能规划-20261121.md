# 线程内核诊断与 APC 功能规划

日期：2026-11-21。范围：立项、源码与符号核对、可行性边界及验收设计；不是实现或发布记录。

## 立项决定

| 用户需求 | 产品范围 | 可行性 |
| --- | --- | --- |
| 1. 使线程 APC 被阻塞、无法投递 | **APC 延迟投递实验**：仅面向 KSword 自有测试线程，有时限、可取消、自动恢复。正常产品线程只做观察。和既有「禁止 APC 入队」分开。 | 文档支持当前线程的 critical/guarded region；未验证远程任意线程的可逆控制，不进入发布范围。 |
| 2. 结束 APC 无法入队的卡死线程 | **线程终止与退出诊断**：区分后端不可用、未入队、已接受、等待超时和已退出；对可控组件提供明确的取消/退出途径。 | 可实现有界处置和验证；没有可承诺普适、安全、强制完成的路径。 |
| 3. R0 线程调用堆栈追踪 | **单次内核栈快照**与**内核事件栈时间线**为两个来源；分别说明捕获时态。 | ETW 采集内核事件栈可立项；任意线程的实时内核栈只按受支持的采集来源和验证覆盖交付。 |
| 4. KTHREAD 结构体解析 | **线程详细信息**：精确类型匹配下的只读字段视图、APC 与等待证据、来源和时间；并入口到调用栈。 | 缓存 PDB 已验证能解出所需字段组；新读路径、版本覆盖和 UI 还需验收。 |

## 本机现场与本轮实证

- **Hime Display 原事件**：两个原 TID 各自有未完成 I/O，进程标记 `IsProcessDeleting`，进程和线程均未触发退出信号，普通挂起计数为零。用户通过产品入口关闭卡巴斯基后，两原 PID 均消失；未取得线程内核栈或对应 I/O 的模块归属。属于第三方防护参与阻塞的线索，不是 APC 阻塞证据，也不是一个可复用的漏洞或驱动归因测试。
- **终止后备路径**：[thread_apc.c](../KswordARKDriver/src/features/thread/thread_apc.c#L877-L888) 先解析三个例程；本机 `ntoskrnl.exe` `10.0.19041.7844` 的 PE 导出有 `KeInitializeApc`、`KeInsertQueueApc`、`KeEnterGuardedRegion`、`KeLeaveGuardedRegion`、`KeAreApcsDisabled`、`KeAreAllApcsDisabled`，没有 `KeRemoveQueueApc`。因此 `0xC000007A` 是到达入队尝试之前返回，不能推出目标拒绝入队。该例程的缺失也不能证明取消工作可以省略。
- **抓栈现状**：[ThreadStackWindow](../Ksword5.1/Ksword5.1/ProcessDock/ThreadStackWindow.cpp#L323-L390) 拿到申请挂起权的句柄后调用 `SuspendThread`，失败即没有用户栈；错误 `5` 可由多个 NTSTATUS 映射而来。现有 `thread detail` 给出 `KernelStack` 等字段，不给出可信的内核调用帧。CLI 和 GUI 都不能把栈指针/边界当成栈展开结果。
- **符号验证**：从本机精确 PDB 和 3 份独立缓存 PDB 提取 `_KTHREAD`；4 份均能提取 `ApcQueueable`、有符号的 `KernelApcDisable`/`SpecialApcDisable`、`CombinedApcDisable`、`WaitMode`/`WaitReason`、`KernelStack`/栈界和 `ContextSwitches`。其中 3 份结构为 1072 字节，1 份为 1216 字节，不能跨版本套用。本机从微软符号服务器取得的 PDB 与磁盘映像 `E2672D6A-6393-04EC-AF7D-417B71DC4D0B/Age 1` 的 PE/RSDS 身份一致：独立读取 PDB 的 DBI Age=1，Info/Summary Age=5，符合[生成器约定](../tools/pdb_offset_generator/README.md#ntoskrnl-deep-runtime-offset-catalog)。从本机 PDB 也已解出 `_KAPC_STATE` 的 pending/in-progress 字段；活跃与保存状态两处同名字段不能按全局字段名取第一个命中。本轮只验证类型提取，未将此布局下发驱动，也未采样实体机上的 `KTHREAD` 字段值。
- **事件栈验证**：本机 `xperf -help stackwalk` 列出 `CSwitch`、`ReadyThread`、`Profile`。仓库已有 [ETW 栈采集样例](../tools/ui_perf/KernelTraceCapture.cpp#L60-L82)和[单归属关联规则](../.claude/memory/ksword-syscall-monitor.md)。这轮未启动实时内核跟踪；确认了工具和源码入口，不把事件注册或能力清单当成实采成功。

## P0：只读线程详细信息（需求 4）

1. **结构化快照**。基于现有 [线程 detail 协议](../shared/driver/KswordArkThreadIoctl.h#L247-L355)、[R0 字段读取](../KswordARKDriver/src/features/thread/thread_detail.c)及现有 DynData/PDB 类型目录做向后兼容扩展。最小首版为身份与时间、线程状态/等待、APC 状态、栈边界、I/O 线索和数据来源。只导出白名单标量与已校验的 APC 状态摘要，不导出整段 KTHREAD、任意内核地址读取或实时 APC 链表枚举。分离 `ApcQueueable`、disable 计数、pending/in-progress、等待原因和终止信号。`WaitReason` 只有在对应等待状态和有效采样中才解释；不由计数/挂起状态推断全部种类 APC 都不能投递。
2. **身份和数据可信度**。冻结 PID/TID + 进程/线程创建时间；R0 在真实引用上复核归属，不能用 UI 的历史地址当引用。私有字段由匹配映像机器类型、RSDS GUID/Age、经验证字段宽度/符号性/位段的 profile 供给。按字段标记有效性、来源与采样时间；不支持、权限不足、采样变动、读取失败与真实零值分开。一次多字段读取不是原子快照；对采样变化返回部分结果，禁止用未知值自动判定危险操作资格。读取沿用 `KswordARKRuntimeReadMemory`，不猜私有布局。
3. **页面接入**。进程主列表的线程页、进程详情的线程页 →「线程详细信息」→ 对象详情类型；共用 `InstallDetailWindowFramework`、`DetailDialogChrome`、`DetailPresentation`、`StructuredFieldView`。对照现有 `ThreadStackWindow` 和 `ProcessDetailWindow` 的线程检查/字段区。全宽身份摘要，分组「概览」「APC 与等待」「栈与 I/O」「布局与来源」；刷新异步，保留旧快照时间与来源。若增加字段结果表，选用紧凑操作条和互补列组；完整导出与复制使用同一份字段文档。现有双击用户栈入口不暗改；新详情由明确菜单和详情内的关联入口打开。

## P1：内核栈与事件时间线（需求 3）

- **快照**：第一阶段支持从用户提供的受信内核转储/调试器证据展开同一 TID 的保存上下文，复用仓库转储/符号链路。再在 VM 中验证只读在线采集来源，必须有可验证的一致寄存器/栈上下文与版本边界。`KernelStack` 是指针，不提供可展开的原子快照；把目标对象引用住也不能锁住栈内容。不可驻留、线程正在运行或身份变化、寄存器缺失、栈切换无法解释时，返回不可用/部分。禁止用扫描栈中像返回地址的数值充当调用帧，不用驱动工作线程自己的栈冒充目标。若在线方案未通过，不把 WinDbg/转储能力包装成「所有线程在线采集」，也不在普通抓栈点击时偷偷制作全机转储。
- **时间线**：复用 ETW 基础与会话所有权规则，用内核 `CSwitch`、`ReadyThread` 和可选 `Profile` 收集启动后的事件栈。R3 管理、按目标呈现，标明事件和栈来自内核 ETW，不借名为自研 R0 快照。依据事件语义区分切出线程、被唤醒线程与唤醒方、采样线程；用 session/QPC/CPU 和载荷身份关联，并以线程生命周期过滤 TID 复用，不能只匹配事件头 PID/TID。必要时用映像加载/卸载证据将历史地址符号化。记录丢失、未配对、身份不明、截断和符号缺失；会话默认有界，只停止自己持有的会话。若线程在采集开始前已静止，没有可归属样本是正常结果。
- **呈现**：调用栈入口可切换「用户栈」「内核快照」「内核时间线」，显示源、时间、完整度和帧地址/模块/符号分层状态；内核时间线可在详情页发起，如跨页常驻通过 `BackgroundTaskRegistry` 登记。离线导入记录来源，不把导入的数据和实时采集混在同一条时间线中。

## P2：APC 投递实验与退出处置（需求 1、2）

- **投递实验**：按 [Microsoft APC 文档](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/disabling-apcs)，critical region 是当前线程语义：延迟普通内核/用户 APC，不能据此宣称 special kernel APC 不投递；guarded region 对当前线程阻止 APC 执行。只在 VM 自有夹具测试线程中进入与退出区域，分开记录“请求入队、入队确认、区域内观察、离开后回调”。采用无副作用回调；固定时限、同线程恢复、等待与回调排空后才能卸载；不持安全关键资源跨等待，不靠提高 IRQL 来长时间阻塞。不对用户指定的第三方 TID 写 `ApcQueueable`、计数或其他调度字段来实现投递实验。现有「禁止 APC 入队」继续明确显示为另一种操作，不复用作本实验的机制。
- **终止处置**：第一步修现有日志/回执，分别保存打开句柄、发出终止请求、APC 例程解析、实际入队、投递证据、线程与进程退出等待各自状态；例如 `backend_unavailable` 不写 `queued`，已经进入退出流程也不等同于退出完成。保留后端缺失时的拒绝和生命周期管理，不为适配未导出取消例程删掉卸载排空要求。对自有、可取消 I/O 的场景可以在拥有者协作下请求取消并等待；对第三方挂住 I/O，诊断提供等待线索，由组件/设备拥有者进行受支持的恢复，不自动停用安全软件或卸载第三方驱动。
- **完成语义**：终止请求和目标的最终退出分开。用同一已核验线程对象的退出信号确认线程结束；结束最后一条线程的回执仍不能代替进程退出信号。到上限后返回“在退出中/仍等待/原因未知”，不通过改信号、直接编辑内核线程状态或清内存制造成功。Windows 文档明确要求进程退出前完成或取消未完成 I/O：[TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)。

## 发布门禁与工作顺序

| 阶段 | 最小验收 | 不通过的处理 |
| --- | --- | --- |
| P0：字段/详情 | x64 Win10、Win11 各至少一份精确映像/符号配置，正常运行/等待/退出中的自有线程与 WinDbg 对照；另验错 GUID/Age、缺字段、零值、TID 复用和关页回执。深浅主题、窄窗、双语和导出由真实主程序验收。 | 布局不符只给公共字段，私有字段不可用；不能用相邻版本填空。 |
| P1：栈 | Win10、Win11 VM 用已知调用链分别验证运行、等待、切出/唤醒和退出；对照 WinDbg/WPA。同一目标已停止调度、事件丢失、映像重载、身份变化、坏栈/边界时，必须正确给出部分或无样本。 | 允许仅发布 ETW + 离线证据，不冒充挂起线程在线回溯。 |
| P2：实验/处置 | 仅 VM 自有测试对象；验证普通/特殊 APC、正常投递/离开区域后投递、取消/超时/卸载排空；另用正常退出、自有可取消 I/O、故意延迟完成 I/O 三类控制夹具核对终止回执。 | 任一情况下不可恢复或产生假成功，就不发布主动功能，只保留诊断。 |

建议顺序为 **4 → 3（时间线和受信快照并行验证）→ 2 的诊断/回执 → 1 的 VM 受控实验**；P2 的主动处置不作为 P0/P1 发布前置。实现时共享协议只落 `shared/driver/`，业务留在 `features/thread/`，由 `ArkDriverClient` 供主程序使用；允许先以现有 `thread detail` 验证字段契约。新增 CLI 时同步内置 help/CLI 文档，新增 IOCTL 同步 CI 测试计划；源码登记 `.vcxproj`/`.filters`，适用构建维持 WDK `/WX` 与 HostX64。此规划只新增文档，未改协议、驱动或 UI；未重新加载或修改实体机内核，也未完成 VM 动态验收。

## 内核事件栈与动态字段交叉核验

- Win11 `26100.9711` 的内置 WPR `CPU` 配置实采约 2.12 秒。自有线程的 QPC 窗口内按载荷 PID/TID 命中 305 条 `StackWalk`；108 条至少包含一个落在同次轨迹记录的 `ntoskrnl.exe` 映像区间内的非零地址，最深 18 帧。三条另用同一 QPC 和 CPU 关联 `SampledProfile` 并核对载荷 TID。事件头 ID 为哨兵值，不能用于归属。只停止本次 WPR 实例，既有循环日志会话与固定 SSH 保持可用；来宾保留原 ETL 与夹具 JSON。此结果不是实时线程栈快照，也未验证符号名称和调度事件栈归属。
- `tools/etw/verify_thread_sampling.py` 对上述 Win11 采样回放：305 条目标 StackWalk、159 条目标 SampledProfile、153 对无歧义的同 QPC/CPU/TID 关联，其中 29 对含已核对的内核映像帧；72 个有歧义的键排除，不算作 CPU 样本配对。保留“命中目标的所有 StackWalk（108 个含内核帧）”与“可归属于同一 CPU 样本的子集（29 对含内核帧）”两个不同口径。六项解析和拒绝用例通过。仅处理离线证据，未接入产品的 R0 刷新。
- Win10 20H2 OS `19042.631`（内核 PE `19041.631`）：WPR 开始后保存报 `0x80010106`，随后使用公开 ETW API 和系统自带 `tracerpt` 成功采集 `2.617 s`，夹具窗口 `2.001 s`。按 StackWalk 载荷 PID/TID 与同一 QPC、CPU 的 SampledProfile 核验至少 151 个不同采样（局部核验下界，不是全轨迹计数）；其中一条有 12 帧，11 帧地址落在同次轨迹所记录的 `ntoskrnl.exe` 映像区间内。该次轨迹报告 0 个事件丢失、0 个缓冲区丢失。只停止本次新建会话；来宾保留原始 ETL（6,684,672 字节）和夹具 JSON。此项仍是事件采样，不代表该线程的瞬时栈或其他事件类型都已验证。
- `tools/verify_thread_accessor_offsets.py` 从两份精确磁盘 PE 的公开 getter 指令独立定位 `Process`、`InitialStack`、`StackBase`、`StackLimit`；两台 VM 版本合计 **8/8** 与各自 PDB 一致。该脚本只读磁盘映像，按 SHA256 锁定 PE；函数缺失、转发、未知代码形态或越范围位移均不当作已定位。仓库驱动已经对这四项有运行时访问器路径；这次交叉核验不是新运行时解析器，也没有可靠依据从这四个 getter 推出 `KernelStack` 或其余字段。
- 复现离线校核：`python tools/verify_thread_accessor_offsets.py --corpus-root <语料库根> --report <语料库根>/profiles/ksword_thread_symbol_metadata/selected.json`。脚本直接消费批处理样本，不依赖临时样本文件。
- `process thread stack query` 的 `--backend r0` 已接入正式 CLI，复用既有只读驱动客户端。宿主运行自有工作线程回归：默认 R3、显式 R3 均采到 25 帧，原挂起计数为 0 且恢复成功；缺驱动 R0 返回 2、`trust=unavailable`、`frames=[]`；错误创建时间在发送驱动请求前拒绝，R0 不接受帧数限制。CLI 的默认 R3 不自动调用 R0；GUI 首次回退语义不变。
- Win11 使用与正式 Release 哈希一致的 CLI 和三个运行库；两条 R3 请求各得到 5 帧、挂起计数 0 和恢复错误 0，`walkWin32Error=487`、退出码 6（部分展开）。无驱动 R0、错误创建时间、R0 帧数参数分别返回 2、3、1。自有工作线程正常退出，清理只触及本次暂存目录，固定 SSH 和原 ETW 证据均保留。
- Win10 经 VIX 验证同一 Release CLI 和三份运行库，SHA-256 均一致。默认和显式 R3 分别取得 14 帧、10 帧，均因 `walkWin32Error=487` 返回部分结果（退出码 6），且 `resumeWin32Error=0`，原线程能在每次采样后响应。`--limit 1` 返回 1 帧并标为截断。现有驱动下显式 R0 返回退出码 6、`trust=unverified_clue`、4 个非空线索字段及 0 帧，线程采样后仍可响应；这不是仅有 `KernelStack` 的实机样本。格式错误的 FILETIME、越界帧数和 R0 携带帧数参数均返回 1；格式正确但不匹配的 FILETIME 返回 3。自有夹具正常退出，专用来宾暂存目录已清理，既有驱动及 ETW 证据保留。
- 最新 Qt 主程序 Release/x64 编译及双语审计通过；独立页使用共享详情外框、摘要、字段投影和工具带，与源进程窗口不联动。源码已核对双击及右键入口、首次加载状态、采样前后对象身份和复制口径。当前宿主运行的是更早启动的高完整性实例，当前执行器不能通过 UIA 核验该实例，未操作或关闭用户窗口。候选 UI 的真实导航、窄窗、DPI、主题及复制显示仍需验证，未用编译或伪页面代替。

## 离线内核转储展开验收

- Win10 VM `19041.631` 的 2026-11-17 VMware 快照可通过 `vmss2core -W8` 转换成 Windows 完整内存转储。使用匹配的本地内核符号，正式 Release CLI 对 PID 4 的 TID 12、36 分别展开 7 和 8 个内核帧。两者首条指令相同，但首帧栈指针不同；后续分别进入 `KeWaitForSingleObject`／`PopIrpWorkerControl` 和 `KeRemoveQueueEx`／`ExpWorkerFactoryManagerThread`。帧顺序及首帧 RIP/RSP 与同一转储的微软调试器 `.thread`、`r rip,rsp`、`kn` 对照一致。微软调试器文本基准在 `.codex-build-logs/ksword-win10-dump-reference.txt`，原始内存证据保留在项目外的 VM 证据目录，不随产品发布。
- 正式 CLI 的正反例：TID 36 的进程和线程 FILETIME 同时匹配时返回 8 帧；帧数上限为 1 时只返回同一首帧，标记 `partial`；错 PID 或线程创建时间错一个单位均返回 `identity_mismatch`、零帧。结果只证明转储时刻的栈，不证明任意现场线程可实时展开。R0 查询仍只提供栈指针及边界线索。
- GUI 入口为线程调用栈 →「打开内核转储」；参数执行型工具窗采用 `ParameterWorkspace`、共享详情窗外壳及紧凑表格操作条。GUI 通过同目录 CLI 隔离主程序已经加载的系统 `DbgHelp`；Release/x64 主程序构建、语言包与主题门禁通过。尚无该转储窗的双 VM 实际 GUI 验收，Win11 未取得可用内核转储。
