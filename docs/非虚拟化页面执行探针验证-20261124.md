## 1. 用户澄清与判断修正

此前讨论把“迁移准入时只阻塞发起者 A，B 原有业务可以继续”扩大成了命中后也不允许停止 B。2026-11-24 用户澄清：执行命中后可以统一停止，再按需放行。

两者可以共存：准入阶段只保持本次发起操作；目标执行探针命中后，为页面重新设防建立内部停止组。没有用户断点时可以自动处理并继续，有用户断点时才按指定范围保持用户停点。

因此，恢复页面执行权限之前先停稳其它执行者，选定线程受控前进后重新设置 NX，最后才恢复其它线程，是可继续推进的非虚拟化路线。此前的 NX 漏报实验只否定“其它线程仍可运行时直接恢复 RX”，没有否定统一暂停后的调试式放行。

## 3. 第一组：PAGE_GUARD 的能力与盲区

`ThreadpoolExecutionProbe.cpp` 用公开线程池 API 建立专用池，最大、最小工作线程数均为 1。先执行预热工作，再给 EXE 自带 `.ksprobe` 映像页设防。被测函数只增加自有计数，不含载荷，也不修改代码。

独立事实来自被测函数中的执行计数；VEH 单独记录异常访问类型和实际 TID。控制器和异常处理器不在被测页内。

| 用例 | 实际结果 | 支持的结论 |
| --- | --- | --- |
| 设防后由预热线程进入 | 真实 TID 与预热线程一致，1 次执行告警、1 次副作用 | 在这个受控页面上可以发现既有线程池工作线程的首次进入 |
| 不重设告警，再进入一次 | 副作用增加，异常数不变 | PAGE_GUARD 不提供持续监听 |
| 手动重设，再进入 | 再产生 1 次执行告警 | 可恢复一次告警，不证明重设过程中没有窗口 |
| 先读取同一代码页，再执行 | 读取产生告警；后续执行无新告警 | 读取会消耗 Guard，访问告警不能一律标为执行 |

此组核对 `MEM_IMAGE` 和原始 `PAGE_EXECUTE_READ`。它没有修改映像字节，没有构造 COW，也没有模拟实际线程池私有结构篡改。

## 4. 第二组：保留其它执行者时恢复 RX 的窗口

继续使用同一预热线程池工作线程。控制器将代码页改为只读、不可执行；工作线程触发执行 AV 后，异常处理器恢复 RX，然后保持该线程等待。控制器主线程这时进入同一页。

结果：首线程仍在异常处理器中，主线程已经完成被测副作用；NX 异常数仍为 1。最终主线程与工作线程均正常完成，总副作用为 6，其中前 4 次来自第一组。

这证明跨线程放行窗口确实存在；本组没有安排两个 CPU 同时取指，也没有测量窗口时长。它不证明 NX 会自行清除：本测试明确调用了恢复 RX 的操作。

## 5. 第三组：统一停止后按需放行

`StopWorldExecutionProbe.cpp` 新建两个自有原生工作线程，等两者发布就绪后才开始设防。两者都执行 EXE 自带 `.ksstop` 中的普通函数。此组用原生线程控制变量，第一组另行验证线程池复用；不把两组拼接成一个已完成的线程池篡改场景。

控制器按以下顺序执行：

1. 保持页面 NX，等待 T1 的执行 AV。异常处理器只登记该自有线程并等待控制许可。
2. 对 T1、T2 分别调用 `SuspendThread`，再读取 `CONTEXT_CONTROL` 确认可以取得停止现场。只有成功持有并确认的线程才进入放行屏障。
3. 给 T2 发出工作许可，但保持其真实挂起计数；此时仍无被测副作用。
4. 将页面恢复 RX，只归还 T1 的本次挂起计数。T1 通过自有 TF 单步前进，T2 保持停止。
5. T1 的 RIP 到达页外后，异常处理器清除自有 TF，先恢复 NX，再发布重设防回执并等待。
6. 重新持有 T1，才恢复 T2。T2 进入同页时仍触发独立执行 AV；随后采用相同步骤完成执行和重设防。
7. 发出完成许可，只归还自己持有的挂起计数，等待两个线程正常退出。清理器恢复原保护、移除自有 VEH、关闭本次句柄。

最终运行记录：

```text
STW_PASS all_owned_workers_held_before_rx
STW_PASS selected_worker_steps_and_rearms_before_other_release
STW_PASS second_worker_still_faults_after_first_was_allowed
STW_PASS two_independent_faults_two_completed_image_effects
STW_PASS both_workers_exit_with_own_suspend_counts_released
STW_EVIDENCE tids=22124,42404 faults=1,1 steps=2,2 effects=2 failure=0
STW_RESULT=PASS failures=0
RESULT=PASS failures=0
```

21 项断言通过，其中本组为 5 项；每个线程各触发一次 NX 异常、两次 TF 事件，独立副作用合计为 2。这里的“统一停止”只覆盖两个事先持有句柄的工作线程，控制器继续运行；测试没有枚举并暂停自身全部系统／运行库线程。

这个结果支持用户提出的调试式放行次序，也修正了“必须让普通页权限表达逐线程执行资格”的前提。产品仍要保证恢复 X 的整个时段内，停止组之外没有其它可进入该页的执行者。

## 6. 产品级后续门槛

| 工作项 | 当前证据 | 下一步需要验证 |
| --- | --- | --- |
| 停止范围 | 固定两个自有线程，逐个持有真实句柄 | 目标进程完整线程集合、退出／新生竞态、已存在外部挂起及并发异常队列 |
| 控制器可靠性 | 控制器与目标函数分处不同页，工作线程不持有业务锁 | 外部控制所有者、暂停目标不能阻塞控制所需的堆／加载器／日志锁，恢复失败仍保留责任 |
| 执行推进 | 简单计数函数，可在两次 TF 内退出测试页 | 同页正常代码、跨页指令、调用／返回、异常、系统调用、长循环、自修改和 TF 干扰 |
| 任意代码洞 | 页独占、稳定代码、原始统一 RX | 与正常代码共页、多个保护类型、映射／内容版本变化以及同页不同合法入口 |
| 传播来源 | 本组没有外部写入 | 写入前设防、成功范围、共享别名、驱动代写与来源证据，不能由执行命中反推写入者 |
| 调试扰动与性能 | 一次受控运行通过，无性能结论 | 冻结 P50/P95/P99、最长暂停、每次重设防步数、CPU、异常率、队列积压与资源峰值 |

需要持续监听同页后续执行时，不能只单步第一条指令就恢复所有线程：RIP 可能仍在不可执行页内。本夹具让选定线程在其它线程停止时前进到页外，再重设 NX。产品应单列“长期停留页内”的预算与处置，不允许没有上限的内部单步循环。

## 7. 普通无附加后端的静态边界

源码核查发现以下现有条件，与夹具成功分别记录；本轮没有修复这些产品代码：

- `kernel_noattach.c` 的绑定与 `kernel_noattach_events.c` 的异常消费先核对已知主线程。现有接口仍不能先登记进程区域再发现任意未知 worker。
- `DebuggerBackend/KswordIndependentFrontend.cpp` 的进程打开权限不含 `PROCESS_VM_OPERATION`，但内存观察使用同一进程句柄调用 `VirtualProtectEx`。这属于待修正的受理前提。
- 当前页级观察首命中退休，前端在返回停止前恢复原保护；恢复返回值、控制端死亡及页面恢复责任仍需完善。不能把当前一次性观察直接接成持续全线程探针。
- 附加线程行主要登记挂起，不等于已经为这些线程安装 DR／区域执行传感器。四个 DR 槽与另四条内存观察是不同资源。
- 普通实验后端仍有精确内核身份、系统保护配置和部署门槛。此次 Windows 10 自有 VEH 夹具没有运行该驱动后端，也没有扩展其支持矩阵。
