# Stop-group snapshot draft amendment

This amends the read-only A0 projection against [sync stop plan §2 and §4.3](../../docs/ActionAnalyze同步全局断点与性能复查.md). It adds no method, token, runtime, driver or control authority. Vectors use the existing top-level `base | set` replacement convention and test JSON Schema acceptance only.

- `members` is the nonempty frozen request set. An `origin` may be outside it; neither origin nor incidental scope changes the membership revision or hash by implication. A held origin can supply the real hold for `held-partial`, even if no member was successfully held. `held-complete` still requires every frozen member to be held or exited, with at least one frozen member held. Origin phase describes the intercepted boundary; a group state never independently proves synchronous interception there.
- `origin-held` resolves the exhausted-membership case: origin must be present with `hold=held`, and every frozen member must be `exited`. That combination uses `origin-held` unless actual release/recovery work takes precedence; it cannot remain `group-building` or claim `held-complete`, `held-partial`, `not-held`, `released` or `ended`. Empty membership is still invalid. The retained origin's identity must resolve outside the exhausted frozen set at the existing runtime identity/consistency gate.
- A released frozen member is no longer held and can make the retained group `held-partial`. This includes selective continue after a previously complete hold. Partial requires both a real held origin/member and a frozen member in `pending`, `not-held`, `released` or `unknown`; an unresolved query alone is not a real hold.
- Origin now also admits `release-pending` and `recovery-required`, so an origin outside the frozen set can expose its remaining responsibility. Explicit origin/member recovery requires group `recovery-required`. Explicit origin/member release pending requires group `release-pending` or `recovery-required`; recovery has precedence when both occur. This prevents a cleanup failure being summarized as an ordinary partial hold or successful release.
- These implications are deliberately one-way. Group `release-pending` or `recovery-required` may remain after every listed hold is released/exited, for native-event, incidental-scope, protection or other restoration responsibilities in the owner's ledger. The projection is not that ledger. All listed holds being clear does not entail group `released`. Conversely, `released`, `not-held` and `ended` require cleared extra responsibilities at runtime as well as their schema conditions. Released means this group's responsibilities are cleared; it does not prove a thread ran or that another group's hold is gone.
- Incidental IDs describe observed scope associated with this group, not currently owned per-thread holds or a release receipt. They may remain in a released snapshot. `verified` with an empty list means checked empty; `partial` is a known subset and may be empty after incomplete collection; `not-collected` requires an empty list and makes no empty-set claim. Quality is independent of frozen-member completion and cannot authorize skipping cleanup. A native event may affect a frozen member too; no structural disjointness rule is introduced.

Ledger-owner handoff: `origin-held` retains the exact native-event obligation and conveys no release authorization. Only explicitly confirmed release of that event (receipt or corroborated owner readback), or explicitly verified retirement of that event on exit, can permit a terminal transition, after all other responsibilities are cleared. Membership exhaustion, an origin exit observation, a sent continue request, a timeout, or an incidental-list quality change cannot do so. A missing/unknown origin must not be fabricated as held; unresolved native release/recovery is reported with the applicable nonterminal state even when all listed threads have exited. This is an offline serialization contract; no native call, runtime state machine, control method or receipt format is added here.

The existing runtime gates remain mandatory: u64 numeric maximum; instance resolution and member identity uniqueness; membership hash/revision; origin/member responsibility consistency when the same thread appears in both; actual holds, exits, native exception ownership, exact release and all residual recovery work; revision ordering and race handling. UUID spelling, state labels and shape validation prove none of these. Snapshot vectors check admissible serialized states, not whether a transition has its required exact-event proof. `futureThreadGate` stays separate from frozen completion and from `regionReady`/the required executor closure.

Live `threadId` retains lowercase UUID-shaped spelling here. Persisted sample objects retain `{sampleId, objectId}` with a sample-local positive u64 `objectId`; the owners must define their mapping separately. No ID type or sentinel policy is silently unified.

Incidental quality remains evidence completeness, not ledger completeness; exact native scope collection and cleanup receipts remain an owner contract rather than a schema-derived guarantee. All existing objects stay closed with `additionalProperties=false`; the group-state enum addition does not add native-event keys, receipt fields or release tokens to the snapshot.
