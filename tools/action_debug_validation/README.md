# ActionAnalyze R3 debug mechanism validation

This independent native fixture tests real Windows Debug API stops in children of its own executable. It is planning evidence, not a product debug engine. It does not load the KSword driver or debugger backend, accept arbitrary target PIDs, attach to another application, inject code into third-party processes, or change UI, network or security settings.

Run from the repository root:

```powershell
pwsh -NoProfile -File tools/action_debug_validation/Invoke-Validation.ps1
```

The optional `-MSBuild` argument must name an installed `amd64/MSBuild.exe`. The script reads back and validates absolute build paths and the HostX64 compiler before one incremental Release/x64 build, uses BelowNormal priority, requires `/W4 /WX`, and disables vcpkg app-local deployment. `IntDir` is fixed at `tools/action_debug_validation/x64/Release/`; `OutDir` is the repository's unified `Ksword5.1/x64/Release/`. The executable is `ActionDebugValidation.exe`. No runtime copy, Qt deployment, or test configuration is created. Build products remain at these standard locations.

Each invocation writes unique, non-overwriting text/JSON evidence under `.codex-build-logs/behavior-planning/action-analyze-r3-debug-<UTC timestamp>-<script PID>-*`: build/run logs, source and executable SHA-256, OS, exit codes, assertions, exact child PIDs, held stop details, Job readback and cleanup records. Failed invocations retain their own evidence.

| Scenario | Actual mechanism and assertions |
| --- | --- |
| Machine instruction step and call step into | Restore/rewind owned INT3, set TF, receive `EXCEPTION_SINGLE_STEP` after one MASM NOP; step the five-byte near CALL into the exact leaf entry and check the pushed return address. |
| Return from current known frame | Read `[RSP]` at the controlled leaf entry, install a temporary INT3 at that known return boundary, require the selected main thread's real breakpoint event and original caller RSP plus RAX=42. |
| Call step over | Stop at the fixed CALL, run to its fall-through temporary breakpoint, verify actual RIP, caller RSP and RAX=42. |
| Earlier user breakpoint | Report a real user-breakpoint stop inside the callee, restore/rewind that breakpoint, cancel/read back the temporary breakpoint, single-step the restored NOP once, explicitly rearm the known return boundary and observe completion. |
| Earlier exception | Report a real first-chance `EXCEPTION_ILLEGAL_INSTRUCTION` from the fixed two-byte UD2, cancel/read back the temporary breakpoint, explicitly skip only that known fixture instruction, rearm and observe the return. This is a fixture recovery policy, not arbitrary application exception handling. |
| Controlled abort while stopped | Leave an owned temporary breakpoint and TF in a held stop; cleanup restores/read-backs bytes and clears/read-backs TF, terminates only the exact self-created child handle, drains exit events, observes the process signaled and matches native exit code to the event. Termination is cleanup, not successful target recovery. |

`DebugSession.cpp/.h` own process/thread/Job handles, debug events, temporary/user breakpoint responsibilities and bounded cleanup. `DebugScenarios.cpp` owns assertions and the narrowly scoped self-child entry point. `FixtureCode.asm/.h` provide fixed benign instruction labels, a single normal CALL and a leaf with no prologue. All sources are registered in the project and filters. Software INT3 writes affect only the private self-created process image, temporarily restore original protection, flush the instruction cache and read bytes back. No injected executable payload or remote thread is used.

Children use `DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED`, with handle inheritance disabled. Each gets its own unnamed, noninherited `KILL_ON_JOB_CLOSE` Job before first resume; Job membership, flags and noninheritance are read back before admission. Failure cleanup uses retained exact process/thread handles, not process-name sweeps. Debug wait has a 12-second per-session deadline; cleanup drains for at most 2.5 seconds plus a 0.5-second process wait. The outer script has an 80-second watchdog for its exact parent instance. Parent death is guarded by Job semantics but is not fault-injected by this fixture. Normal scenarios must exit zero without forced termination; the abort scenario deliberately exits 99.

Assumptions and limits: native AMD64 Windows, same executable image and account for parent/child, Windows permission to debug one's own child and assign a nested Job. No `SeDebugPrivilege` is enabled or required by design; host policy can still refuse debug creation or Job assignment, which must fail explicitly. Debug events stop the debuggee according to Windows semantics and are not a no-attach or R0 implementation. The first unowned loader breakpoint is consumed during startup. Only the known main thread and known assembly call/leaf return are supported: no general disassembler, stack unwinder, recursion, tail calls, arbitrary frame selection, shared return addresses, concurrent breakpoint ownership, arbitrary exception forwarding, attach/detach, cancellation stop acquisition, or performance claim. Earlier-breakpoint/exception coverage is a minimal controlled interruption matrix. It cannot establish production recovery, full thread admission, product GUI behavior, R0 capability or completion of ActionAnalyze.

The first run exposed fixture errors and remains recorded separately: the address of a MASM `PROC` symbol could resolve through an incremental-link thunk instead of the direct CALL target; use an explicit byte entry label, disable incremental linking and independently decode the fixed CALL displacement. Also, Job `ActiveProcesses` counts terminated processes until all references are released, including external references this fixture cannot close. The second run corrected entry labels and event-handle ownership and passed the step assertions, but still failed the inappropriate Job-zero assertion: all five child processes had real exit events and were gone from the outer process lookup, while immediate accounting still read one. Cleanup therefore uses the process object's signaled state and matching native/event exit codes as the liveness oracle, closes its retained handles and preserves the actual Job count as diagnostic evidence; it does not claim accounting drained to zero. Windows closes debug-event process/thread handles when exit events are continued; the fixture closes only the event's file handles itself. See Microsoft's [ContinueDebugEvent ownership](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent) and [Job accounting semantics](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information). Failed-run counts are not added to a later successful run.
